# Драйвер на Rust

`AcerHelperLampArray` существует в двух сборках: **C** (`driver/AcerHelperLampArray/`) и **Rust**
(`driver/AcerHelperLampArrayRust/`). Это один и тот же пакет — то же имя `.sys`, тот же INF, тот же контракт
с приложением, — собранный двумя разными тулчейнами. **Поставляется C-сборка**: `dist/driver` — это она, и
ничего в ней не изменилось. Rust-сборка лежит рядом, в `dist/driver-rust`, и остаётся добавлением, пока
владелец не скажет иначе.

Этот файл отвечает на три вопроса: **что выяснила разведка** (и почему ответ не тот, которого ждали), **чем
Rust-сборка отличается по устройству** и **что в ней проверено, а что нет**.

---

## 1. Разведка: чем всё закончилось

Задача ставилась так: выяснить, до какого шага дойдёт сборка драйвера на Rust под Wine, и там остановиться.
Ожидаемый путь — `rustup` с целью `x86_64-pc-windows-msvc`, MSVC-линкер и его библиотеки под Wine
(`msvc-wine`), WDK-инструменты, и `windows-drivers-rs` (`wdk-build`, `wdk-sys`, `wdk`, `wdk-panic`,
`wdk-alloc`, `wdk-macros`) плюс `cargo-wdk` как набор крейтов.

**Wine не понадобился.** И это не «получилось обойти» — это измеренный факт: линковка Rust-драйвера
проходит тем же линкером, которым уже собирается C-драйвер. Ни `link.exe`, ни библиотек VC, ни Wine в
цепочке нет.

**А набор крейтов `windows-drivers-rs` не работает вообще.** Не «работает с оговорками» — не компилируется
на Linux-хосте, по явному запрету в исходнике.

### Что именно упирается

| Шаг | Результат |
|---|---|
| Rust + цель `x86_64-pc-windows-msvc` | **работает** — rustc 1.98.1, цель ставится `rustup target add` |
| `lld-link` по Rust-объектам против WDK из NuGet | **работает** — PE32+ Subsystem NATIVE, импорт `WDFLDR.SYS` + `ntoskrnl.exe` |
| bindgen по заголовкам WDK на Linux | **работает** — включая `const _: () = …` проверки раскладок, которые bindgen генерирует для каждой записи |
| Wine, msvc-wine, MSVC-линкер | **не нужны** |
| `wdk-build`, `cargo-wdk`, а с ними и `wdk-sys` | **не работают** — см. ниже |
| `stampinf`, `inf2cat`, `signtool` (`cargo wdk package`) | не понадобились: INF штампуется тем же `sed`, что и у C-драйвера, `.cat` не делается (как и в C-сборке) |


`compile_error!` стоит в не-Windows ветке `#[cfg(target_os = "windows")]`, то есть это не ошибка настройки
окружения, а отказ на уровне исходника: ни `WDKContentRoot`, ни установленный WDK, ни Wine этого не
меняют. Обойти нечем — `cargo-wdk` тянет тот же `wdk-build`, а `wdk-sys` вызывает его из своего build.rs
(`configure_wdk_library_build_and_then`). Весь набор недостижим с Linux-хоста.

### Что вместо него

Сохраняется **приём**, а не крейт:

- **bindgen** запускается из `build.rs` по тому же WDK из NuGet, против которого компилируется C-драйвер.
  Он кросс-платформенный: dlopen `libclang` и чтение заголовков. Для каждой записи он генерирует
  `size_of`/`offset_of`-проверки, так что раскладки структур проверяет компилятор на каждой сборке, а не
  человек при переносе.
- **Таблица функций KMDF** подключается вручную (см. §3, дефект 3). Это то, что делает `wdk-sys`; здесь это
  делает `build.rs` — и, что важнее, делает это **от одного пина версии**.
- Линковка — `lld-link` с теми же флагами, что в `driver/build.sh`.

`cargo-wdk` не нужен: он занимается упаковкой (`stampinf`, `inf2cat`, `infverif`, `signtool` — нативные
Windows-бинарники), а INF в этом проекте и так штампуется `sed`-ом, и `.cat` не собирается.

### Про QEMU

Маршрут «если Wine не пойдёт — считать QEMU» **не открывался**: Wine не понадобился, потому что не
понадобился MSVC. Ответ на смежный вопрос, который в нём был, короткий: **user-mode QEMU (`qemu-x86_64`)
здесь не добавляет ничего** — архитектура хоста и цели для user-mode части совпадает, а Windows-бинарники
он всё равно не исполняет. Полноценная ВМ (`qemu-system-x86_64` + ISO Windows + установка + лицензия) без
KVM — это программная эмуляция x86-64, то есть порядок «часы на загрузку ОС, десятки минут на сборку», и
она нужна была бы ровно для одного: **запустить MSVC-`link.exe`**, если бы без него не линковалось. Он не
нужен. Оценка снимается вместе с предпосылкой.

## 2. Что проверено и что нет

**Предел проверки — «компилируется и пакуется», и ничего сверх.** Драйвер **не загружался и не исполнялся**:
он неподписанный, для загрузки нужен тестовый режим, а ошибка в драйвере — синий экран на рабочей машине
владельца. Ни одно утверждение о поведении в ядре здесь не делается.

Проверено измерением:

1. **Собирается.** `cargo build --release`, 0 ошибок, 0 предупреждений (включая сгенерированный bindgen-код).
2. **Линкуется в драйвер.** `dist/driver-rust/AcerHelperLampArray.sys` — 25600 байт, PE32+ x86-64,
   `Subsystem = 1` (NATIVE), импортирует ровно `WDFLDR.SYS` и `ntoskrnl.exe` — те же два, что у C-сборки.
   Рядом валидный PDB (`Microsoft C/C++ Program Database 7.00`, 479232 байта). `.cat` нет — как и у C.
3. **Вызов идёт через таблицу функций.** Дизассемблер `DriverEntry`: `mov -0x241a(%rip),%rax` (загрузка
   `WdfFunctions_01033`) и `call *0x3a0(%rax)` — смещение 0x3a0 = 928 = 116 × 8, а 116 это
   `WdfDriverCreateTableIndex` из `wdffuncenum.h`.
4. **Таблицу определяет `wdfdriverentry.lib`, а не мы.** `WdfFunctions_01033` и `WdfDriverGlobals` —
   определённые символы `stub.obj` в этом `.lib`; драйвер их не импортирует. Ровно так же устроена
   C-сборка. Единственное, что Rust-сторона обязана определить сама, — `WdfMinimumVersionRequired`
   (в C его печатает `wdffuncenum.h` как `__declspec(selectany)`), и линковка без него падает:
   `lld-link: error: undefined symbol: WdfMinimumVersionRequired >>> referenced by wdfdriverentry.lib(stub.obj):(WdfBindInfo)`.
5. **Контракт с C# не сдвинулся.** См. §4.
6. **INF побайтово совпадает** с INF в `dist/driver` (3145 байт, `diff` чист): это один и тот же файл,
   подставленный одинаково. `KmdfLibraryVersion = 1.33`, `NTamd64`, `Security`, `PnpLockdown`,
   `LowerFilters = vhf`, `KmdfService`, пол `10.0...22621`.
7. **Сборка идёт в образе.** Стадия `driver-rust` собирает и пакует, и сама же проверяет три вещи:
   INF объявляет ту же версию KMDF, что закреплена; образ — PE NATIVE; `WDFLDR.SYS` в импорте.

Не проверено:

1. **Ничего о поведении.** Драйвер не загружался. Верификатор, IRQL, гонки, жизненный цикл VHF — не
   наблюдались.
2. **Структуры WDF не сверялись с C-сборкой побайтово.** Их раскладки — из bindgen, и bindgen проверяет их
   против заголовков; но это проверка против *заголовка*, а не против того, что видит C-компилятор в
   `driver.obj`.
3. **Побайтового совпадения `.sys` с C-сборкой нет и быть не может** — разные компиляторы. Сверялись
   форма, подсистема, импорт и INF, а не байты.
4. **Один драйвер на образ.** Две сборки одного пакета не проверялись одновременно в одной системе: у них
   одно имя `.sys` и одна служба, так что ставить их вместе нельзя по построению.

## 3. Четыре дефекта C-драйвера: как они становятся непредставимыми

Каждый из четырёх — не «исправлен», а **сделан невыразимым**. Ниже — механизм, которым это обеспечивается,
и место, где его можно проверить.

### Дефект 1 — `WdfIoQueuePurgeSynchronously` из колбэка очереди

C-драйвер вызывает его в обработчике STOP IOCTL. KMDF это запрещает (очередь не может синхронно
вычищаться из собственного колбэка — это ожидание того самого колбэка, который сейчас исполняется), и
верификатор на это ругается.

**В Rust его нет.** В `src/ffi.rs` для него нет ни индекса в таблице, ни типа `Pfn*`, ни обёртки — в модуле
есть раздел «What is deliberately NOT here», и проверить это можно одной командой:

```
grep -rn "Purge" driver/AcerHelperLampArrayRust/src/    # пусто
```

Поведение, ради которого он был, — разблокировать припаркованный `WAIT_FRAME`, когда приложение перестаёт
слушать, — отдаётся `cancel_parked`: запрос извлекается из ручной очереди (`WdfIoQueueRetrieveNextRequest`)
и завершается `STATUS_CANCELLED`. Фреймворк делает с припаркованным запросом при purge ровно то же, поэтому
приложение видит тот же `ERROR_OPERATION_ABORTED` (995), который `LampArrayTransport.Stop` и так считает
своей отменой, а не отказом.

### Дефект 2 — очередь уровня Passive, к которой обращаются на DISPATCH_LEVEL

В C `FrameQueue` создаётся с `WDF_NO_OBJECT_ATTRIBUTES`, то есть `ExecutionLevel` наследуется от устройства
(`WdfExecutionLevelPassive`), а читается из `AhlaEvtSetFeature` — колбэка `EVT_VHF_ASYNC_OPERATION`,
документированного как `IRQL <= DISPATCH_LEVEL`. Наследование здесь и есть механизм дефекта.

**В Rust уровень — параметр типа, а метод существует только у одного уровня** (`src/irql.rs`):

- `Queue<L>` — обёртка над `WDFQUEUE`, где `L` это `Passive` или `Dispatch`;
- `Queue::create` **сам** пишет `ExecutionLevel` в атрибуты из `L`; перегрузки, принимающей чужие атрибуты,
  нет, и пути `WDF_NO_OBJECT_ATTRIBUTES` тоже нет — наследовать нечем;
- `retrieve_next()` реализован **только** на `Queue<Dispatch>`.

Ручка кадровой очереди лежит в `Context::frame_queue` как `Queue<Dispatch>`, и это тип, а не комментарий:
положить туда Passive-очередь нельзя, а вызвать `retrieve_next` на Passive-очереди нечем. Компилятор
отвергает именно ту программу, которую написал C-драйвер.

Побочно: очередь по умолчанию создаётся как `Queue<Passive>` — и на ней `retrieve_next` недоступен, что
верно, потому что её колбэк зовёт `VhfCreate`/`VhfStart`, а те только PASSIVE.

### Дефект 3 — версия фреймворка, закреплённая за тем, что объявляет INF

В C версия приходит в разбор заголовков из `-DKMDF_VERSION_MAJOR/MINOR` в `driver/build.sh`, а в INF — из
отдельной подстановки `$KMDFVERSION$`. Два места, которые могут разойтись; драйвер, собранный против KMDF
новее объявленного, не стартует на той ОС, которую называет INF.

**В Rust версия записана один раз** — `src/kmdf_version.rs`, и её читают три потребителя:

| Потребитель | Как читает | Что делает |
|---|---|---|
| `build.rs` | `include!` | defines для bindgen, каталог `x64/1.33` для линковки, **и имя символа таблицы** `WdfFunctions_01033` |
| `driver/build-rust-driver.sh` | `sed` | подстановка в INF; затем **проверяет прочитанное значение**, а не наличие числа |
| `src/lib.rs` | `crate::ffi::kmdf` | экспортируемый `WdfMinimumVersionRequired = KMDF_MINOR` |

Имя символа таблицы собирается из константы (`format!("WdfFunctions_{:02}0{:02}", major, minor)`), а его
присутствие проверяет линкер: сборка, разрешившаяся против другой версии, — это неразрешённый внешний
символ, а не тихо более новый драйвер. То же и с каталогом библиотек: `x64/<major>.<minor>` берётся из той
же константы.

### Дефект 4 — `PAGED_CODE()` вне pageable-секции

`PAGED_CODE()` — утверждение о том, **где лежит функция**, и в C его приходится сопрягать с размещением
руками (`#pragma alloc_text`).

**В Rust это одно действие** — макрос `paged_fn!` (`src/irql.rs`) в одном разворачивании ставит
`#[link_section = "PAGE"]` и выдаёт функции `PagedGuard`. `PagedGuard` не конструируется больше нигде
(`unsafe fn new` с `#[doc(hidden)]`, единственный вызов — в разворачивании макроса), поэтому утверждение
не может оказаться в функции, которая не в PAGE. Плюс `#[inline(never)]`, иначе инлайн унёс бы копию в
секцию вызывающего и размещение ничего не значило бы.

Проверяется по факту: в собранном `.sys` секции `PAGE` (0x138b байт) и `INIT` (0x8a) присутствуют как
настоящие секции, а `DriverEntry` лежит в `INIT` — как и в C.

## 4. Как сверялся контракт с C#

Контракт — `driver/AcerHelperLampArray/public.h` и `lamparray.h` с одной стороны и
`Infrastructure/Vendors/Generic/LampArrayTransport.Windows.cs` с другой. Rust-сторона — `src/contract.rs`.

| Что | Чем закреплено | Результат |
|---|---|---|
| Дескриптор HID-отчётов (292 байта) | сравнение байт за байтом с `lamparray.h` | **совпадает побайтово**, 292 из 292 |
| Размеры `AHLA_LAMP`/`LAYOUT`/`COLOR`/`FRAME` | `const _: () = assert!(…)` — перенос `C_ASSERT` | 28, 1820, 4, 268 |
| Смещения полей, которые C# пишет по индексам | `offset_of!` в тех же assert-ах | `Lamps`=28, `Colors`=12, `RgbLevels`=20… | 
| Три `CTL_CODE` | assert против литералов, которые считает `LampArrayTransport.Ctl` | `0xB007A000`, `0xB0076004`, `0xB007A008` |
| Размеры шести HID-отчётов | assert против `C_ASSERT` из `lamparray.h` | 23, 3, 29, 51, 10, 2 |
| Имя symbolic link и hardware id | assert: link = `\DosDevices\` + hardware id | совпадает |
| INF | `diff` с INF из `dist/driver` | **совпадает побайтово** |

Проверка размеров структур опирается ещё и на то, что `core::ffi::c_long` на этой цели 32-битный: в
`contract.rs` стоит `assert!(size_of::<c_long>() == 4)`. Без этого сборка под Linux-цель дала бы 64-битные
`ULONG` и промолчала бы — именно так и выглядел один из отладочных прогонов разведки.

### Исправленный устаревший комментарий

`AHLA_FRAME.Sequence` в `public.h` был описан как «lets the app detect dropped frames». Это неверно:
`LampArrayTransport.DecodeFrame` кладёт значение в `LampFrame.Sequence`, и **дальше его не читает никто** —
приложение рисует самый новый кадр, а драйвер перезаписывает невостребованный, поэтому пропущенный кадр
невидим по построению. Комментарий в `public.h` исправлен; в Rust-зеркале (`contract.rs`) та же правка
записана как факт.

## 5. Как собрать

Через образ (стадия `driver-rust` — то же, чем `driver-image` является для C):

```bash
docker buildx build --target artefacts --output type=local,dest=dist .
# -> dist/driver-rust/AcerHelperLampArray.sys|.pdb|.inf
```

Смонтировав исходники, как описано для C-драйвера:

```bash
docker build --target driver-rust-image -t acerhelper-wdk-rust .
docker run --rm -v "$PWD/driver/AcerHelperLampArrayRust:/src" \
                -v "$PWD/driver/AcerHelperLampArray/AcerHelperLampArray.inf:/inf/AcerHelperLampArray.inf" \
                acerhelper-wdk-rust
```

Скрипт один — `driver/build-rust-driver.sh`; он читает версию KMDF из `src/kmdf_version.rs` и печатает
тулчейн в лог, как это делает `build.sh`.

Чего в образе нет и почему: **Wine, MSVC, `cargo-wdk`**. Первые два не нужны (§1), третий не собирается
(§1).

## 6. Датированные поправки

- **2026-09-19.** Файл создан. Драйвер написан, собирается и пакуется; **не загружался**.
  `windows-drivers-rs` признан недостижимым с Linux-хоста по `compile_error!` в `wdk-build` — это
  измеренный отказ, а не предположение. Wine в цепочке не оказался нужен; маршрут QEMU не открывался.
- **2026-09-19.** Найдено при первой контейнерной сборке: INF доезжает до контейнера с **CRLF** (контекст
  сборки на Windows — рабочее дерево, а `.gitattributes` нормализует при коммите, а не при checkout). Это
  свойство не Rust-сборки, а обеих: C-пакет получает тот же файл с теми же окончаниями. Проверка в
  `build-rust-driver.sh` поэтому снимает `\r` перед сравнением — иначе она отвергала бы корректную
  подстановку.
