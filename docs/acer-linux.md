# Acer на Linux: паритет с Windows, mainline-интерфейсы и пробелы

Измерено на Acer Nitro AN18-61 (AMD Radeon 880M + RTX 5070 Ti Laptop), ядро
`7.2.4-ogc3.1.fc44.x86_64`, 2026-09-20. Дата в заголовке не украшение: почти каждое число ниже
зависит от сборки ядра и от DMI этой машины, и правило «перевыводи, а не копируй» относится ко
всему документу.

Документ отвечает на три вопроса: **что на Linux приходит из mainline**, **чем имена и числа
Linux отличаются от Windows** и **что недостижимо вообще**. Пробелы записаны с описанием того,
что именно проверено, — иначе следующий читатель пойдёт тем же путём.

## Что где живёт

Linux-бэкенд Acer стоит на **двух** транспортах, и оба module-free:

1. **HID через hidraw** — тот же кодек, что на Windows, только транспорт другой:
   ENE-контроллер подсветки и EC-канал конверта мощности (`docs/power-an18-61.md`,
   `docs/lighting-an18-61.md`). Ни один модуль не нужен; нужен только `uaccess`-ACL
   (`packaging/60-acer-helper.rules`), потому что оба висят на HID-over-I2C.
2. **mainline `acer-wmi`**, открытый параметрами модуля, которые ставит установщик: набор
   профилей вендорского обработчика `platform-profile`, обороты, температуры и — после
   `force_caps` — запись в вентиляторы. Внутри ядро само ходит тем же gaming-WMI, которым
   Windows-половина ходит напрямую.

**Третьего яруса нет.** Linuwu-Sense удалён целиком решением владельца (2026-09-20): Linux-бэкенд
module-free **по построению**, поэтому машина со штатным `acer-wmi` и без единого out-of-tree
модуля получает всё, что бэкенд умеет. Возврат яруса — это решение, которое придётся
аргументировать: его сторожит `tests/AcerHelper.Tests/AcerLinuxWiringTests.cs`.

## Карта паритета

| Фича | Windows (эталон) | Linux |
|---|---|---|
| Профили: набор и переключение | WMI `SetGamingMiscSetting` (байт 0x0B, набор из маски 0x0A) | class-node `platform-profile-1/profile` того же драйвера `acer-wmi`; те же пять имён |
| Идентификаторы профилей | байт EC **десятичной строкой** (`"6" "0" "1" "4" "5"`) | те же — id общие с пресетами, лотком и `settings.json` |
| Тип/акцент/вспышка профиля | `AcerProfiles` | `AcerProfiles` (un-suffixed, общий файл) |
| Гейт по питанию | нет | нет: декоратор удалён 2026-09-20, все пять профилей пишутся на батарее |
| Конверт мощности | EC HID, отчёт `0xA0`, mode byte | тот же кодек через hidraw; **путь записи на Linux end-to-end не прогонялся** |
| Обороты | `GetGamingSysInfo` 0x02/0x06, подписи CPU/GPU | hwmon `fan1_input`/`fan2_input` чипа `acer`, те же подписи |
| Запись в вентиляторы | `SetGamingFanSpeed` (id 0x01/0x04) + `SetGamingFanBehavior` | hwmon `pwmN`/`pwmN_enable`; ядро внутри зовёт те же gaming-WMI методы |
| Режим вентиляторов | `FanMode` = 1/2/3 | `pwm_enable` = 2/0/1 — см. отдельную таблицу ниже |
| Температуры | `GetGamingSysInfo` 0x01/0x0A | `temp1_input`/`temp2_input` того же чипа; фолбэк на generic-источник — когда EC отвечает нулём **или** канала нет (см. «Почему GPU-канал читается не как на Windows») |
| Turbo-клавиша | приложение (`TogglePerformance`) | **замерено 2026-09-21**: вендорский HID-отчёт `04 85 ff` на hidraw Acer HID-устройства (VID 0x1025/PID 0x174B), декодируется самим приложением (`AcerHotkeyReports` — та же сигнатура, что на Windows) в то же действие `TogglePerformance`. Ядро эту клавишу НЕ потребляет: `cycle_gaming_thermal_profile=Y` существует и включён, но клавиша не является WMI-событием — при нажатиях нет ни evdev-кода на AT-клавиатуре, ни строки `acer_wmi` в журнале, ни движения счётчиков ACPI. Прежняя запись «клавишу потребляет ядро» опровергнута замером — см. «Открытое: что здесь НЕ измерено» |
| Nitro-клавиша | RawInput | evdev `KEY_PRESENTATION` (udev `uaccess` на AT-клавиатуру) |
| Ось питания CPU | overlay `powrprof.dll` | отдельной оси нет **по устройству**, а не как пробел: её роль играет сам platform profile |
| Подсветка RGB | ENE HID (HidSharp) | тот же кодек через hidraw |
| LampArray | Windows Dynamic Lighting | **вне охвата** (решение владельца) |
| LCD overdrive, лимитер/калибровка батареи, таймаут подсветки, USB-зарядка | WMI `AcerGamingFunction` / `BatteryControl` / `APGeAction` | **пробел** — интерфейса в mainline нет ни в каком виде; module-free маршрут закрыт разведкой EC HID |
| Чтение яркости подсветки | `GetGamingKBBacklight` (gaming WMI) | **пробел** — ENE write-only, геттера нет ни у ядра, ни у HID-дескриптора |
| Фильтр синего света | `SetDeviceGammaRamp` (gdi32), шкала синего 1.00/0.85/0.70/0.60/0.50 | Цепочка: гамма-рампа X11 (только не-Wayland) → настройки night light KWin (`kwriteconfig6` + `reconfigure`) → настройки GNOME (`gsettings`) → `wlr-gamma-control` (слот; протокола у KWin нет); температуры 6500/4500/4000/3500/3000 K. Звено конфигурации тихое, обратимое (маркеры) и не трогает включённый у пользователя night light; если не подошло ни одно звено — порта нет и строка прячется |

## Параметры модуля

Ставятся одним файлом `packaging/acer-helper-modprobe.conf` → `/etc/modprobe.d/acer-helper.conf`,
одной строкой (нескольких строк `options acer_wmi …` быть не должно: их слияние в kmod
зависит от версии, и вторая строка молча разоружила бы первую):

```
options acer_wmi predator_v4=1 force_caps=7200
```

**Происхождение.** Ядро `7.2.4-ogc3.1.fc44.x86_64`, DMI «Acer Nitro AN18-61», upstream-коммит
`f9124f2a` («platform/x86: acer-wmi: Add predator_v4 module parameter») — параметр заведён ровно
для моделей вне DMI-таблицы драйвера; модели из таблицы получают тот же флаг квирком
(`quirk_acer_nitro_an515_58 = { .predator_v4 = 1, .pwm = 1 }`). Эта машина в таблицу не входит,
поэтому признаки есть в модуле, но выключены.

**`predator_v4=1`** открывает: вендорский набор профилей на `platform-profile-1` (пять имён) и
телеметрию чипа `acer` (`fan1_input`, `fan2_input`, `temp1..temp3`). Без него обработчик отдаёт
три дефолтных имени, а у чипа нет ни вентиляторных, ни температурных каналов.

**`force_caps=7200` (0x1C20)** добавляет **запись** в вентиляторы: появляются `pwm1`,
`pwm1_enable`, `pwm2`, `pwm2_enable`. Значение — **замена маски целиком, а не OR**
(`interface->capability = force_caps`), поэтому выводится суммой всех бит, которые должны выжить,
и состоит из четырёх:

```
ACER_CAP_SET_FUNCTION_MODE          0x0020   (на машине есть ACER_WMID3)
| ACER_CAP_PLATFORM_PROFILE         0x0400
| ACER_CAP_HWMON                    0x0800
| ACER_CAP_PWM                      0x1000   (тот бит, ради которого файл и существует: DMI-записи
                                              нет, поэтому квирк его не выдаёт)
=                                   0x1C20 = 7200
```

Сумма — это **кандидат**, а не ответ: она выведена из модуля и затем **подтверждена на машине**
диффом инвентаря (см. ниже, «`force_caps`: процедура и измеренный результат»).

### 7206 (0x1C26) — ложный ответ, и это стоит прочитать целиком

Первая версия этого файла несла **7206**, и он выглядит как более безопасное число: он
дополнительно выставляет биты дескриптора интерфейса `WIRELESS | BLUETOOTH` (`0x6`,
`ACER_CAP_WIRELESS | ACER_CAP_BLUETOOTH`, прочитанные из `wmid_v2_interface.capability`), «сохраняя»
то, что драйвер вычислил бы сам. **Он не сохраняет ничего.** Измерено на этой машине, один и тот
же установщик, отличается только число:

- **`force_caps=7206`** — acer-wmi регистрирует **ДВА ФАНТОМНЫХ** rfkill-устройства под
  `/sys/devices/platform/acer-wmi/rfkill/`: `acer-wireless` (wlan) и `acer-bluetooth` (bluetooth),
  и каждая такая загрузка модуля пишет три отказа:
  `acer_wmi: Get 0x1 Device Status failed: 0xe2 - 0x0`,
  `Get 0x800 Device Status failed: 0xe2`, `Get Current Device Status failed: 0xe2`. В том журнале
  эти три строки встречаются ровно один раз за всю загрузку — на единственной загрузке, что шла
  с 7206.
- **`force_caps=7200`** — rfkill это только `hci0`/`phy0` (устройства самих драйверов wifi и
  Bluetooth), ни одной строки отказа, `pwm1`/`pwm1_enable`/`pwm2`/`pwm2_enable` на месте, пять
  имён на `platform-profile-1`, оба обработчика целы.
- **Без `force_caps` вовсе** (только `predator_v4=1`) тех rfkill-устройств тоже нет и строка отказа
  не пишется.

Значит зарегистрированная способность этой машины **не содержит** `WIRELESS | BLUETOOTH`: биты
дескриптора не доживают до зарегистрированного устройства, и 0x1C26 их не удерживает — он
**создаёт** два устройства, чей собственный опрос статуса падает. Биты `TURBO_OC` / `TURBO_LED` /
`TURBO_FAN` не добавляются по той же причине, по которой их не добавляет upstream: они открывают
EC-пути записи на моделях, которых никто не вайтлистил.

**Общий урок, ради которого эта история здесь.** Читать OR-ы драйвера **недостаточно**: бит
способности, дошедший до маски, не обязан дожить до устройства, которое будет зарегистрировано.
Значение маски подтверждается **диффом инвентаря до/после** — имена rfkill, backlight, leds, оба
обработчика `platform-profile` с их наборами, каналы hwmon, WMI-хоткеи и журнал, — а не
арифметикой. Именно поэтому 7206 и дожил до первого коммита: он был выведен, а не измерен.

**Правило перевывода.** Обновление ядра или другая модель обесценивают оба значения: `predator_v4`
— это whitelist-override, а `force_caps` — собственная маска машины, и эпизод с 7206 показывает,
что её нельзя вывести даже из исходников драйвера. Поэтому порядок такой: `modinfo -p acer_wmi` и
таблица `acer_quirks` дают **кандидата** (плюс `#define`-ы capability для состава), а кандидат
подтверждается диффом инвентаря на самой машине — rfkill, backlight, leds, platform-profile,
hwmon, журнал — и только потом попадает в строку. Файл
`packaging/acer-helper-modprobe.conf` — источник истины: он несёт и вывод, и доказательство
отказа, и его сторожат тесты (`HardwareAccessWiringTests`): строка обязана нести
`force_caps=7200`, значение `force_caps=7206` запрещено как отсутствующее, а слова-улики —
`acer-wireless`, `acer-bluetooth`, `phantom`, `0xe2`, `Get Current Device Status failed`,
`wmid_v2_interface.capability`, `ACER_CAP_WIRELESS`, `ACER_CAP_BLUETOOTH`, `INVENTORY DIFF` —
закреплены, чтобы никто не «починил» число обратно из старого вывода.

## Профили: имя в `platform_profile` ↔ байт EC

Обе половины — про одну машину, но говорят на разных языках. Перевод написан **один раз**, в
`Infrastructure/Vendors/Acer/AcerProfiles.cs` (колонка `Choice`, двери — `ToChoiceName` /
`FromChoiceName`); ни один вызывающий не имеет права сопоставлять эти слова сам.

| Байт EC | `platform_profile` | Имя в приложении | `ProfileKind` |
|---|---|---|---|
| `0x06` | `low-power` | Eco | Eco |
| `0x00` | `quiet` | Quiet | Quiet |
| `0x01` | `balanced` | Balanced | Balanced |
| `0x04` | `balanced-performance` | Performance | Performance |
| `0x05` | **`performance`** | **Turbo** | Turbo |

> **ЛОВУШКА. `performance` в ядре — это Acer TURBO (0x05, 108 Вт), а не Performance (0x04, 93 Вт).**
> Очевидный поиск по имени неверен **в обе стороны**: прочитать `performance` как Performance
> значит показать не тот режим и отправить в EC не тот конверт, а записать Performance, отправив
> токен `performance`, значит попросить у ядра Turbo. Это самое опасное столкновение слов в
> проекте, и оно записано ещё и в словаре (`docs/context-map.md` §2).

**Порядок** профилей — Windows-овский (Eco, Quiet, Balanced, Performance, Turbo), и он же порядок
перебора хоткеем. На Windows клавиша — приложение, поэтому порядок его; на Linux клавишу держит
ядро и перебирает **свой** список, так что порядок перебора там может отличаться. Приложение от
этого не ломается: оно в любом случае читает текущий профиль из порта и следует за ним.

**id профилей — байт EC десятичной строкой** и на Linux: `Id` идёт в пресеты режимов, в память по
источнику питания, в лоток и в `settings.json`, поэтому `settings.json`, записанный на Windows,
читается на Linux и наоборот. Токен sysfs в id не попадает никогда — иначе одна и та же машина
завела бы вторую, несовместимую идентичность режима.

**Запись идёт только в вендорский узел.** `SysfsPowerProfiles("acer-wmi")` рассматривает
исключительно class-node, чей разрешённый путь содержит `acer-wmi`, и **никогда** — legacy-алиас
`/sys/firmware/acpi/platform_profile`. Причины две, обе измеренные: запись в алиас веером уходит
**всем** зарегистрированным обработчикам (на этой машине это ещё и AMD-обработчик
`platform-profile-0` с тремя своими именами, то есть один клик двигал бы два независимых
источника профиля), а читается алиас как `custom`, как только записал вендорский обработчик, —
назвать режим машины он не может. Именно поэтому `custom` (и чужой `cool`) для
`FromChoiceName` — `null`, и `AcerMappedProfiles.Current()` на них тоже возвращает `null`:
режим, который приложение не может назвать, не должен молча применять чужие пресеты.

**Проверено на машине (2026-09-20).** Все пять имён были записаны через вендорский узел и
прочитаны обратно, и всё это время `platform-profile-0` — обработчик AMD — оставался
`balanced`. Это и есть доказательство, что источник приложения пишет **вендорский** узел, а не
алиас-веер: клик по профилю не двигает второй, независимый источник профиля на той же машине.
Второе, что из этого следует, — почему алиас нельзя даже читать: после записи он отдаёт `custom`
для всего, кроме того значения, которое держит сам AMD, то есть назвать режим машины по нему
невозможно ни в каком случае.

**Boot sync.** Профиль переживает перезагрузку, а EC usage mode за ним — нет, поэтому при
старте бэкенд читает **тот порт, которым реально пользуется**, и толкает в EC режим его
`Kind`. Читать здесь сырой sysfs нельзя: до правки это отправляло режим 1 (93 Вт) машине,
которую прошивка оставила в Turbo (нужен режим 0, 108 Вт). Запись по-прежнему **только в EC** —
без смены профиля, без вспышки подсветки, как на Windows.

## Вентиляторы

**Каналы.** Таблица общая у порта вентиляторов и у датчиков
(`Infrastructure/Vendors/Acer/AcerFanPort.cs`), потому что один канал — это один физический
вентилятор на обеих ОС:

| Канал hwmon | Подпись UI | WMI id вентилятора | Id датчика оборотов | Id датчика температур |
|---|---|---|---|---|
| `fan1` / `pwm1` | `CPU` | `0x01` | `0x02` | `0x01` |
| `fan2` / `pwm2` | `GPU` | `0x04` | `0x06` | `0x0A` |

Три последние колонки — **Windows-овские id** (аргумент `SetGamingFanSpeed`, `GetGamingSysInfo`
для оборотов и для температур), и они приведены здесь потому, что таблица обязана быть
проверяемой: числа не выдуманы локально, это собственные таблицы ядра, где канал — индекс:

- `fan_channel_to_fan_id = {1,4}` — канал → id вентилятора (то, что Windows шлёт как `0x01`/`0x04`);
- `fan_channel_to_sensor_id = {2,6}` — канал → id датчика **оборотов** (`0x02`/`0x06`);
- `predator_v4_sensor_id = {1,10}` — **температуры**, то есть ровно `0x01`/`0x0A`;
- `{1,8}` — id **поведения**: `0x08` у GPU — то самое, что Windows-половина обходит комментарием
  «GPU uses different ids for behaviour 0x08 vs speed 0x04».

Подписи `CPU`/`GPU` — кросс-ОС контракт отображения, а не местная привычка.

**Имена узлов обнаруживаются, а не хардкодятся.** На этой сборке запись дежурства живёт в
`pwmN` (не в `pwmN_input`, как в других сборках), поэтому каталог листается и берётся первое из
`pwmN_input` / `pwmN`, что существует **и** доступно на запись.

**`pwmN_enable` — по-канальный.** Драйвер резолвит канал в собственный бит вентилятора перед
вызовом EC, поэтому одна запись в `pwm1_enable` оставила бы GPU-вентилятор в прежнем поведении.
`Max` и `Custom` пишут **оба** регистра поведения; отказ на одном не отменяет попытку на втором
(это два собственных регистра двух вентиляторов), а сообщается первая ошибка.

**Режим приложения → значение узла** (`AcerFanEnable.TryFor`, закреплено тестом, названным по
ловушке):

| `FanMode` (приложение) | `pwmN_enable` | Поведение в ядре | Байт поведения | Windows `FanMode` |
|---|---|---|---|---|
| Auto = 1 | `2` (AUTO) | 1 | 1 | Auto = 1 |
| Max = 2 | `0` (TURBO) | 2 | 2 | Max = 2 |
| Custom = 3 | `1` (CUSTOM) | 3 | 3 | Custom = 3 |

**Тождественный маппинг здесь — ошибка**: у приложения Auto = 1, а единица в узле — это CUSTOM,
так что «очевидная» подстановка `((byte)mode).ToString()` ставила бы вентиляторы в TURBO при
каждом запросе Auto — навсегда, молча, на самой громкой настройке машины. Измеренная таблица
ядра `pwm_enable → behaviour` = `{2,3,1}` независимо подтверждает маппинг шага: байты поведения
ядра **совпадают** с байтами `FanMode` Windows, поэтому Auto→2→behaviour 1 — это Windows-овский
Auto (поведение 1), а не что-то похожее.

**Порядок записей** повторяет Windows: `Max` и `Auto` пишут только поведение (дежурство
остаётся тем, что оставила прошивка или наша последняя custom-запись), `Custom` — поведение,
затем CPU, затем GPU, с остановкой на неудаче CPU (половина одной кривой хуже, чем ничего).
Дежурство — 0..255 на 0..100 % (тот же масштаб, что у generic `pwmN`); Windows пишет проценты в
WMI напрямую, поэтому масштаб существует только на этой стороне.

**Проверено на машине, через САМ код приложения (2026-09-20).** При остановленном приложении в
`settings.json` подложена запись `FanPresets` **под ключом `"5"`** — байт EC Turbo десятичной
строкой, то есть ровно то, что пишет Windows, — со значениями `Mode: 3` (Custom), `Cpu: 45`,
`Gpu: 35`. После запуска профиль переключён на `performance` через вендорский узел, и
**приложение само** записало `pwm1_enable=1`, `pwm1=112`, `pwm2_enable=1`, `pwm2=86`, а
вентиляторы поднялись с 910/885 до 3636/3327 об/мин. После ядрового пересчёта 0..255 эти
дежурства — 44 % и 34 %, то есть подложенные 45/35: пресет, ключованный Windows-совместимым id,
был найден и применён **портом приложения**, а не записью в sysfs руками. Это закрывает сразу две
приёмки — кросс-ОС контракт `settings.json` и UI-путь вентиляторов.

Наблюдение, которое здесь — **поведение, а не дефект**: возврат на `balanced` оставил вентиляторы
в custom-режиме. Это документированная политика пустой оси для кулеров
(`EmptyAxisPolicy.LeaveUntouched`): режим, у которого нет сохранённого пресета, вентиляторы не
трогает. Реальные настройки пользователя после прогона восстановлены (`FanPresets` снова пуст),
приложение перезапущено.

**`Dispose` не пишет ничего** — и в этом порт расходится с `HwmonFanControl`, который на выходе
возвращает вентилятор прошивке. Разница в том, что стоит за узлом: generic PWM-канал не защёлка
(его значение живёт, только пока кто-то пишет), а этот путь защёлкивает регистр поведения EC, и
вентиляторы продолжают делать то, что попросил пользователь, после выхода из приложения. Windows
оставляет это ровно так же. Альтернатива (восстанавливать AUTO на выходе) записана как решение
владельца, а не забыта: она обоснована, но она **не** поведение Windows и молча отменяла бы
защёлку, которую поставил пользователь.

## Датчики

Вентиляторы читаются из чипа `acer` **безусловно, оба**, с подписями `CPU`/`GPU`. Это и есть
причина существования переопределения `Sensors`: generic-путь выбрасывает канал, который читает
0 об/мин **и не имеет подписи** (а чип `acer` не публикует `fanN_label` вовсе), после чего
индексный фолбэк UI переназывает оставшийся вентилятор первым. Это не косметика: 0 об/мин
GPU-вентилятора показывались бы как обороты CPU, и машина читалась бы как один вентилятор,
который крутится, когда второй стоит. Холостые вентиляторы честно дают 0 (измерено: на AN18-61
они останавливаются), и 0 — это показание, которое UI умеет показать.

Температуры — `temp1_input`/`temp2_input` того же чипа: это сенсоры `{1,10}`, то есть ровно те
два, что Windows читает через sysinfo `0x01`/`0x0A`. **Правило чтения: показание EC выигрывает,
когда оно настоящее; 0 — нет.** Если EC отвечает нулём (или канала нет вовсе), берётся фолбэк на
generic-источник (`Hwmon.CpuTempPath`/`GpuTempPath`); если и там пусто — `-1`, и строка в UI
прячется. То же правило применяется к CPU-каналу, для симметрии. Почему ноль здесь не показание
— отдельный раздел ниже («Почему GPU-канал читается не как на Windows»). Чип отдаёт ещё и
`temp3_input`; он растёт под нагрузкой (37 → 42 °C) и в номенклатуре EC зовётся «external temp 2»,
но соответствия в Windows-половине у него нет: там читаются только `0x01`/`0x0A`, то есть
`temp1`/`temp2`. Поэтому третий сенсор не показывается — а не потому, что его забыли.

**Проверено на машине (2026-09-20) — закрывающий замер для этого переопределения.**
`temp1_input` чипа `acer` (CPU-сенсор EC, `0x01`) сверен с `Tctl` у `k10temp` на той же машине: в
простое 36.0 против 36.2 °C, под нагрузкой 70 с — 65.0/65.9, 69.0/69.1, 70.0/70.1, 70.0/70.5,
70.0/70.9. Расхождение в пределах **1 °C по всему диапазону**, то есть `temp1` действительно
температура CPU и выбор переопределения верен. `temp2_input` всё это время читал 0 — и это
наблюдение САМОГО EC-сенсора (дискретной видеокарты, которую он читает, на машине нет), а не то,
что приложение в итоге показывает: см. следующий раздел. `temp3` рос вместе с нагрузкой — см.
абзац выше.

**Почему GPU-канал читается не как на Windows (2026-09-20, по наблюдению владельца).** Monitor
показывал «0 °C» для GPU. Причина: `temp2_input` чипа `acer` — это GPU-сенсор EC (id `0x0A`), и
на этой машине он честно отвечает нулём, потому что дискретной видеокарты, которую он читает,
здесь нет вовсе (соседние каналы того же чипа несут настоящие значения: `temp1` CPU ≈ 40,
`temp3` external ≈ 39).

Прежнее правило — пропускать 0 наружу, «как на Windows» — оказалось **неверным показанием в UI**,
а не честным паритетом, и ломается оно о собственный контракт приложения:
`Domain/Models.cs` объявляет, что недоступность — это **отрицательная** температура
(«Temperatures of -1 mean unavailable/unsupported»), а UI рисует её как «—» и прячет строку
(`UI/ViewModels/MonitorViewModel.cs`: `GpuTempC < 0 ? "—" : $"{…} °C"`, `ShowGpu = GpuTempC >= 0`).
Ноль под этот контракт не попадает, поэтому читается как «0 °C» — то есть как температура,
которой нет.

**Правило теперь:** показание EC выигрывает, когда оно настоящее; 0 (или отсутствующий канал) от
EC уходит в фолбэк на generic-источник GPU — на этой машине это edge **iGPU amdgpu**, единственная
GPU, которую Linux здесь видит, и ровно то, что приложение показывало до этой работы; если не
читается нигде — `-1`, и строка прячется. Это **осознанное исключение из паритета с Windows**, и
граница у него одна: паритет держится везде, где EC действительно может прочитать дискретную GPU,
а фолбэк срабатывает **только** когда у EC нет своего показания. Windows в той же ситуации
показывает 0, и это правильно там: dGPU есть, и 0 означает «спит». Здесь 0 означает «читать
нечего», и показывать его как температуру нельзя.

Чип может зарегистрироваться **после** старта приложения (перезагрузка модуля установщиком, гонка
с автозапуском), поэтому промах перепроверяется на каждом чтении, а попадание запоминается.

## Фильтр синего света: цепочка адаптеров, и почему на Wayland X11-гамма молчит

**Симптом владельца:** «фильтр синего цвета не работает вовсе» — сессия KWin/Wayland, KWin 6.7.5.

### Корень: проба X11-рампы была ложной

`Infrastructure/Vendors/Generic/DisplayTint.Linux.cs` опускает гамма-рампу X11
(`xrandr --output N --gamma 1:1:B`). На Wayland композитор владеет цветовым конвейером, и этот API не
влияет ни на что.

Ключевой замер: **`xrandr` на этой сессии работает**. `DISPLAY=:0` выставлен, потому что Plasma поднимает
XWayland, и `xrandr --query` отвечает `DP-1 connected primary 3440x1440`. Прежняя проба спрашивала только
«ответил ли xrandr» — и отвечала «да», поэтому порт создавался, `Available` был истинен, раздел в UI
показывался и молча ничего не делал. Худший из возможных отказов.

Отсюда правило, закреплённое тестом: X11-рампа годится, только если сессия **не** Wayland
(`TintProbe.X11GammaWorks(xrandrSaysYes, sessionIsWayland)`). На X11 она остаётся правым рычагом — тихим,
постоянным и не трогающим конфигурацию; на Wayland она не участвует в цепочке вообще.

### Форма: цепочка адаптеров

Решение владельца — **кроссплатформенная цепочка** за существующим портом `IDisplayTint`, порядок такой
(каждое звено выпадает, если его среды нет), `Infrastructure/Vendors/Generic/DisplayTintChain.cs`:

| # | Звено | Где живёт | Что решает доступность |
|---|---|---|---|
| 1 | Гамма-рампа X11 | `DisplayTint.Linux.cs` / `Windows` | ответил xrandr **и** сессия не Wayland |
| 2 | Night light KWin **через конфиг** | `KwinTint.cs` + `KwinTint.Linux.cs` | сессионная шина, интерфейс `org.kde.KWin.NightLight`, `available=true` |
| 3 | Night light GNOME **через конфиг** | `GnomeTint.cs` + `GnomeTint.Linux.cs` | `gsettings` **и** установленная схема цвета |
| 4 | `wlr-gamma-control` | слот в `TintChain.Linux.cs` | протокол должен быть в реестре Wayland — см. ниже |
| 5 | — | — | порт `null`, строка в UI прячется. **Никогда** не выдаётся звено, не способное изменить экран |

Звено 4 оставлено слотом осознанно: постоянная рампа через `wlr-gamma-control` была бы идеальным
механизмом (тихая, без конфигурации, без перевзвода), но это протокол wlroots, и KWin его не предлагает —
**измерено**: `wayland-info` на этой сессии показывает 66 глобалов, и ни один не `zwlr_gamma_control_v1`
(родственные имена `wp_color_manager_v1`/`frog_color_management_factory_v1` — про управление цветом
поверхностей, не про гамма-рампу). Вдобавок приложение не линкует Wayland-клиент, а протокол достижим
только сканированием реестра, поэтому слот всегда отвечает отказом — с комментарием, где и почему.

### Звено KWin: конфигурация, а не D-Bus-preview

Пишется группа `NightColor` файла `kwinrc` тем же способом, каким это делает диалог самой KDE:

```
kwriteconfig6 --notify --file kwinrc --group NightColor --key NightTemperature --type int 3500
kwriteconfig6 --notify --file kwinrc --group NightColor --key Mode             --type int 0
kwriteconfig6 --notify --file kwinrc --group NightColor --key Active           --type bool true
→ enabled=true, mode=0 (Constant), running=true, currentTemperature=3500
```

Имена — из исходников: `nightlightsettings.kcfg` даёт группу `NightColor` и ключи
`Active`/`Mode`/`NightTemperature`; `Mode` — перечисление всего из двух вариантов, `Constant` (0) и
`DarkLight` (1), по умолчанию `DarkLight` (отсюда наблюдённый `mode=1` на шине при чистом `kwinrc`).

**ЗАМЕР, КОТОРЫЙ СТОИЛ ВЛАДЕЛЬЦУ СЛОМАННОЙ ФИЧИ: без `--notify` запись не работает.**
Первая версия этого звена писала файл «молча», и владелец увидел ровно то, что видел:
«применяется с секундным лагом, но цвет не теплеет». `kwriteconfig6` без `--notify` пишет файл и никому
не сообщает, а KWin **не перечитывает конфигурацию сам** — он продолжает пользоваться копией в памяти.
Проверено перебором: (а) `Mode` именем варианта `Constant`, (б) `Mode` числом `0`, (в) `reconfigure` после
каждой записи, (г) и то и другое вместе — KWin всё это время оставался `enabled=false, mode=1,
currentTemperature=6500`. С `--notify` те же записи срабатывают мгновенно. Внутри это
`KConfig::WriteConfigFlags::Notify` (`kwriteconfig.cpp`), то есть тот самый сигнал, который слушает
`KConfigWatcher` в KWin. **`reconfigure` поэтому не используется вовсе** — он не помогает.

**`Mode` пишется ЧИСЛОМ (0 = Constant), а не именем варианта.** Чтение исходников сначала дало
противоположный вывод, и это стоило отдельного разбора. Механизм: `nightlightsettings.kcfgc` задаёт
`UseEnumTypes=true`, поэтому компилятор выдаёт каждому варианту `value` из C++ перечислителя и передаёт
умолчание как `int(...)`; `KCoreConfigSkeleton::ItemEnum::writeConfig` пишет `valueForChoice(...)`, который
отдаёт это `value` («0»), а имя — только если `value` пуст; `readConfig` сравнивает значение из конфига с
теми же `value`, поэтому запись `Mode=Constant` **не совпадает ни с чем** и читатель проваливается в
`readEntry(int)`, который слово тоже не разбирает и возвращает **умолчание** (`DarkLight`). Симптом —
полная тишина: файл выглядит правильно, KWin возвращается к своему расписанию.

**Проверка требует `running` и `currentTemperature`, а не `targetTemperature`.** Цели мало: цель — это
намерение, и она может быть выставлена, когда ничего не применяется; на этом первая версия и отчиталась об
успехе на нетронутом экране. Теперь применение подтверждается четырьмя фактами сразу: `enabled`,
`running`, `mode=0` и `currentTemperature`, равная запрошенной. Отсюда же следствие: смена уровня при уже
включённом фильтре подтверждается только когда KWin дойдёт до неё своим `quick-adjust` (50 K за шаг,
`QUICK_ADJUST_DURATION = 2000` мс), поэтому такой клик может занять до ~2 с — ожидание ограничено сверху и
живёт в Linux-половине.

**`Mode=Constant` снимает зависимость от расписания KWin, и это существенно.** При `Constant` флаг
`daylight` уходит в false, и температура применяется независимо от суточного расписания — а расписание на
этой машине считает днём даже 23:00, поэтому в режиме `DarkLight` оно красить отказывается. Ручному фильтру
нужен именно `Constant`.

**Снятие фильтра тоже требует `--notify`, и это худший отказ фичи.** Замерено на живой машине: после
записи `--notify` владельческий `kwinrc` был возвращён к исходному состоянию (группы `[NightColor]` нет
вовсе) и вызван `reconfigure` — но KWin **оставил тинт применённым** (`running=true`,
`currentTemperature=4000`), потому что о смене файла не узнал. Погасила его только явная запись
`kwriteconfig6 --notify … Active=false`. Поэтому этим же сборщиком команд идут **все** записи звена —
применение, снятие и маркеры, — а `Release` проверяет не файл, а состояние композитора
(`enabled=false` И `running=false`) и возвращает `false`, если тот не отпустил. Обе эти вещи закреплены
тестами: сборщик argv (`--notify` в каждой форме записи и удаления) и релиз, который не заметил отказа
композитора.

**Два свойства, ради которых маршрут приемлем, и оба несущие, а не вежливость:**

1. **Тихий.** Никаких OSD: в отличие от `preview()` (ниже), запись конфигурации ничего не показывает.
2. **Обратимый.** Приложение помнит, что было у пользователя, и возвращает это: при выключении фильтра,
   при выходе из приложения и при неудачной записи. Память лежит **в том же конфиге** — три ключа-маркера
   `AcerHelperPrior*` в той же группе (KWin неизвестные ключи игнорирует). Это не украшение: без маркеров
   прогон, оборвавшийся с включённым фильтром (`kill -9`, пропажа питания), оставил бы `Active=true`, и
   следующий запуск, обязанный уважать включённый night light, принял бы **наше** наследство за
   пользовательское и отказался бы к нему подходить — фильтр запер бы сам себя, а экран остался бы тёплым.
   С маркерами наследство себя опознаёт, и `Recover()` откатывает его **на старте**, а не только при
   следующем применении: приложение может вернуться с выключенным фильтром, и тогда чинить было бы нечему.

**Не спорить с KDE.** Если у пользователя night light включён — неважно, по расписанию или с постоянной
температурой — приложение его **не трогает**: ни одной записи, и строка в UI прячется, а строка состояния
объясняет почему. Проверка делается **по конфигу**, а не по runtime-фазе: у включённого night light по
расписанию `enabled` истинно весь день, а красит он только ночью, поэтому проверка по фазе позволила бы
приложению днём забрать конвейер, а на закате начать драться с расписанием. Ловушка `enabled` ≠ «красит»
разобрана в коде и закреплена таблицей тестов.

**Запись проверяется, а не предполагается.** Если проверка не проходит — конфиг откатывается, а `Apply`
возвращает `false`. Именно эта проверка и поймала бы обе ошибки выше: без `--notify` она видит
`running=false`, с `Mode`-именем — `mode=1`, и в обоих случаях приложение честно говорит «не применилось»
вместо того, чтобы отчитаться о тёплом экране, которого нет.

### Звено GNOME: написано по документации, НЕ ПРОВЕРЕНО

**На этой машине не проверено ничего**: сессия KDE, и `gsettings list-schemas` не содержит
`org.gnome.settings-daemon.plugins.color` (замерено: «схема не существует»), поэтому проба звена отвечает
отказом и цепочка до него не доходит. Имена, типы и умолчания взяты из исходника схемы
`gnome-settings-daemon` (`data/org.gnome.settings-daemon.plugins.color.gschema.xml.in`):
`night-light-enabled` — Bool, по умолчанию false; `night-light-temperature` — `u`, в **кельвинах**, по
умолчанию **2700** (ниже нашей самой тёплой ступени 3000 — поэтому возврат пользовательского значения тут
особенно важен); `night-light-schedule-automatic` — по умолчанию **true**, то есть включённый night light в
GNOME почти всегда идёт по расписанию закат→рассвет, и правило «включённый не трогаем» покрывает именно его.

дисциплина та же — не трогать включённое, помнить, проверять, возвращать, — но у GNOME **нет** механизма
маркеров: `gsettings` отказывается писать ключ, которого нет в схеме, поэтому памяти негде пережить
падение. Это записанный пробел: оборвавшийся прогон оставит `night-light-enabled=true`, следующий запуск
(по тому же правилу) откажется к нему подходить, и симптомом будет включённый night light в собственных
настройках GNOME и спрятанная строка приложения — видно и обратимо вручную, но чинится не само. На KDE то
же наследство вдобавок запирало бы приложение, поэтому маркеры есть там и нет здесь.

### Почему НЕ выбран D-Bus-preview (измерено, и это причина отказа)

Интерфейс `org.kde.KWin.NightLight` даёт точный и самоочищающийся тинт, и он был измерен целиком:

| Вызов | Что делает (измерено) |
|---|---|
| `preview(u) -> ()` | ставит **ровно** запрошенную температуру, рампа ~1745 K/с (6500→3000 за 2.0 с) |
| — | **ограничен 15 с**: `m_previewTimer->start(15000)` в `nightlightmanager.cpp`, таймер **перевзводится на каждом вызове**. Замер: после одного вызова 3000 K держались 14.7 с; вызов раз в 5 с держал 75 с без единого шага |
| `stopPreview()` | снимает за <0.07 с; защищён `if (m_previewTimer)`, поэтому не может выключить night light самого KDE |
| `inhibit() -> u cookie` | аргумента не принимает и **температуру не ставит** (45 с — 6500 K); это холд на состояние KDE. Cookie — общий счётчик; холды снимаются при отключении клиента от шины |

**Причина отказа — OSD.** Каждый `preview()` заставляет KWin отправить `showText` в
`org.kde.plasmashell`/`/org/kde/osdService` («Предварительный просмотр цветовой температуры»), проверено на
шине: два вызова — два `showText` и два `osdText`. Постоянный фильтр требует перевзвода (окно 15 с), то
есть всплывающего попапа **раз в несколько секунд** — это не паритет с Win32-рампой, которая молчит. Метод
`hide` у службы OSD есть, но гасить чужой OSD (например, громкости) — драка с чужим компонентом, и он не
используется.

Ещё одно наблюдение, стоившее отдельного замера, потому что оно опровергает удобное допущение: **preview не
является per-client состоянием**. Клиент, отключившийся сразу после вызова, оставил экран закрашенным все
15 с; per-client уборка KWin покрывает `inhibit`, но не `preview`. Гарантия «экран не останется закрашенным»
— это таймер: клиент, убитый `SIGKILL` посреди тинта, оставил экран закрашенным ещё на 11.5 с, после чего
KWin убрал тинт сам.

### Уровни

Пять уровней (Off/Low/Medium/High/Long-use) — общий словарь UI; температуры лестницы
6500/4500/4000/3500/3000 K. Они **не тот же цвет**, что у рамп: Windows и X11 масштабируют только синий
канал (1.00/0.85/0.70/0.60/0.50), а это сдвигает белое к жёлто-зелёному, а не по локусу Планка — CCT
результата идёт **не в ту сторону** (0.50 синего даёт ≈6235 K против ≈4664 K у нейтрали по Макками),
поэтому честной «эквивалентной температуры» из тех таблиц не вывести. Лестница — обычная тёплая
(как у redshift/gammastep), и звенья совпадают словарём уровней и направлением, а не рендерингом.

Рамки температур — из `constants.h` KWin: `MIN_TEMPERATURE = 1000`, `DEFAULT_DAY_TEMPERATURE = 6500`,
`DEFAULT_NIGHT_TEMPERATURE = 4500`. Верхний предел — 6500, ниже лестница не доходит (`Clamp` подрезает
только верх).

### Пробелы: что здесь НЕ проверено

* **Живой `kwinrc` приложением так и не тронут.** Механика KWin измерена (владельцем и координатором,
  вручную, — см. выше: `--notify`, `Mode` числом, снятие через `Active=false`), но **путь целиком**
  «приложение → файл → композитор» кодом этого звена не прогонялся ни разу: все проверки идут через
  подставные делегаты. После всей работы в `kwinrc` нет ни группы `NightColor`, ни единого ключа
  `AcerHelper*` — это проверено. Разница важная: измерена механика, а не наша обвязка вокруг неё.
* **Цена ожидания на клик.** Смена уровня при уже включённом фильтре ждёт `quick-adjust` KWin (до ~2 с), и
  это происходит на UI-потоке (`LaptopService.SetBlueLight`). Замерена константа KWin
  (`QUICK_ADJUST_DURATION = 2000`), а не фактическая задержка клика в приложении: приложение на живой
  конфигурации не запускалось. Если это будет заметно, лечится переносом `Apply` с UI-потока — но это не
  файлы этого звена.
* **GNOME целиком** — см. выше: схемы на машине нет, звено не выбиралось ни разу.
* **`wlr-gamma-control`** — измерено только отсутствие протокола у KWin.
* **`gsettings get` для `u`** печатает `uint32 2700` — так записано в документации, и это то, что разбирает
  `ParseKelvin`; наблюдать негде. Если неверно, проверка чтения провалится и запись откатится (а не соврёт).
* **Экран.** Пиксели не читались ни разу; ни один замер не подтверждает визуально, что температура доходит
  до экрана — только состояние композитора.
* **Рамка `Mode=Constant` против расписания** в момент заката: включённый у пользователя night light
  приложение не трогает, поэтому сценарий «наш Constant, а у пользователя включилось расписание» не
  наблюдался; тесты покрывают решение, не наблюдение.
* **Несколько мониторов**: KWin применяет температуру глобально; по выходам не измерялось.


## `force_caps`: процедура и измеренный результат

Порядок установки: установщик кладёт **четыре** файла (правила udev, tmpfiles, юнит systemd
`acer-helper-smu-perms.service` для прав SMU и — только на Acer — параметры модуля), перезагружает
правила udev, прогоняет `udevadm trigger --subsystem-match=hwmon`, применяет tmpfiles, делает
`systemctl daemon-reload && systemctl enable --now acer-helper-smu-perms.service` и **последним в
том же скрипте** перезагружает модуль (`modprobe -r acer_wmi && modprobe acer_wmi`) — правило
должно лечь в набор **до** того, как перезагрузка создаст `pwm`-узлы, которые оно матчит.
Параметры ставит только Acer (`sys_vendor` из DMI) — на чужом ноутбуке файл не предлагается
вовсе, потому что `modprobe -r acer_wmi` там только ругался бы.

**Чего этот порядок не мог: сохранить права SMU до следующей загрузки.** `ryzen_smu` вставляется
из initramfs (журнал: `systemd-modules-load[335]: Inserted module 'ryzen_smu'` на прогоне dracut),
то есть bind-событие PCI уходит до появления настоящего systemd-udevd, а coldplug
`systemd-udev-trigger` переигрывает `add`/`change`, а не bind. Правило `ACTION=="bind"` поэтому на
этой машине не срабатывало ни разу за загрузку, и права терялись молча — файлы в `/etc` оставались
байт-в-байт равны упакованным, а порт андервольта (гейт по записи в `smn`) возвращал null, из-за
чего пропадала вкладка Tuning. Теперь за это отвечает юнит `acer-helper-smu-perms.service`
(`After=systemd-modules-load.service`, `ConditionPathExists=/sys/kernel/ryzen_smu_drv`), а
`RulesNeeded()` спрашивает не только «файлы совпадают», но и «права на месте»
(`SmuMailboxAccess.GrantMissing`; отсутствие узлов — не потерянное право). Подробности —
`docs/curve-optimizer-linux.md`.

**Процедура, из которой получилось 7200.** Кандидат выводится из модуля (см. выше), но
принимается он только после **диффа инвентаря до/после на самой машине** — иначе не видно
ровно того класса дефекта, который и погубил 7206: бит, дошедший до маски, может не дожить до
зарегистрированного устройства. Диффать надо: имена `/sys/class/rfkill/*/name` (и `rfkill list`),
`/sys/class/backlight`, `/sys/class/leds`, оба обработчика `platform-profile` с их наборами
`choices`, каналы чипа `acer` и WMI-хоткеи, плюс `journalctl -b -k`. Первые два кандидата
сравнивались между собой на одном и том же установщике — это и есть измерение из раздела выше.

Измерено после применения (2026-09-20, `force_caps=7200`):

- **появились** `pwm1`, `pwm1_enable`, `pwm2`, `pwm2_enable` под
  `/sys/devices/platform/acer-wmi/hwmon/hwmonN/`; имена — **`pwmN` / `pwmN_enable`**, не
  `pwmN_input`;
- **не потеряно ничего**: `rfkill list`, `/sys/class/backlight`, `/sys/class/leds`,
  имена `/sys/class/rfkill/*/name`, оба обработчика `platform-profile` со своими наборами, каналы
  чипа `acer` и Acer WMI-хоткеи совпали **байт в байт** до и после, а `journalctl -b -k` не
  получил ни одной новой ошибки ACPI/WMI;
- **не приобретено лишнего**: rfkill — только `hci0`/`phy0`, устройств `acer-wireless` /
  `acer-bluetooth` нет и строк `0xe2` в журнале нет. Именно этой строки проверки не хватало
  кандидату 7206 (см. «7206 (0x1C26) — ложный ответ» выше);
- **запись реальна и видна тахометром**: CPU 1920 → 5085 об/мин на MAX, GPU 619 → 4510 об/мин на
  MAX, ровно 0 об/мин при duty 0;
- **путь записи — собственный gaming-WMI ядра**: `WMI_gaming_execute_u64(0x10)` для скорости и
  `(0x0E)` для поведения, GUID `7A4DDFE7-…` — те же методы, которые Windows-половина зовёт
  напрямую.

Понять, что параметры **не** применены, тоже можно из ядра, и это стоит уметь: `predator_v4=Y`
при `force_caps=-1` означает «модуль загружен со штатной вычисленной маской» — тогда `pwm*`-узлов
нет вовсе, и деградация выглядит как **отсутствие секции вентиляторов**, а не как ошибка.

## Разведка EC HID: что проверено и почему маршрут закрыт

Четыре контрола и чтение яркости пытались взять **без модуля**, через EC HID. Результат
отрицательный, и он записан здесь подробно ровно для того, чтобы никто не пошёл этим путём снова.

**Пространство feature id перебрано терпеливо** (cmd `0x02`, idx `0x00`, все 256 id, выдержка
0.5 с): живых групп ровно **восемь** — `0x0000`, `0x0001`, `0x0002`, `0x0005`, `0x0008`,
`0x0009`, `0x000A`, `0x000B`; остальные 248 отказывают.

**Признак отказа:** `reply[2] == 0xE0`, но параметры все `0xFF` **и** `reply[5] == 0xFF`.
Одного `reply[5]` недостаточно: группа `0x0002` отвечает валидной строкой при `r5 = 0xFF`, так
что признак — это конъюнкция, а не одно поле.

**Решающая (зеркальная) проба.** Снимки всех групп в трёх состояниях — duty 100 %, ~8 % и auto —
показали, что двигается **только** группа `0x0008` (обороты), и только вслед за rpm. Ни duty, ни
режим, ни профиль на канале не отражаются:

| Группа | Что это оказалось |
|---|---|
| `0x0008` | обороты — единственная, что меняется; зеркалит **измеренное** состояние, которое hwmon отдаёт бесплатно |
| `0x0002` | статическая таблица кривой (константа при любом состоянии вентиляторов) |
| `0x000A` | idx `0x02` — фиксированные 100, не дежурство |
| `0x0000`, `0x0005`, `0x0009`, `0x000B` | скаляры-константы |
| `0x0001` | то, что пишет приложение; **не читается вовсе** (совпадает с `docs/power-an18-61.md`) |

Смысл вывода: канал зеркалит **измеренное** состояние, а не управляющее. Того, что он даёт, hwmon
уже даёт бесплатно, а управляющих ручек для LCD overdrive, лимитера/калибровки батареи, таймаута
подсветки и USB-зарядки в нём нет.

**Проба чтения яркости у ENE тоже провалилась.** Поле в дескрипторе есть (usage `0x43`,
логический максимум `0x64`), но `HIDIOCGFEATURE` на report `0xA4` возвращает `EINVAL` на любой
длине от 5 до 65, а ядро пишет `device returned incorrect report (63 vs 164 expected)`. Читаются
только `0xA1` и `0x00`, и коррелировать их не с чем. Значит чтение яркости этим путём недостижимо
— что совпадает с уже записанным в `Infrastructure/Vendors/Acer/EneHidController.cs`.

## Замеры конверта мощности

Байт режима EC → установившийся лимит dGPU (измерено под нагрузкой, каждый режим вводился из
заново подтверждённого режима 0; методика и предупреждения — `docs/power-an18-61.md`):

| mode | `enforced.power.limit` | SM clock | Профиль приложения |
|---|---|---|---|
| 0 | **108 Вт** | ~2230 МГц | Turbo (`0x05`) |
| 1 | 93 Вт | 2050 МГц | Performance (`0x04`) |
| 2 | 79 Вт | 1895 МГц | Balanced (`0x01`) |
| 3 | 71 Вт | ~1700 МГц | Quiet (`0x00`) |
| 4 | 71 Вт | ~1700 МГц | Eco (`0x06`) |
| 5+ | — | — | подтверждается и **игнорируется** |

Числа получены на **Windows** (NitroSense и наш WMI-путь), но принадлежат EC, а не ОС: Linux
шлёт те же 65-байтные отчёты `0xA0` тем же кодеком.

**На Linux эти числа замерить не удалось, и причина не в спящем dGPU: на этой установке дискретной
видеокарты не видно вообще.** `lspci` показывает только iGPU AMD (Radeon 880M), PCI-устройства с
vendor `0x10de` нет, hwmon-чипа `nvidia` не существует, а `nvidia-smi` отвечает
`No devices were found` — при том что модули nvidia загружены. Инструмент, назначенный планом
(`nvidia-smi --query-gpu=enforced.power.limit`), здесь **неприменим**, и прогреть dGPU тоже
нечем: путь «разбудить через power/control» требует самого PCI-устройства, которого нет. Поэтому
абсолютные 108/93/79/71 Вт остаются **непроверенными на Linux** — не потому, что сомнительно
соответствие mode↔профиль, а потому, что на этой коробке нет прибора.

**Но само соответствие профиля конверту на этой машине замерить всё-таки можно — с другой
стороны.** EC-режим задаёт не только лимиты dGPU, но и лимиты CPU-пакета, а на этой коробке есть
счётчик энергии RAPL: `/sys/class/powercap/intel-rapl:0/energy_uj` (только root; домен —
`package-0`, то есть пакет целиком, а не поддомен). Методика: держать `stress-ng --cpu 0` ровно
30 с на профиле и проинтегрировать счётчик — получается установившаяся мощность пакета:

| имя в `platform_profile` | байт EC | Профиль приложения | Мощность пакета CPU |
|---|---|---|---|
| `low-power` | `0x06` | Eco | **49.12 Вт** |
| `balanced` | `0x01` | Balanced | **59.27 Вт** |
| `balanced-performance` | `0x04` | Performance | **73.47 Вт** |
| `performance` | `0x05` | Turbo | **83.35 Вт** |

Повторный проход по краям: `low-power` 49.67 Вт, `performance` 84.41 Вт — разброс воспроизводится,
это не шум.

**Это и есть доказательство, которого требовал план, и вот почему.** Порядок монотонный, а четыре
значения различны. При **старом** маппинге — том самом живом дефекте, который эта работа
исправила — запись `performance` резолвилась в `ProfileKind.Performance` и уходила в **тот же**
EC-режим, что и `balanced-performance`: две строки таблицы выше показали бы **одну и ту же**
мощность. Они показывают 73.47 и 83.35. То есть исправление подтверждено измерением, а не именем:
ядровое слово `performance` действительно переводит машину в самое энергетически высокое
состояние, а `balanced-performance` — ступень под ним.

Честная оговорка: это **ватты CPU-пакета под чисто процессорной нагрузкой через RAPL** — другой
наблюдаемый, чем документированные GPU TGP-числа выше. Ими подтверждается **маппинг и порядок**, а
не значение 108 Вт: прибор для второго здесь по-прежнему отсутствует. Второй инструмент, который
мог бы дать пакет напрямую, не работает: `ryzenadj` установлен, но падает с
`Unable to get os_access Obj, check permission` даже от root, поэтому рабочий прибор на этой
коробке — именно RAPL.

Проверено и другое, и это проверяемо: раздел о профилях («Проверено на машине») — запись всех
пяти имён через вендорский узел и чтение их обратно.

## Пробелы и что именно пробовали

| Контрол | Почему недоступен | Что уже пробовали |
|---|---|---|
| LCD overdrive | mainline не даёт интерфейса; WMI `SetGamingProfile` аналога не имеет | разведка EC HID: управляющего канала нет (см. выше) |
| Лимитер и калибровка батареи | в mainline нет ни атрибута, ни свойства батареи под это | то же; generic-механизм `charge_control_*_threshold` на этой машине отсутствует целиком (`/sys/class/power_supply/BAT1` его не содержит), так что запасного пути нет и здесь |
| Таймаут подсветки клавиатуры | LED-класс отдаёт `stop_timeout`, только если его завёл драйвер; `acer-wmi` такого узла не публикует | то же; LED-класса `*kbd_backlight` на этой машине нет вовсе (клавиатурная подсветка целиком на ENE), а правило udev chmod'ит `stop_timeout`, если узел когда-нибудь появится от другого драйвера |
| USB-зарядка | mainline не даёт интерфейса в любом виде | то же |
| Чтение яркости подсветки | ENE — write-only HID; gaming-WMI геттер есть только на Windows | `HIDIOCGFEATURE` на `0xA4` → `EINVAL` на всех длинах 5..65 |

Запись яркости при этом **работает** (через ENE по hidraw) — недоступно только чтение, из-за
чего приложение не может синхронизировать ползунок с Fn-клавишами, как это делает Windows-путь.

## Что решено, а что нет

- **Linuwu-Sense**: удалён целиком (решение владельца, 2026-09-20). Linux-бэкенд module-free **по
  построению**. Кросс-ОС ключи настроек (`lcd_override`, `backlight_timeout`, `usb_charging`)
  остаются объявленными в Windows-половине — это контракт `settings.json`, а не привязка к узлам:
  на Linux эти строки просто не появляются.
- **`acpi_call` отклонён**: в этом ядре его нет (`modinfo` не находит, `/proc/acpi/call` нет), а
  сборка любого out-of-tree модуля под OGC-ядро на atomic-системе с Secure Boot — отдельный
  проект, более дорогой, чем задача. Разбор — `docs/open-decisions.md` §7.
- **LampArray** вне охвата (решение владельца): см. `docs/lamparray.md`.
- **Замер GPU-ватт на этой машине невозможен** — и это свойство машины, а не пробел бэкенда: её
  Linux-установка не видит дискретной видеокарты вовсе (`lspci` — только iGPU AMD, PCI-устройства
  с vendor `0x10de` нет, `nvidia-smi` — `No devices were found`, модули nvidia при этом
  загружены). `nvidia-smi --query-gpu=enforced.power.limit` здесь неприменим, и разбудить dGPU
  тоже нечем. Кто возьмётся за приёмку 108 Вт — сначала пусть убедится, что прибору есть что
  показать. **Маппинг при этом уже замерен** — по CPU-пакету через RAPL (см. «Замеры конверта
  мощности»), так что остаётся именно абсолютное число для dGPU.
- **Upstream-патч с DMI-записью для AN18-61** — потом: он убрал бы необходимость в
  `predator_v4`/`force_caps` на этой машине, но пока параметры остаются способом включить
  признаки.

### Открытое: что здесь НЕ измерено

Список того, что в этом документе (и в коде, на который он ссылается) написано как факт, но
прибором не проверено. Это не список дефектов — это список долгов.

- **Turbo-клавиша: стояла здесь как «не измерено» — замер сделан 2026-09-21, и записанное
  утверждение опровергнуто.** И здесь, и в `AcerHotkeys.Linux.cs` было написано «клавишу потребляет
  ядро (`cycle_gaming_thermal_profile`), а приложение следует за сменой профиля в пределах тика».
  Подтверждён из этого был ровно один факт — что параметр модуля существует и равен `Y`; замер с
  нажатием показал обратное: до ядра клавиша не доходит вовсе (ни evdev-кода на AT-клавиатуре, ни
  строки `acer_wmi` в журнале, ни движения счётчиков ACPI-прерываний), зато каждое нажатие приходит
  вендорским отчётом `04 85 ff` на hidraw Acer HID-устройства. Клавиша теперь декодируется
  приложением (`AcerHotkeyReports` — две сигнатурные байта, общие с Windows-половиной), и код с
  комментариями приведены к замеру. Долг закрыт.
- **Перезагрузки не было.** Живой прогон — не ребут: после установки исправленных файлов
  `modprobe -r acer_wmi && modprobe acer_wmi` **без явных параметров** (то есть ровно то, что
  делает загрузка) подняло `predator_v4=1 force_caps=7200` из `/etc/modprobe.d/acer-helper.conf`,
  rfkill вернулся как `hci0`/`phy0` без фантомных `acer-wireless`/`acer-bluetooth` и без строк
  `0xe2`, а `pwm`-узлы появились заново с групповой записью. Это самое близкое к ребуту
  доказательство из имеющихся; сама перезагрузка ещё предстоит.
- **`PendingReboot`: подсказка «перезагрузитесь» живёт одну СЕССИЮ, а не до перезагрузки.**
  Сначала — что здесь исправлено, потому что это половина записи: совет больше **не** одноразовый.
  При `PendingReboot` (файлы легли, но модуль не перезагрузился, поэтому параметры не в силе)
  приложение оставляет баннер доступа на экране и **переподписывает** его: «Restart your computer to
  finish enabling the unlocked controls (click to retry).» (русская строка — в `Strings.Ru.cs`), а
  строка состояния несёт только немедленную обратную связь («… the acer-wmi driver could not be
  reloaded, so the new module settings take effect after a reboot.»). Почему именно баннер, а не
  строка состояния, — причина **механическая** и её стоит помнить: `Notify` пишет тот же слот
  `Status`, который тик обновления перезаписывает сообщением самого устройства, а на этом бэкенде
  оно не пустое никогда, — то есть приказ о перезагрузке, положенный туда, исчезает за один тик
  (~3 с) и заменяется текстом, который про перезагрузку не говорит вовсе. Баннер же виден, пока
  что-то его не снимет. Клик по баннеру **повторяет** установку — это реально помогает в худшем
  варианте, когда модуль выгрузился и не загрузился назад и драйвер пропал на сессию, — а
  формулировка «could not be reloaded» выбрана так, чтобы покрыть и его, и случай «модуль занят».
  Состояние переживает и смену языка (перестройка окна по языку снова показывает баннер,
  `AppController._accessRebootPending`).
  **Остаточный пробел — память процесса.** Флаг лежит только в памяти, на диск не пишется, поэтому
  выход из приложения и повторный запуск (в отличие от перезагрузки машины) не показывают баннера
  вовсе: установленные файлы байт-в-байт равны упакованным, `RulesNeeded()` возвращает false, а
  почему файлы вообще ставились, помнить некому. Следствие: подсказку пропустит тот, кто
  перезапускает приложение, а не компьютер. Это **решение, а не упущение** — сохранить её значило бы
  писать на диск состояние ради условия, которое снимает перезагрузка, и реализатор счёл это худшим,
  чем пробел, оставив выбор владельцу.
  Что при этом сделано правильно: сам `PendingReboot` выставляется не по коду возврата перезагрузки
  модуля (она под `|| true` и статуса не несёт), а по чтению собственных файлов параметров модуля в
  `/sys/module/acer_wmi/parameters/`, то есть ровно тогда, когда параметры действительно не в силе
  (`HardwareAccess.ParametersAreLive`).

Закрыто измерением 2026-09-20 и с этого списка снято: **кросс-ОС приёмка `settings.json`**,
**UI-путь вентиляторов** — обе прошли одним прогоном через собственный код приложения
(Windows-овый `FanPresets` под ключом `"5"` применён портом вентиляторов, вентиляторы
раскрутились; запись — «Проверено на машине, через САМ код приложения» в разделе о вентиляторах,
там же наблюдение о возврате на `balanced`), — и **сверка датчиков под нагрузкой** (`temp1`
против `k10temp.Tctl`, расхождение ≤ 1 °C; запись — «закрывающий замер» в разделе «Датчики»).

## Завершение сеанса: окно обязано отпускать сеансового менеджера (2026-09-21)

Сообщено владельцем: «выплывало сообщение, что завершение сеанса отменено (безымянное приложение).
Пришлось отключить acer helper сначала» — то есть машина выключалась только после ручного выхода из
приложения.

**Причина — наша, и она была в одной строке.** `MainWindow.Closing` отменял **любой** запрос на
закрытие, не глядя на причину: так сделано правило трея («закрытие прячет флайаут, приложение
живёт»). Но Avalonia на X11 — клиент сеансового протокола XSMP: у процесса есть ICE-соединение с
ksmserver и загружен `libICE.so.6.3.0`, а в самой сборке есть `SmcOpenConnection` / `SaveYourself` /
`SmcDieProc`. KDE при выходе просит приложение закрыть окна и **отменённое закрытие читает как отказ
приложения завершить сеанс** — отсюда и сообщение, и «безымянное»: имя сеансового клиента Avalonia не
объявляет.

Причины закрытия в Avalonia 12.1.2 (считаны из установленной сборки, не по памяти):
`Undefined=0`, `WindowClosing=1`, `OwnerWindowClosing=2`, `ApplicationShutdown=3`, `OSShutdown=4`.

**Правка.** Решение вынесено в чистую функцию `UI/FlyoutClosePolicy.cs` (un-suffixed, значит
проверяется тестами; на Windows тот же запрос приходит как `WM_QUERYENDSESSION`, поэтому политика
намеренно кросс-ОС): прячут окно только `WindowClosing` и `Undefined`, а `ApplicationShutdown`,
`OSShutdown` и `OwnerWindowClosing` окно отпускает. На отпущенном закрытии поднимается
`MainWindow.SessionEnding` → `FlyoutCoordinator` → `AppController.ExitApp()`, потому что иначе
приложение и не завершится: `ShutdownMode = OnExplicitShutdown`, а трей держит процесс живым без
единого окна. `ExitApp` получил флаг повторного входа (пункт меню трея и конец сеанса могут прийти
вместе), а само событие отправляется через очередь UI-потока — обработчик выполняется внутри
закрытия окна, а разбор приложения закрывает окна снова.

**Что проверено, а что нет.** Проверено: сборка и тесты (`FlyoutClosePolicyTests` — все пять причин
плюс три guard-строки по источнику), и что закрытие окном по-прежнему только прячет флайаут.
**Не проверено: сам конец сеанса** — для этого нужен настоящий выход из системы; приёмка — следующее
выключение машины владельцем. Если сообщение повторится, искать надо не здесь: политика причин
закрытия больше не отменяет ничего, кроме закрытия окном.

## Wayland: почему приложение остаётся X11-клиентом (проба 2026-09-20)

Пробовали нативный Wayland-бэкенд Avalonia (`ACERHELPER_WAYLAND=1`, отдельная сборка). Он
**работает** — запускается, трей через StatusNotifierItem регистрируется, закрытие по клику мимо
срабатывает, падений нет, — но выпадающая панель теряет три своих определяющих свойства, потому что
в xdg-shell их решает композитор, а не клиент:

| свойство | X11 | Wayland |
|---|---|---|
| позиция | угол, как задумано (`Reanchor()` ставит `+2830+330`) | **по центру** — KWin поставил на `x=1142` при логической ширине 2752, то есть ровно `(2752−468)/2`; присвоение `Position` игнорируется |
| поверх всех | `keepAbove=true` | **не работает** — в xdg-shell такого состояния нет |
| не в списке задач | `skipTaskbar=true` | **не работает** |
| трей, закрытие по клику мимо | работает | **работает** |

Что выяснено про способы это починить:

- **layer-shell из Avalonia недостижим.** В `Avalonia.Wayland` нет ни одного упоминания
  `layer_shell`/`zwlr`; роли поверхностей — только xdg-shell (toplevel/popup). А именно layer-shell
  (в сессии он есть, `zwlr_layer_shell_v1` v5) и есть штатный способ якорить панель к краю выхода с
  отступом. Значит «правильный» путь — нативный слой-сурфейс или другой тулкит, то есть проект, а не
  настройка.
- **Правило KWin проверить не удалось**, и это отрицательный результат: написанное правило не
  применилось даже к X11-контролю, поэтому опыт ничего не говорит именно о Wayland. Отдельно важно,
  что правило умеет только **фиксированную координату**, а не «правый-нижний угол текущего экрана» —
  при двух выходах с разными масштабами это негодное решение.
- **Резкость: выигрыш есть, но только на одном выходе.** Нативный Wayland берёт дробный масштаб
  per-output (1.25 и 1.5), тогда как XWayland имеет один глобальный (`[Xwayland] Scale=1.25`).
  Замер на выходе с 1.25 разницы не показал (17.60 против 19.21 по краевой энергии на одной строке
  интерфейса); случай 1.5 наблюдать не удалось, потому что выход выбирает композитор.

**Цена:** `Avalonia.Wayland` не существует ниже 12.1.0, поэтому проба вынужденно подняла все четыре
пина Avalonia с 12.0.5 на 12.1.2 — это обновление решено оставить (оно проверено: X11-путь идентичен,
тесты те же), но сама проба откачена: Wayland-пакета и переменной включения в дереве нет.

**Незакрытое наблюдение:** владелец видел у wayland-сборки верхний бар с кнопками и сказал, что он
держался, пока не собрали следующую версию. Проба этого не воспроизвела (`frameGeometry ==
clientGeometry`, окна безрамочные), но нашла, что Avalonia вообще-то договаривается о клиентских
декорациях и имеет опцию `ForceDrawnDecorations`; наиболее вероятное объяснение — первичная серверная
рамка до того, как запрос клиента доедет. Вопрос закрыт вместе с откатом пробы, но записан, чтобы не
потеряться, если Wayland когда-нибудь вернётся в повестку.

## `force_caps` и пять контролов: что гейтит что, и почему параметр здесь не ответ (2026-09-22)

Разбор написан **до** решения «писать ли свой модуль ради пяти контролов» и отвечает на три
вопроса: какими битами способностей закрыты недостающие интерфейсы и дотягивается ли до них
`force_caps`; дотягивается ли до них уже существующий EC-канал приложения; и движется ли туда
upstream. Порода каждого утверждения названа: **измерено** (прибором на этой машине),
**прочитано из исходника** (torvalds/linux, `drivers/platform/x86/acer-wmi.c` — master, сверенный
по тегам `v6.12`…`v7.2`) или **выведено** (следствие из двух первых, прибором не проверенное).
Ничего не записывалось в железо; новых замеров в этой работе нет — «измерено» здесь всегда
отсылает к уже записанному выше или в `docs/plan-grant-durability.md`.

### Карта `ACER_CAP_*` — прочитано из исходника

Битов ровно **тринадцать**, `BIT(0)`…`BIT(12)`; четырнадцатого в mainline нет (`force_caps` —
это **присваивание маски целиком**, `interface->capability = force_caps`, поэтому выставить бит,
которого нет в перечислении, нечем — см. вывод ниже).

| бит | значение | что открывает | где спрашивается |
|---|---|---|---|
| `ACER_CAP_MAILLED` | `BIT(0)` `0x0001` | светодиод почты, класс LED `acer-wmi::mail` | `acer_led_init` в `acer_platform_probe`; гашение в suspend/shutdown |
| `ACER_CAP_WIRELESS` | `BIT(1)` `0x0002` | rfkill WLAN `acer-wireless` | `acer_rfkill_init` |
| `ACER_CAP_BLUETOOTH` | `BIT(2)` `0x0004` | rfkill BT `acer-bluetooth` | `acer_rfkill_init` |
| `ACER_CAP_BRIGHTNESS` | `BIT(3)` `0x0008` | подсветка **панели** (backlight-класс); `ec_write(0x83)` на квирковом пути | `acer_backlight_init`; снимается, если `acpi_video_get_backlight_type() != acpi_backlight_vendor` |
| `ACER_CAP_THREEG` | `BIT(4)` `0x0010` | rfkill WWAN `acer-threeg` | `acer_rfkill_init` |
| `ACER_CAP_SET_FUNCTION_MODE` | `BIT(5)` `0x0020` | **только инициализация**: `acer_wmi_enable_rf_button()` плюс `acer_wmi_enable_lm()` или `acer_wmi_enable_ec_raw()` | `acer_wmi_init`, единственные два места |
| `ACER_CAP_KBD_DOCK` | `BIT(6)` `0x0040` | `SW_TABLET_MODE` для клавиатурного **дока** (не подсветки) | `acer_wmi_input_setup`, `acer_kbd_dock_event` |
| `ACER_CAP_TURBO_OC` | `BIT(7)` `0x0080` | OC через misc setting `OC_1`/`OC_2` | `acer_toggle_turbo` |
| `ACER_CAP_TURBO_LED` | `BIT(8)` `0x0100` | gaming-LED, методы 2/4 класса `AcerGamingFunction` | `WMID_gaming_set_u64`/`get_u64` |
| `ACER_CAP_TURBO_FAN` | `BIT(9)` `0x0200` | режим вентиляторов через `SetGamingFanBehavior` | `acer_toggle_turbo` |
| `ACER_CAP_PLATFORM_PROFILE` | `BIT(10)` `0x0400` | регистрация обработчика `platform-profile` **и** реакция на клавишу режима (`key_num == 0x5`) | `acer_platform_profile_setup`, `acer_wmi_notify` |
| `ACER_CAP_HWMON` | `BIT(11)` `0x0800` | чип `acer`: `temp1..temp3`, `fan1_input`/`fan2_input` | `acer_wmi_hwmon_init` |
| `ACER_CAP_PWM` | `BIT(12)` `0x1000` | **видимость** `pwmN`/`pwmN_enable` на том же чипе | `acer_wmi_hwmon_is_visible` — единственное место |

Две подробности карты, которые видно только из исходника и которые стоит помнить:

- **`pwmN` и есть `HWMON_PWM_INPUT`.** `drivers/hwmon/hwmon.c`, таблица `hwmon_pwm_attr_templates`:
  `[hwmon_pwm_input] = "pwm%d"`, `[hwmon_pwm_enable] = "pwm%d_enable"`. То есть измеренная выше
  форма имён (`pwmN`, без `_input`) — не особенность этой сборки, а общее правило hwmon;
  `acer_wmi_hwmon_info` объявляет `HWMON_PWM_INPUT | HWMON_PWM_ENABLE` на оба канала, а
  `acer_wmi_hwmon_is_visible` отдаёт `0` на `hwmon_pwm`, если бита нет. Читает `pwmN` через
  `WMID_gaming_get_gaming_fan_speed`, пишет — через `set_gaming_fan_speed`/`set_fan_behavior`.
- **`ACER_CAP_SET_FUNCTION_MODE` — не про пять контролов, а про режим прошивки.** Это
  единственный бит, который драйвер выставляет сам (`if (wmi_has_guid(WMID_GUID3)) capability |=
  ACER_CAP_SET_FUNCTION_MODE`), но присваивание `force_caps` идёт **после** — поэтому в маске его
  приходится писать явно, иначе модуль молча пропустит и `acer_wmi_enable_rf_button()`, и выбор
  Launch Manager / EC raw.

### Что делает `force_caps` и что означает `7200`

**Прочитано из исходника.** Умолчание — `force_caps = -1` («не переопределять»). Порядок в
`acer_wmi_init` такой: `WMID_set_capabilities()` (из блока `WMID_GUID2` даёт `WIRELESS`/`THREEG`/
`BLUETOOTH`, плюс безусловный `ACER_CAP_BRIGHTNESS`) → `set_quirks()` (по квирку модели:
`.turbo` → три TURBO-бита, `.predator_v4` → `PLATFORM_PROFILE | HWMON`, `.pwm` → `PWM`) → отсечение
`BRIGHTNESS` по типу подсветки → `|= ACER_CAP_SET_FUNCTION_MODE` → **и только потом**
`interface->capability = force_caps`. Три следствия, все наблюдаемые: значение заменяет маску
целиком; `SET_FUNCTION_MODE` надо писать самому; `BRIGHTNESS` и коммуникационные биты, вычисленные
драйвером, теряются (на этой машине терять нечего — измеренный дифф инвентаря выше не показал ни
одной потери).

**`7200` = `0x1C20`** = `BIT(12) | BIT(11) | BIT(10) | BIT(5)` = `PWM | HWMON | PLATFORM_PROFILE |
SET_FUNCTION_MODE`. Это не «правдоподобное» число, а ровно то, что выдал бы сам драйвер этой
модели, будь она в `acer_quirks`: `quirk_acer_nitro_an515_58 = { .predator_v4 = 1, .pwm = 1 }` даёт
три из четырёх битов через `set_quirks()`, а `SET_FUNCTION_MODE` добавляется по наличию
`WMID_GUID3` — который на машине есть (измерено). Принимается значение, как и записано выше, не
суммой, а диффом инвентаря.

**Поправка к арифметике, найденная этой сверкой (и только к подписям).** `7206` — это **`0x1C26`**,
а не `0x1C23`, и он выставляет `0x6` = `WIRELESS | BLUETOOTH`, а не `0x3`: `0x3` — это
`MAILLED | WIRELESS`, `BLUETOOTH` же `BIT(2)` = `0x4`. Подпись была ошибочна в двух местах, и оба
исправлены: строка «7206 (0x1C26)» здесь выше и строка «WIRELESS | BLUETOOTH bits (0x6, …)» в
`packaging/acer-helper-modprobe.conf`; **значение `force_caps=7200` и весь вывод про 7206 при этом
верны**, и вот чем это доказывается независимо от арифметики: в журнале стоят
`Get 0x1 Device Status failed` и `Get 0x800 Device Status failed`, а это два вызова
`wmid3_get_device_status()` из `acer_rfkill_register()` с `ACER_WMID3_GDS_WIRELESS` (`1<<0`) и
`ACER_WMID3_GDS_BLUETOOTH` (`1<<11` = `0x800`). Второй вызов возможен только при выставленном
`ACER_CAP_BLUETOOTH` — то есть измерение требует ровно `0x6`, что даёт именно `7206 = 0x1C26`.
Измерение и исходник согласны, разошлась подпись под ними.

### Пять контролов: интерфейса нет ни за каким битом — прочитано из исходника

**Ни один из пяти контролов в `acer-wmi.c` не гейтится никаким битом, потому что кода для них
там нет вообще.** Это не «не нашли подходящий флаг»: в файле нет ни `power_supply`, ни
`charge_control_end_threshold`, ни LED-класса подсветки клавиатуры, ни таймаута, ни чего-либо с
`lcd_override`; единственные вхождения слова `backlight` — это `ACER_CAP_BRIGHTNESS` и
`MODULE_PARM_DESC(brightness, "Set initial LCD backlight brightness")`, то есть подсветка **панели**.
Слово `battery` не встречается ни разу. `force_caps` здесь бессилен **по построению**: он
присваивает значение переменной, чьё перечисление кончается на `BIT(12)`.

Ниже — чем каждый контрол является на Windows (из `AcerDevice.Windows.cs` / `AcerBattery.Windows.cs`)
и что из этого есть в драйвере. Колонка «класс» важна: пять контролов живут в **четырёх разных**
WMI-классах, и в одном из них драйвер не ходит вовсе.

| контрол | класс / методы (Windows-половина) | что есть в `acer-wmi.c` |
|---|---|---|
| LCD overdrive | `AcerGamingFunction` `7A4DDFE7…` (= `WMID_GUID4`): `SetGamingProfile`(1) / `GetGamingProfile`(3) | **методов 1 и 3 нет вовсе**; из `WMID_GUID4` драйвер зовёт только 2/4 (LED), 5 (sysinfo), 14/15 (behavior), 16/17 (speed), 22/23 (misc setting) |
| лимитер заряда | `BatteryControl` `79772EC5…`: `GetBatteryHealthControlStatus`(20) / `SetBatteryHealthControl`(21) | **класса нет**; отдельного `drivers/platform/x86/acer-wmi-battery.c` в mainline нет (путь отдаёт 404, `ACER_WMI_BATTERY` в `Kconfig` отсутствует, в каталоге только `acer-wmi.c`, `acer-wireless.c`, `acerhdf.c`) |
| калибровка батареи | тот же класс, метод 21, маска другая | то же — и в mainline не предложена |
| таймаут подсветки клавиатуры | `APGeAction` = `WMID_GUID3` `61EF69EA…`: `SetFunction`(1) / `GetFunction`(2), аргумент — packed u64 | **GUID знаком** — им драйвер делает `wmid3_set_function_mode()` и `wmid3_get_device_status()`, — но вход там структура `func_input_params`, u64-аргумента нет, и методов 1/2 с u64 драйвер не зовёт |
| USB-зарядка | тот же `APGeAction`, метод 2 для чтения и 1 для записи | то же |
| (чтение яркости подсветки) | `GetGamingKBBacklight` (метод 21 того же gaming-класса) | не вызывается ни разу |

Вывод по вопросу 1: **`force_caps` — не ответ, и не потому, что значение не то, а потому что
гейтить нечего.** Второй слой того же вывода: даже если бы бит добавили, `force_caps` —
**параметр загрузки модуля**, а не интерфейс: бит открывает узел, но не придумывает метод. Для
любого из пяти нужен новый код в драйвере, а не новое число в `modprobe.d`.

### Параметры модуля — прочитано из исходника

| параметр | умолчание | что делает |
|---|---|---|
| `mailled` | `-1` | начальное состояние LED почты; `set_u32(mailled, ACER_CAP_MAILLED)` в `acer_commandline_init()` (после регистрации устройства) |
| `brightness` | `-1` | начальная яркость **панели** через `ACER_CAP_BRIGHTNESS` |
| `threeg` | `-1` | начальное состояние 3G; пропускается при `has_type_aa` |
| `force_series` | `0` | «навязать серию»; реализована ровно одна — `2490` (Travelmate 2490). Ненулевое неизвестное значение оставляет `quirks` пустым, то есть **отключает и разбор DMI-таблицы** |
| `force_caps` | `-1` | замена маски способностей целиком; он же — DMI-callback `set_force_caps()` для нескольких планшетов Switch/One 10, где через него выдают `ACER_CAP_KBD_DOCK`, если пользователь ничего не навязал |
| `ec_raw_mode` | `false` (`0444`, только при загрузке) | см. ниже |
| `cycle_gaming_thermal_profile` | `true` (`0644` — **единственный**, меняемый на ходу) | клавиша режима перебирает профили (`platform_profile_cycle()`) вместо переключения Turbo; читается в `acer_thermal_profile_change()` |
| `predator_v4` | `false` | в `find_quirks()` **заменяет** разбор DMI на один `quirk_acer_predator_v4` — то есть DMI-таблица не читается вовсе. Форма та же, что у `force_caps`: не «добавить», а «заменить» |

**Что `ec_raw_mode` делает на самом деле.** Если `WMID_GUID3` есть и `SET_FUNCTION_MODE` в маске,
загрузка вместо `acer_wmi_enable_lm()` зовёт `acer_wmi_enable_ec_raw()`; обе — один и тот же
`wmid3_set_function_mode()`, различаются **одним битом входа** (`app_status`/`app_mask`):
`enable_lm` шлёт `app_status = 0x01` («Launch Manager Active»), `enable_ec_raw` — `0x00`
(«Launch Manager Deactive», бит 0 структуры подписан как «Launch Manager Status»). Содержание —
не окно в EC, а сообщение прошивке о том, что Acer-агент не запущен. Три следствия, которые
приложению пришлось бы учитывать:

1. **Опрос rfkill.** `acer_rfkill_init()`/`acer_rfkill_exit()` планируют и отменяют
   `acer_rfkill_work` при `(ec_raw_mode || !wmi_has_guid(ACERWMID_EVENT_GUID)) &&
   has_cap(ACER_CAP_WIRELESS | ACER_CAP_BLUETOOTH | ACER_CAP_THREEG)`; сама работа
   перепланирует себя раз в секунду (`round_jiffies_relative(HZ)`). **Условие конъюнктивное**:
   на этой машине при `force_caps=7200` ни один из трёх битов не выставлен, поэтому опроса не
   будет даже с `ec_raw_mode=1` — это **выведено** из исходника и согласуется с измеренным
   (фантомных rfkill нет).
2. **Отказ загрузки.** В `acer_wmi_init` неудача `acer_wmi_enable_ec_raw()` — это `return -ENODEV`,
   то есть `ec_raw_mode=1` на машине, где метод не отвечает, оставляет систему **без `acer-wmi`
   вообще** (не «с предупреждением»). Отказ уровня EC (`error_code`/`ec_return_value` в ответе)
   загрузку не роняет — только `pr_warn`; роняет отказ уровня WMI.
3. **И это не дверь в EC.** Ни `debugfs_create_file`, ни fops, ни разбора «адрес/значение» в
   драйвере нет: единственный `debugfs_create_*` — один `u32`-атрибут `devices` (битовая карта
   `WMID_GUID2`), и создаётся он только при наличии `WMID_GUID2`. Разведка в
   `docs/ec-registers-recon.md` §0 записала это прибором; здесь подтверждается исходником.

Заодно: `predator_v4=1` и `force_caps=7200` вместе обходят **оба** механизма подбора — DMI-таблицу
и вычисление маски. На этой машине терять нечего (измерено), но на другой это ровно тот случай,
когда строка параметров молча отнимает признаки, которые драйвер выдал бы сам. Правило
«перевыводи на машине» из раздела выше этим только усиливается.

### EC-канал приложения до этих пяти не дотягивается — измерено + прочитано из кода

- **Формат и что шлётся.** `A0 00 A0 <featureId:LE16> <cmdId> <params…>` — 65-байтные feature-отчёты,
  id отчёта `0xA0`, ответ с `byte[2] == 0xE0` на успех кадра. Приложение **пишет ровно одно**:
  feature `0x0001`, cmd `0x01`, параметр — байт режима (`SetTargetSystemUsageMode`). Читает:
  feature `0x0000`/cmd `0x04` (capability), feature `0x0002`/cmd `0x02` (таблица), feature
  `0x0000`/cmd `0x06` (лимит). Ни адреса, ни байта EC RAM в этом протоколе нет — это
  HID-feature-протокол Acer со своими feature id, а не окно в EC.
- **Измерено** (разведка EC HID выше): из 256 feature id живых восемь (`0x0000`, `0x0001`, `0x0002`,
  `0x0005`, `0x0008`, `0x0009`, `0x000A`, `0x000B`), и ни один не является управляющей ручкой для
  пяти контролов: единственная, что двигается, — `0x0008`, и только за об/мин; `0x0001` не
  читается вовсе.
- **Про регистры — честный ответ: «неизвестен на этой машине», а не «известен, но не отдан».**
  `EC[0x06]` для таймаута подсветки — самое сильное из известного, и то измерено на **других**
  моделях (nbfc-linux#65, AN515-47). Для лимитера — `EC[0x03]`/`0xDD` как «композитный байт» на
  AN515-46/47/57/58 (не подтверждено на AN18-61); для калибровки — `+0x80` в том же байте, оттуда
  же; для USB — `EC[0x08]` как проектное знание **без дампа**; для LCD overdrive — `EC[0x21]`,
  **опровергнутый** двумя другими проектами. Ни одного измерения на AN18-61 нет.
- **И даже с адресом.** ACPI EC RAM приложению недоступна ничем: `ec_sys` в этом ядре не собран,
  `acpi_call` отсутствует, generic-интерфейса вызова WMI-методов из userspace не существует;
  единственная дверь — `/dev/port`, требующая `CAP_SYS_RAWIO` (root на каждый запуск) и
  обходящая мьютекс EC-драйвера. Это довод против маршрута, а не за него.

Вывод по вопросу 2: **канал EC приложения до пяти контролов не дотягивается**, и это закрыто и
измерением (перебор feature id), и формой протокола (в нём нет EC-адресации). «Отсутствие
интерфейса в драйвере» здесь верно ровно наполовину: интерфейса нет в драйвере, но и в железе
байтовый маршрут на этой модели не показан — известны только чужие адреса.

### Upstream: RFC приземлился — прочитано из исходника

- `WMID_gaming_set_misc_setting()` / `WMID_gaming_get_misc_setting()`, `#define
  ACER_WMID_SET_GAMING_MISC_SETTING_METHODID 22` / `…GET… 23`, маски
  `ACER_GAMING_MISC_SETTING_STATUS_MASK`/`_INDEX_MASK` = `GENMASK_ULL(7, 0)` и `_VALUE_MASK` =
  `GENMASK_ULL(15, 8)` — **в mainline есть**, вместе с `enum acer_wmi_gaming_misc_setting {
  OC_1 = 0x0005, OC_2 = 0x0007, SUPPORTED_PROFILES = 0x000A, PLATFORM_PROFILE = 0x000B }`
  (`SUPPORTED_PROFILES` помечен в перечислении как «Unreliable on some models»).
- **Когда приземлилось** (сверено по тегам): в `v6.12`/`v6.13` хелперов нет; в `v6.14` они есть
  вместе с `ACER_CAP_HWMON`; `ACER_CAP_PWM` появляется в `v6.19`; в `v7.2` и в master всё на месте.
  То есть работа RFC от 2024-12-29 не заглохла — она вошла в 6.14 как переписанный на WMI
  `platform-profile`, а в 6.19 туда же добавилась запись в вентиляторы (`ACER_CAP_PWM`, методы
  speed 16/17 и behavior 14/15).
- **Направление видно по диффу между тегами, и оно показательно.** В `v6.13` чтение профиля — это
  `ec_read(ACER_PREDATOR_V4_THERMAL_PROFILE_EC_OFFSET /* 0x54 */, &tp)`; в `v6.14` там уже
  `WMID_gaming_get_misc_setting(ACER_WMID_MISC_SETTING_PLATFORM_PROFILE, &tp)`. Драйвер **ушёл от
  сырого байта EC к WMI-методу**, а не наоборот.
- **Это тот же механизм `0x0B`, которым ходит Windows-половина.** `AcerDevice.Windows.cs` шлёт
  `SetGamingMiscSetting` со входом `0x0B | ((ulong)byte << 8)`, а драйвер собирает вход как
  `FIELD_PREP(INDEX_MASK, setting) | FIELD_PREP(VALUE_MASK, value)` — индекс в битах 7..0, значение
  в 15..8. Совпадение побитовое; `GetGamingMiscSetting` 0x0A/0x0B в приложении — те же два индекса.
- **Чего это не даёт.** Ни одного нового узла в userspace для пяти контролов: занятые индексы —
  только 0x05, 0x07, 0x0A, 0x0B (OC и профиль), и пять контролов через misc setting и не проходят:
  LCD overdrive — методы 1/3 другого класса, таймаут и USB — методы 1/2 `WMID_GUID3` с u64,
  батарея — вообще другой GUID. Ценность приземлившегося RFC — **образец формы** («методы класса
  заворачиваются в хелпер и открываются атрибутом»), а не готовый интерфейс.

### Что из этого следует

1. **`force_caps` как ответ на пять контролов закрыт**, и это доказано исходником, а не замером:
   перечисление `ACER_CAP_*` кончается на `BIT(12)`, а `force_caps` — присваивание.
2. **EC-канал приложения закрыт** измерением (перебор 256 feature id) и формой протокола.
3. **Бесплатного маршрута не осталось:** сырой EC RAM — только `/dev/port` под root с обходом
   мьютекса; WMI из userspace недостижим в принципе. Значит, для любого из пяти нужен **код в
   ядре**, и развилка ровно одна: **upstream-патч в `acer-wmi`** (та форма, в которой misc setting
   уже приземлился, и тогда интерфейс приходит с дистрибутивом) против **out-of-tree модуля**.
   Второй — то, что уже отвергнуто в `docs/open-decisions.md` §7 для `acpi_call`: сборка под
   конкретное OGC-ядро на atomic-системе с Secure Boot. «Свой» модуль эту цену не меняет.
4. **И до обеих развилок есть шаг дешевле обеих и без единой записи** — разбор DSDT этой машины
   (`docs/ec-registers-recon.md` §8): посмотреть, трогает ли AML пяти контролов именованные
   EC-поля. Он решает то, чего не решает ни исходник, ни инвентарь: существует ли на этой модели
   байтовый маршрут вообще. Побочный результат того же шага не менее важен — **`uFunctionList`
   машины**, то есть предлагает ли её прошивка лимитер и калибровку: сейчас это неизвестно, и без
   этого и свой, и upstream-драйвер пишутся вслепую.

### Чего эта сверка не проверяла

- **Установленную сборку `7.2.4-ogc3.1.fc44` не читали.** Отрицание «интерфейса нет» прочитано из
  master и сверено по тегам `v6.12`…`v7.2`; на машине ему соответствует только инвентарь (нет
  узлов, нет `charge_control_*`, нет LED-класса). Если OGC-сборка несёт правку в `acer-wmi`, здесь
  её не видно.
- **`0x800` и `0x1` в журнале — это device-биты GUID3, а не capability.** Вывод «бит `BLUETOOTH`
  был выставлен» — **выведенный** из этих строк и из `ACER_WMID3_GDS_*`, а не измеренный напрямую.
- **Тред RFC не открывался** (lore отдаёт страницу-заглушку Anubis, spinics не отвечает). О том,
  что работа приземлилась, судим **по исходнику и тегам**, а не по треду; содержание RFC
  подтверждено только в той части, которую видно в коде.
