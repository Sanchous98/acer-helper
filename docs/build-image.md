# Сборка релиза в контейнере

Один многостадийный `Dockerfile` в корне репозитория собирает из коммита тот артефакт, который вообще
собирается на Linux: приложение под Linux (Native AOT, `net10.0`/`linux-x64`). Ни Visual Studio, ни
установленного тулчейна с машины сборки: источник — контекст сборки, то есть коммит.

Второй артефакт, приложение под Windows, в этот файл не входит — и это измеренный факт, а не пропуск:
тулчейн отказывается кросс-собирать его из Linux. Разбор с текстами ошибок — в разделе «Почему
Windows-артефакта нет в образе».

Этот файл — точка входа: команды, что где оказывается, что закреплено, что проверено, а что нет.

## Стадии одного Dockerfile

| Стадия | Что это |
|---|---|
| `dotnet-base` | SDK 10.0.301 плюс предпосылки AOT: `clang-18`, `binutils` (`ld.bfd` и `objcopy`), `zlib1g-dev` |
| `app-linux` | сборщик: приложение под Linux → `/out/linux` |
| `artefacts` | экспорт: пустая файловая система, в которой только `/linux` и `/PROVENANCE.txt` |

Стадий драйвера (и самого каталога `driver/`) в файле больше нет — они удалены 2026-09-22, разбор в
датированной записи ниже.

## Быстрый старт

```bash
docker buildx build --target artefacts --output type=local,dest=dist .
```

`dist/` — BuildKit обязателен: `--output type=local` и кэш NuGet внутри образа без него не работают; в
Docker Desktop он включён по умолчанию.

| Путь | Что это |
|---|---|
| `dist/linux/` | каталог публикации: `AcerHelper` (нативный бинарник), `libSkiaSharp.so`, `libHarfBuzzSharp.so`, `.dbg` — то, что упаковывается в AppImage |
| `dist/PROVENANCE.txt` | версии SDK и clang, команда публикации, ревизия исходников (если передана) |

Ревизию исходников в провенанс кладут руками: `.git` в контекст не отправляется намеренно, поэтому взять
её изнутри неоткуда.

```bash
docker buildx build --target artefacts --output type=local,dest=dist --build-arg GIT_SHA=$(git rev-parse HEAD) .
```

Если BuildKit недоступен — сборка в образ и `create`+`cp`: у стадии экспорта внутри нет ничего, кроме
артефактов, поэтому копировать из неё безопасно.

```bash
docker build -t acerhelper-release:local --target artefacts .
docker create --name acerhelper-rel acerhelper-release:local
docker cp acerhelper-rel:/linux ./dist/
docker cp acerhelper-rel:/PROVENANCE.txt ./dist/
docker rm acerhelper-rel
```

## Что именно запускается внутри

Образ не изобретает команд: он повторяет то, что уже делает CI, дословно — `.github/workflows/build.yml`,
задание `linux`:

```
dotnet publish AcerHelper.csproj -c Release -f net10.0 -r linux-x64 --self-contained true -p:PublishAot=true -o publish-linux
```

Отличий два, и оба только в стадии `app-linux`:

- добавлено `-p:CppCompilerAndLinker=clang-18`. `Microsoft.NETCore.Native.Unix.targets` по умолчанию
  называет компилятор безверсионным `clang` и ищет его через `command -v`; в образ ставится только
  `clang-18`, поэтому пин передаётся явно, а не подразумевается;
- выход публикации (`publish-linux`) копируется в `/out/linux`, потому что стадия экспорта пуста: иначе
  `--output type=local` выгружал бы на диск вызывающего образ SDK.

## Что закреплено

| Вход | Значение | Почему так |
|---|---|---|
| Frontend Dockerfile | `docker/dockerfile:1.7.1` | нужен для `--mount=type=cache`; теги `:1` и `:1.7` плавают, поэтому закреплён патч. Всё используемое поддерживается с 1.3, так что зеркало без 1.7.1 обойдётся любым более новым фронтендом |
| SDK | `mcr.microsoft.com/dotnet/sdk:10.0.301-noble` | 10.0.301 — версия, которой этот репозиторий собирается на машине владельца (`dotnet --list-sdks`) |
| Компилятор AOT | выводится из SDK | `Microsoft.DotNet.ILCompiler` подключается неявно (`KnownILCompilerPack`), поэтому в `AcerHelper.csproj` нет версии компилятора, и здесь её тоже нет: закреплён SDK — закреплён и компилятор |
| Компилятор Linux | `clang-18` | пакет закреплён по мажорной версии, а не отдан метапакету `clang` |
| Линкер и стриппер Linux | `binutils` | `LinkerFlavor` для linux по умолчанию `bfd`, то есть нужен `ld.bfd`; `objcopy` из того же пакета — запасной стриппер, который берётся, когда `llvm-objcopy` не найден |
| zlib | `zlib1g-dev` | нативные библиотеки рантайма линкуются с zlib; документированная строка предпосылок для Ubuntu — `apt-get install clang zlib1g-dev` |
| Пакеты NuGet | из `AcerHelper.csproj` | образ не добавляет, не заменяет и не переопределяет ни одной версии |

Чего пин **не** покрывает, и это стоит знать: `apt` внутри закреплённого тега всё равно отдаёт `clang-18`
той версии, которая лежит в архиве Ubuntu на момент сборки образа, — закреплено имя мажорной версии, не
конкретный патч. Полная воспроизводимость потребовала бы `clang-18=<версия>` и снапшот-архива.

## Чего образ не делает

- **Не подписывает ничего.** Ни AppImage, ни что-либо другое — как и CI.
- **Не собирает AppImage и MSI.** AppImage — упаковка `packaging/{AppRun,…}` поверх каталога публикации и
  `appimagetool --appimage-extract-and-run`; MSI — WiX поверх каталога публикации Windows. Оба шага
  остаются там, где описаны: `.github/workflows/build.yml` и `README.md`.
- **Не запускает тесты.** Прогон обоих TFM — отдельный гейт владельца, не шаг упаковки релиза.
- **Не берёт ничего с машины сборки.** Ни один путь не монтируется: источник — только контекст сборки.
  `bin/`, `obj/` и `.git` из контекста исключены (`.dockerignore`).

## Почему Windows-артефакта нет в образе

Это измеренный факт. Native AOT под `win-x64` из Linux запрещён тем самым тулчейном, который стадия
`dotnet-base` и ставит, причём несколькими независимыми способами:

- `Microsoft.NETCore.Native.Publish.targets` валит публикацию с `Cross-OS native compilation is not
  supported.` — условие покрывает оба направления, снять его можно только `DisableUnsupportedError=true`;
- там же: `Add a PackageReference for 'runtime.linux-x64.Microsoft.DotNet.ILCompiler' to allow
  cross-compilation`. Компилятор, который исполняется на хосте, и нативные библиотеки цели — **разные**
  пакеты, и назвать их можно только `PackageReference`, то есть правкой `AcerHelper.csproj`, чего эта
  задача делать не должна;
- `Microsoft.NETCore.Native.Windows.targets` жёстко задаёт `CppLinker=link`, запускает
  `findvcvarsall.bat` (batch-файл, то есть `cmd.exe`), чтобы найти тулсет, и при неудаче говорит прямо:
  `Platform linker not found. … Desktop Development for C++ workload in Visual Studio.`;
- библиотек для линковки из NuGet-пакетов берутся **не все**. Библиотеки Windows SDK — берутся: пятнадцать
  записей `SdkNativeLibrary` (kernel32, ole32, …), `ucrt.lib` из принудительного `/DEFAULTLIB:ucrt.lib` и
  `uuid.lib`, который требуют сами нативные библиотеки рантайма, есть в `microsoft.windows.sdk.cpp(.x64)`.
  А нативные библиотеки рантайм-пака несут `/DEFAULTLIB:LIBCMT`, `/DEFAULTLIB:libcpmt` и
  `/DEFAULTLIB:OLDNAMES` — это статический CRT MSVC, собственность Visual Studio, и ни в одном WDK/SDK
  NuGet-пакете его нет (измерено сканированием каталога `native/` пакета
  `Microsoft.NETCore.App.Runtime.NativeAOT.win-x64`).

Существуют обходы — `PublishAotCross`, `PublishAotCrossXWin`, `PublishAotCross.LinuxToWin`; все они
приносят либо `msvc-wine`, либо `xwin` (скачивание тулчейна VC с CDN Visual Studio), требуют
`DisableUnsupportedError`, шима для `CppCompilerAndLinker` (перевод MSVC-синтаксиса в `lld-link`) и
`PackageReference` в csproj. Это неподдерживаемая комбинация, собранная сторонним MSBuild-пакетом, и
сознательно **не** сделана: она противоречит и пину версий, и запрету на правку csproj, и правилу не
выдавать непроверенное за проверенное. Поэтому Windows-артефакт собирается там, где поддерживаемый
тулчейн существует, — на Windows-хосте, как это уже делает задание `windows` в
`.github/workflows/build.yml`.

Это не шероховатость именно этого тулчейна, а документированная граница. Страница Microsoft про
кросс-компиляцию Native AOT
(`https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/cross-compile`, обновлена 2025-08-22)
говорит дословно: «Since there's no standardized way to obtain native macOS SDK for use on Windows/Linux, or
Windows SDK for use on Linux/macOS, or a Linux SDK for use on Windows/macOS, Native AOT does not support
cross-OS compilation. Cross-OS compilation with Native AOT requires some form of emulation, like a virtual
machine or Windows WSL.» Поддерживается только кросс-компиляция между **архитектурами** внутри одной ОС, а
единственный названный обход — эмуляция, то есть виртуальная машина. Wine — слой трансляции, а не
виртуальная машина, и в поддерживаемом списке его нет: поэтому отказ выше — не то, что нужно обойти шимом,
а сама граница, и обходы через `msvc-wine` упираются в неё же.

**Альтернатива, если сборка нужна в контейнере и на той стороне** — Windows-контейнер: база
`mcr.microsoft.com/dotnet/sdk:10.0.301-windowsservercore-ltsc2022`, установка Visual Studio Build Tools
через bootstrapper канала (`aka.ms/vs/17/release/vs_buildtools.exe`) с компонентами
`Microsoft.VisualStudio.Component.VC.Tools.x86.x64` и компонентом Windows SDK, затем та же команда CI
(`-f net10.0-windows -r win-x64 --self-contained true -p:PublishAot=true -o publish`) без единой правки —
на Windows у тулчейна корректные умолчания, и именно поэтому файла с этим содержимым здесь нет: он
потребовал бы демона в режиме Windows-контейнеров, а пины внутри него (версия MSVC и Windows SDK из канала
Visual Studio) всё равно не закрепляются хешем — bootstrapper публикуется только по плавающей ссылке
канала, и вместо хеша там годится та же проверка, что у CI для `PawnIO_setup.exe`: валидная подпись
Authenticode от Microsoft.

## Что проверено и что нет

Раздел назывался «Что не проверено» и начинался словами «Docker не запускался ни разу» — это было верно до
2026-09-18 и неверно с 2026-09-19. Список тот же, но с вердиктом по каждому пункту; вердикт — измерение, а
не предположение. Пункты, которые проверяли стадии драйвера, сняты вместе с ними 2026-09-22; сами эти
измерения остались в датированных записях ниже.

Проверено первой настоящей сборкой (2026-09-19):

1. **Тег фронтенда `docker/dockerfile:1.7.1` разрешается.** Скачан, digest
   `a57df69d0ea827fb7266491f2813635de6f17269be881f696fbfdf2d83dda33e`.
2. **Тег SDK существует, и noble даёт весь тулчейн.** `mcr.microsoft.com/dotnet/sdk:10.0.301-noble`,
   digest `ea8bde36c11b6e7eec2656d0e59101d4462f6bd630730f2c8201ed0572b295d5`. `apt` внутри стадии поставил
   clang 18.1.3 (`Ubuntu clang version 18.1.3 (1ubuntu1)`), binutils 2.42, `zlib1g-dev`.
3. **`-p:CppCompilerAndLinker=clang-18` принимается, и запасным стриппером работает `objcopy` из binutils.**
   Измерено внутри стадии `dotnet-base`: имя `clang` отсутствует, `clang-18` есть; `llvm-objcopy`

4. **`libicu-dev` не нужен.** Линковка прошла без него; в образ он не добавлен и добавлять его не пришлось.
5. **`--output type=local,dest=…` даёт именно ту раскладку, что в таблице выше.** Сверено с фактическим
   экспортом, файл за файлом — см. датированную поправку ниже; расхождений с таблицей нет.

Не проверено — и часть этого непроверяема здесь по своей природе:

1. **`--cache-from`/`--cache-to type=gha` в CI здесь не прогонялись** — нечем: бэкенда Actions на этой
   машине нет. Прогонялось только `--output type=local`.
2. **Прогон на чистом кеше слоёв не делался.** Кеш BuildKit сохранил слои `apt` и WDK от предыдущей
   сборки, поэтому измеренное время сборки (публикация 46.7 s на пустой кеш-точке NuGet) не включает
   9 минут, которые заняла установка `clang-18` на первой сборке. Это время известно из лога владельца, а
   не из моего прогона.
3. **Повторяемость байтов между машинами не проверена** — и не будет: см. оговорку про `apt` в разделе
   «Что закреплено», и то, что Windows-артефакт по-прежнему собирается на Windows.
4. **Причина исходного отказа при сборке NuGet не доказана** (см. датированные поправки): отказ не
   воспроизвёлся ни одной попыткой, включая точную команду на пустой кеш-точке. Поэтому `sharing=locked` —
   устранение единственного механизма, который мог это дать, а не доказанное исправление.

Отдельно — свойство, **изменившееся 2026-09-18**: **бинарник для Linux из этого образа и бинарник внутри
релизного AppImage — одни и те же байты.** CI больше не собирает приложение сам: задание `linux` в
`.github/workflows/build.yml` выполняет ту самую команду из «Быстрого старта» (`--target artefacts`), а
AppImage пакуется из выданного стадией `artefacts` каталога `dist/linux`. Прежнее утверждение — «CI собирает
в `fedora:41` (glibc 2.40), образ на `noble` (glibc 2.39), байты разные» — было верным до этой даты и снято
вместе с контейнером `fedora:41`, который из задания убран: границу glibc теперь задаёт стадия `dotnet-base`
(noble, glibc 2.39), то есть более старая из двух. Native AOT линкуется с glibc хоста сборки, поэтому
бинарник работает на своей или более новой системе — для сверки хешей с релизом это теперь как раз
безразлично.

## Датированные поправки

- **2026-09-18.** Файл создан. Утверждение, из которого он вырос, — «Windows-артефакт это кросс-сборка из
  Linux» — **неверно**: раздел «Почему Windows-артефакта нет в образе» это фиксирует. Отметка добавлена в
  `README.md` (раздел *Build*).
- **2026-09-18.** Правило `.gitattributes`, которое держало `driver/Dockerfile` в LF, переехало на корневой
  `Dockerfile` (и добавлен `.dockerignore`): с CRLF ломаются продолжения строк в `RUN`, а CR в конце шаблона
  `.dockerignore` — это молча не совпавшее исключение. Это тот же дефект, ради которого правило и
  существовало.
- **2026-09-18.** CI переведён на этот образ. Задание `linux` в `.github/workflows/build.yml` выполняет
  `docker buildx build --target artefacts --output type=local,dest=dist` (плюс `--cache-from/--cache-to
  type=gha,mode=max` и `--build-arg GIT_SHA`), пакует AppImage из `dist/linux` и не ставит на runner
  ничего: ни .NET SDK, ни `clang`/`zlib-devel`, ни dnf-пакеты, ни — вместе с самим заданием — контейнер
  `fedora:41`, в котором раньше шла AOT-сборка. Вместе с этим снято прежнее утверждение о разных байтах (см.
  «Что не проверено»): релизный AppImage теперь содержит бинарник из этого образа. Пакет драйвера тот же
  прогон собирает и отдаёт артефактом workflow, а не релизом: он неподписанный, а в поставку идёт только то,
  что вернётся из attestation signing. Задание `windows` интеграция не затронула — Windows-артефакт
  по-прежнему собирается на Windows-раннере теми же командами.
- **2026-09-18.** `driver/Dockerfile` удалён, его содержимое перенесено в стадию `wdk-toolchain` того же
  корневого `Dockerfile`; сценарий сборки драйвера сохранён дословно стадией `driver-image`, и
  `driver/README.md` показывает его новую первую строку. Причина — не экономия файла, а пин версии WDK:
  два экземпляра одного пина расходятся, и драйвер, собранный против KMDF новее объявленного в INF, не
  стартует на той ОС, которую INF называет. `driver/build.sh` не изменён.

### 2026-09-19 — первая настоящая сборка: отказ в `app-linux`, `sharing=locked`, и что именно проверено

**Первая сборка этого файла упала.** Стадия `app-linux`, шаг публикации, 33.39 s после старта, сразу после
`Determining projects to restore...`:

```
/usr/share/dotnet/sdk/10.0.301/NuGet.targets(198,5): error : Directory not empty :
    '/root/.nuget/packages/skiasharp/3.119.4/lib' [/src/AcerHelper.csproj]
```

До этого шага всё прошло: базовый образ скачался, `apt` поставил `clang-18`, `binutils`, `zlib1g-dev`,
`wdk-toolchain` собрался, драйвер скомпилировался.

**Что измерено.** Это ровно тот набор фактов, из которого выбрана правка; всё, что сверх него, —
предположение, и оно помечено как предположение.

- `NuGet.targets:198` в SDK 10.0.301 — это `<RestoreTask>` внутри цели `Restore`. Отказ пришёл из
  установки пакетов при restore, а не из компиляции.
- Начало кеш-точки NuGet (`exec.cachemount` с id `//root/.nuget/packages`) — 20:32:04 UTC, ровно старт
  exec'а публикации. То есть на момент отказа точка была **пустой**: половинчатый пакет в ней — следствие
  отказа, а не его причина. Это снимает версию «кеш принёс половинчатый пакет из прошлого прогона».
- Оставленное состояние: `skiasharp/3.119.4` — **наполовину удалённое дерево**. На месте: `.signature.p7s`,
  `interactive-extensions/`, `ref/` целиком и 17 из 22 каталогов `lib/`. Отсутствуют: `SkiaSharp.nuspec`,
  `icon.png`, `LICENSE.txt`, `README.md`, сам `.nupkg`, его `.sha512` и `.nupkg.metadata` — то есть все
  файлы, которыми NuGet помечает установку завершённой. Так выглядит рекурсивное удаление, которое не
  доехало до конца, а недоехать оно может только если в каталог одновременно кто-то пишет.
- Все остальные 34 каталога пакетов в той же точке — целые. Половинчатым был ровно один пакет.
- **Отказ не воспроизвёлся — ни одна попытка.** Все прогоны, которыми его пытались повторить, прошли
  успешно: точная команда публикации на никогда не использованной кеш-точке, холодная и следом тёплая
  (46.7 s и 33.1 s); та же команда против намеренно воссозданного половинчатого `skiasharp`; два параллельных
  restore в одной сборке; шесть параллельных restore в одну свежую точку; и, наконец, restore в одиночку
  против той самой точки, которую отказавшая сборка за собой оставила, — он её починил. NuGet чинит
  половинчатый каталог пакета всякий раз, когда он единственный писатель. Поэтому **причина не доказана**:
  доказан только сам механизм двух писателей в одном каталоге.

**Правка.** У кеш-точки NuGet поставлено `sharing=locked`. По умолчанию BuildKit даёт `sharing=shared`, то
есть писать в одну точку может любой exec сразу; `sharing=locked` их сериализует — второй ждёт первого
вместо того, чтобы распаковываться в те же каталоги. Это **единственная** из известных правок, которая
делает второго писателя невозможным: `NUGET_PACKAGES` в свежий путь под кешем не меняет ничего, а отказ от
кеш-точки в пользу обычного слоя стоил бы перекачивания сотен мегабайт на каждое изменение исходников
(слой инвалидируется вместе с ними). Цена `sharing=locked` — ожидание и только: пакеты не перекачиваются.

Что это **не** доказанное исправление — сказано и в самом `Dockerfile`, у этой правки.

**Экспорт сверен с таблицей выше, файл за файлом.** Расхождений нет:

`.cat` в пакете нет — как и написано выше. В `PROVENANCE.txt` измеренные SDK 10.0.301 и clang 18.1.3, пин

### 2026-09-22 — драйвер LampArray удалён целиком: стадии, `/driver`, `/driver-rust` и каталог `driver/`

**Решение владельца, дословно:** «тогда удаляй lamp array, мы не будем ставить неподписанный драйвер и не
будем покупать аттестацию у microsoft». Это ровно та граница, которую описывал раздел «Подпись — вне
контейнера» (удалён вместе с драйвером; его текст остался в истории git, а не в этом файле): неподписанный
пакет Windows не загружает, а в поставку попадает только то, что вернётся из attestation signing, то есть
EV-сертификат подписи кода и аккаунт Partner Center для оборудования. Ни того, ни другого не будет —
значит, не будет и пакета. Развилка при этом снята, а не потеряна: VHF существует только в ядре
(`VhfCreate` живёт в `VhfKm.lib`), совместимых путей у Microsoft ровно два — прошивка устройства или
VHF-драйвер, — пользовательского API нет, поэтому самоподписанный драйвер в user mode не был вариантом ни
при каком решении о подписи.

**Что удалено.** Из `Dockerfile` — стадии `wdk-toolchain`, `driver-image`, `driver`, `rust-toolchain`,
`driver-rust-image`, `driver-rust`, аргументы `WDK_VERSION`, `KMDF_VERSION` и `RUST_VERSION`, строки
`driver:`, `driver-rust:`, `rust (Rust driver):` и `WDK:` в `PROVENANCE.txt`, копии `/driver` и
`/driver-rust` в стадии `artefacts`. Из `.github/workflows/build.yml` — шаг сборки драйвера (он же теперь
просто сборка приложения), имена `dist/driver/…` в проверке экспорта и шаг `Upload the driver package
(unsigned)`: upload-artifact в файле не осталось ни одного. Из `.dockerignore` и `.gitignore` — четыре
шаблона вывода сборки драйвера, из `.gitattributes` — абзац о переезде `driver/Dockerfile` в корневой
`Dockerfile`. И весь каталог `driver/`: 20 файлов под git плюс локальный `driver/AcerHelperLampArray/out/`.

**Чего это не касается.** Приложения под Linux, его публикации, AppImage и собственной подсветки клавиатуры
в приложении: драйвер публиковал зоны клавиатуры в Windows Dynamic Lighting как HID LampArray и не делал
ничего другого, путей через драйвер у подсветки приложения нет. Стадии `dotnet-base`, `app-linux` и
`artefacts`, таблица пинов, команда из «Быстрого старта» и раскладка `dist/linux` — без изменений.

**Проверено после удаления.** Сначала проверка фронтендом, `docker buildx build --call=check .` — «Check
complete, no warnings found»: висячих ссылок на стадии и аргументы не осталось. Затем одна сборка оставшейся
цели, `docker buildx build --target artefacts --output type=local,dest=dist .` — код возврата 0, в экспорте
`dist/linux/` (в том числе `AcerHelper`, 26 348 816 байт) и `dist/PROVENANCE.txt` (346 байт), и ничего
похожего на `dist/driver*` в нём нет. Задание `windows` в `.github/workflows/build.yml` не изменилось ни на
байт.

**Побочно измерено.** Строка `source:` в `PROVENANCE.txt` несёт `not`, а не `not recorded`: пробел в
значении по умолчанию у `ARG GIT_SHA=not recorded` фронтенд обрезает, и переменная получает только первое
слово. Строка в `Dockerfile` при этом не менялась — поведение досталось по наследству, и записано оно здесь
потому, что запись 2026-09-19 утверждает обратное («без неё там `not recorded`, что тоже проверено»), а
измерение этого не подтверждает: то же самое даёт минимальный `FROM alpine` с тем же `ARG`. В CI
`--build-arg GIT_SHA` передаёт хеш коммита, пробелов в нём нет, поэтому обрезка касается только значения по
умолчанию.
