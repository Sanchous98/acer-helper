# Сборка релиза в контейнере

Один многостадийный `Dockerfile` в корне репозитория собирает из коммита те артефакты, которые вообще
собираются на Linux: приложение под Linux (Native AOT, `net10.0`/`linux-x64`) и пакет драйвера. Ни
Visual Studio, ни установленного WDK, ни путей с машины сборки: источник — контекст сборки, то есть коммит.

Третий артефакт, приложение под Windows, в этот файл не входит — и это измеренный факт, а не пропуск:
тулчейн отказывается кросс-собирать его из Linux. Разбор с текстами ошибок — в разделе «Почему
Windows-артефакта нет в образе».

Этот файл — точка входа: команды, что где оказывается, что закреплено, что проверено, а что нет, и почему
подпись в контейнер не помещается.

## Стадии одного Dockerfile

| Стадия | Что это |
|---|---|
| `dotnet-base` | SDK 10.0.301 плюс предпосылки AOT: `clang-18`, `binutils` (`ld.bfd` и `objcopy`), `zlib1g-dev` |
| `app-linux` | сборщик: приложение под Linux → `/out/linux` |
| `wdk-toolchain` | Debian trixie + clang-cl/lld-link + WDK/SDK, распакованные из NuGet (перенесено из `driver/Dockerfile`) |
| `driver-image` | `wdk-toolchain` плюс `ENTRYPOINT` и `/src` — то есть образ драйвера, который описывает `driver/README.md` |
| `driver` | сборщик: драйвер, через неизменённый `driver/build.sh` → `/out` |
| `artefacts` | экспорт: пустая файловая система, в которой только `/linux`, `/driver`, `/PROVENANCE.txt` |

Общие стадии (`dotnet-base`, `wdk-toolchain`) существуют не для красоты: `apt-get` — самая дорогая часть
образа, и вторая стадия, которой понадобится тот же тулчейн, наследует его, а не ставит заново. `wdk-toolchain`
используют две стадии — образ драйвера и сборщик драйвера.

**`driver/Dockerfile` удалён, а не оставлен рядом.** Его содержимое перенесено в стадию `wdk-toolchain`
без изменений: тот же `debian:trixie-slim`, тот же `clang`/`lld`, те же три NuGet-пакета, та же
нормализация регистра заголовков, тот же `build.sh` по пути `/usr/local/bin/build-driver`. Оставить файл
значило бы держать пин версии WDK (`ARG WDK_VERSION=10.0.26100.6584`) в двух местах, а два пина одного
тулчейна расходятся — ровно тот дефект, от которого этот проект уже пострадал: драйвер, собранный против
KMDF новее объявленного в INF, не стартует на той ОС, которую INF называет. Поведение при этом сохранено
дословно: `driver-image` — тот же образ с тем же `ENTRYPOINT` и тем же монтированием `/src`, поэтому
документированный в `driver/README.md` сценарий меняет только первую строку (см. «Образ только для
драйвера» ниже).

## Быстрый старт

```bash
docker buildx build --target artefacts --output type=local,dest=dist .
```

`dist/` — BuildKit обязателен: `--output type=local` и кэш NuGet внутри образа без него не работают; в
Docker Desktop он включён по умолчанию.

| Путь | Что это |
|---|---|
| `dist/linux/` | каталог публикации: `AcerHelper` (нативный бинарник), `libSkiaSharp.so`, `libHarfBuzzSharp.so`, `.dbg` — то, что упаковывается в AppImage |
| `dist/driver/` | `AcerHelperLampArray.sys` (**неподписанный**), `.pdb`, `driver.obj`, `AcerHelperLampArray.inf` с подставленными вместо `$TOKENS$` значениями |
| `dist/PROVENANCE.txt` | версии SDK и clang, команда публикации, пин WDK, ревизия исходников (если передана) |

Ревизию исходников в провенанс кладут руками: `.git` в контекст не отправляется намеренно, поэтому взять
её изнутри неоткуда.

```bash
docker buildx build --target artefacts --output type=local,dest=dist --build-arg GIT_SHA=$(git rev-parse HEAD) .
```

Если BuildKit недоступен — сборка в образ и `create`+`cp`: у стадии экспорта внутри нет ничего, кроме
артефактов, поэтому копировать из неё безопасно.

```bash
docker build -t acerhelper-release:local --target artefacts .
docker create --name acerhelper-rel acerhelper-release:local
docker cp acerhelper-rel:/linux ./dist/
docker cp acerhelper-rel:/driver ./dist/
docker cp acerhelper-rel:/PROVENANCE.txt ./dist/
docker rm acerhelper-rel
```

### Образ только для драйвера

Стадия `driver-image` — это в точности то, чем был `driver/Dockerfile`: монтируете исходники в `/src`,
`ENTRYPOINT` собирает их, ничего больше знать не нужно.

```bash
docker build --target driver-image -t acerhelper-wdk .
docker run --rm -v "$PWD/driver/AcerHelperLampArray:/src" acerhelper-wdk
```

Переопределить версию KMDF по-прежнему можно: `KMDF_VERSION=1.35 docker run …` (скрипт читает переменную
из окружения), а для релизной стадии — `docker build --build-arg KMDF_VERSION=1.35 --target artefacts …`.

## Что именно запускается внутри

Образ не изобретает команд: он повторяет то, что уже делает CI, дословно — `.github/workflows/build.yml`,
задание `linux`:

```
dotnet publish AcerHelper.csproj -c Release -f net10.0 -r linux-x64 --self-contained true -p:PublishAot=true -o publish-linux
```

Отличий два, и оба только в стадии `app-linux`:

- добавлено `-p:CppCompilerAndLinker=clang-18`. `Microsoft.NETCore.Native.Unix.targets` по умолчанию
  называет компилятор безверсионным `clang` и ищет его через `command -v`; в образ ставится только
  `clang-18`, поэтому пин передаётся явно, а не подразумевается;
- выход публикации (`publish-linux`) копируется в `/out/linux`, потому что стадия экспорта пуста: иначе
  `--output type=local` выгружал бы на диск вызывающего образ SDK.

Драйвер собирается вызовом существующего скрипта, а не его пересказом: `OUT=/out
/usr/local/bin/build-driver /src`. Разбор путей WDK, выбор библиотек KMDF, `/imsvc`, подстановка токенов
INF — всё это решено в `driver/build.sh`, и вторая копия стала бы второй вещью, которую надо держать
правильной. `KMDF_VERSION` в стадию передаётся пустым, если вызывающий его не задал, а `build.sh` читает
пустое значение как незаданное — поэтому пин остаётся там, где он записан (в `build.sh`: 1.33, версия,
которая есть в Windows 11 22H2, то есть на полу INF), а в логе сборки всё равно печатается та версия,
которая в итоге разрешилась.

## Что закреплено

| Вход | Значение | Почему так |
|---|---|---|
| Frontend Dockerfile | `docker/dockerfile:1.7.1` | нужен для `--mount=type=cache`; теги `:1` и `:1.7` плавают, поэтому закреплён патч. Всё используемое поддерживается с 1.3, так что зеркало без 1.7.1 обойдётся любым более новым фронтендом |
| SDK | `mcr.microsoft.com/dotnet/sdk:10.0.301-noble` | 10.0.301 — версия, которой этот репозиторий собирается на машине владельца (`dotnet --list-sdks`) |
| Компилятор AOT | выводится из SDK | `Microsoft.DotNet.ILCompiler` подключается неявно (`KnownILCompilerPack`), поэтому в `AcerHelper.csproj` нет версии компилятора, и здесь её тоже нет: закреплён SDK — закреплён и компилятор |
| Компилятор Linux | `clang-18` | пакет закреплён по мажорной версии, а не отдан метапакету `clang` |
| Линкер и стриппер Linux | `binutils` | `LinkerFlavor` для linux по умолчанию `bfd`, то есть нужен `ld.bfd`; `objcopy` из того же пакета — запасной стриппер, который берётся, когда `llvm-objcopy` не найден |
| zlib | `zlib1g-dev` | нативные библиотеки рантайма линкуются с zlib; документированная строка предпосылок для Ubuntu — `apt-get install clang zlib1g-dev` |
| База драйвера | `debian:trixie-slim` | сохраняется намеренно: драйвер проверен именно на этом clang, и смена дистрибутива ради экономии слоя `apt-get` меняла бы решённую часть |
| Компилятор драйвера | `clang` и `lld` из `debian:trixie-slim` | перенесено из `driver/Dockerfile` без изменений, включая отсутствие версии в имени пакета: закреплён тег базового образа, а не мажор LLVM. Так этот тулчейн и был проверен — на нём собран `AcerHelperLampArray.sys`, разобранный в `driver/README.md` |
| WDK | `ARG WDK_VERSION=10.0.26100.6584` | 26100 — WDK Windows 11 24H2 (линия 28000.x — это Insider SDK). Единственное место, где эта версия записана |
| KMDF | `build.sh`, по умолчанию `1.33` | пин не дублируется в Dockerfile: 1.33 — версия, которая есть в Windows 11 22H2 (build 22621), а это пол, объявленный в `AcerHelperLampArray.inf`. Поднимать только вместе с полом INF |
| Пакеты NuGet | из `AcerHelper.csproj` | образ не добавляет, не заменяет и не переопределяет ни одной версии |

Чего пин **не** покрывает, и это стоит знать: `apt` внутри закреплённого тега всё равно отдаёт `clang-18`
той версии, которая лежит в архиве Ubuntu на момент сборки образа, — закреплено имя мажорной версии, не
конкретный патч. Тот же уровень строгости, что у прежнего образа драйвера. Полная воспроизводимость
потребовала бы `clang-18=<версия>` и снапшот-архива.

## Чего образ не делает

- **Не подписывает ничего.** Ни `.sys`, ни AppImage — как и CI. Подпись вынесена наружу, см. ниже.
- **Не собирает AppImage и MSI.** AppImage — упаковка `packaging/{AppRun,…}` поверх каталога публикации и
  `appimagetool --appimage-extract-and-run`; MSI — WiX поверх каталога публикации Windows. Оба шага
  остаются там, где описаны: `.github/workflows/build.yml` и `README.md`.
- **Не запускает тесты.** Прогон обоих TFM — отдельный гейт владельца, не шаг упаковки релиза.
- **Не берёт ничего с машины сборки.** Ни один путь не монтируется: источник — только контекст сборки.
  `bin/`, `obj/`, `driver/**/out` и `.git` из контекста исключены (`.dockerignore`).

## Подпись — вне контейнера

Контейнер отдаёт **неподписанный** пакет драйвера: `.sys` и INF, без `.cat`. Это граница возможного, а не
недоделка:

1. `signtool.exe` и `inf2cat.exe` — нативные Windows-бинарники; они лежат внутри тех же NuGet-пакетов
   WDK/SDK, которые распаковывает стадия `wdk-toolchain`, а запускаются на Windows. Именно этим занимается
   `driver/sign-test.ps1`: достаёт инструменты из образа, делает самоподписанный сертификат, собирает
   `.cat`, подписывает и `.cat`, и `.sys` (тестовая подпись требует выключенного Secure Boot).
2. Релизная подпись — **аттестация в Microsoft**, а не самоподпись: EV-сертификат подписи кода
   (~€250–400/год), аккаунт Partner Center для оборудования, `.cab` с пакетом, отправка на attestation
   signing, и в поставку идёт возвращённый `.cat`.
3. Ключ EV обязан жить на токене FIPS 140-2 или в облачном HSM. **В контейнер его не поместить ни в каком
   виде**: аппаратный токен — физическое устройство, которого у контейнера нет, а облачный HSM — это
   аутентифицированный сервис с политикой доступа, а не шаг сборки. Поэтому подпись — отдельный шаг вне
   контейнера, со своим носителем ключа, и образ эту границу не размывает.

Подробности и точные команды — `driver/README.md`, раздел *Signing*.

## Почему Windows-артефакта нет в образе

Это измеренный факт. Native AOT под `win-x64` из Linux запрещён тем самым тулчейном, который стадия
`dotnet-base` и ставит, причём несколькими независимыми способами:

- `Microsoft.NETCore.Native.Publish.targets` валит публикацию с `Cross-OS native compilation is not
  supported.` — условие покрывает оба направления, снять его можно только `DisableUnsupportedError=true`;
- там же: `Add a PackageReference for 'runtime.linux-x64.Microsoft.DotNet.ILCompiler' to allow
  cross-compilation`. Компилятор, который исполняется на хосте, и нативные библиотеки цели — **разные**
  пакеты, и назвать их можно только `PackageReference`, то есть правкой `AcerHelper.csproj`, чего эта
  задача делать не должна;
- `Microsoft.NETCore.Native.Windows.targets` жёстко задаёт `CppLinker=link`, запускает
  `findvcvarsall.bat` (batch-файл, то есть `cmd.exe`), чтобы найти тулсет, и при неудаче говорит прямо:
  `Platform linker not found. … Desktop Development for C++ workload in Visual Studio.`;
- библиотек для линковки из NuGet-пакетов берутся **не все**. Библиотеки Windows SDK — берутся: пятнадцать
  записей `SdkNativeLibrary` (kernel32, ole32, …), `ucrt.lib` из принудительного `/DEFAULTLIB:ucrt.lib` и
  `uuid.lib`, который требуют сами нативные библиотеки рантайма, есть в `microsoft.windows.sdk.cpp(.x64)`.
  А нативные библиотеки рантайм-пака несут `/DEFAULTLIB:LIBCMT`, `/DEFAULTLIB:libcpmt` и
  `/DEFAULTLIB:OLDNAMES` — это статический CRT MSVC, собственность Visual Studio, и ни в одном WDK/SDK
  NuGet-пакете его нет (измерено сканированием каталога `native/` пакета
  `Microsoft.NETCore.App.Runtime.NativeAOT.win-x64`).

Существуют обходы — `PublishAotCross`, `PublishAotCrossXWin`, `PublishAotCross.LinuxToWin`; все они
приносят либо `msvc-wine`, либо `xwin` (скачивание тулчейна VC с CDN Visual Studio), требуют
`DisableUnsupportedError`, шима для `CppCompilerAndLinker` (перевод MSVC-синтаксиса в `lld-link`) и
`PackageReference` в csproj. Это неподдерживаемая комбинация, собранная сторонним MSBuild-пакетом, и
сознательно **не** сделана: она противоречит и пину версий, и запрету на правку csproj, и правилу не
выдавать непроверенное за проверенное. Поэтому Windows-артефакт собирается там, где поддерживаемый
тулчейн существует, — на Windows-хосте, как это уже делает задание `windows` в
`.github/workflows/build.yml`.

**Альтернатива, если сборка нужна в контейнере и на той стороне** — Windows-контейнер: база
`mcr.microsoft.com/dotnet/sdk:10.0.301-windowsservercore-ltsc2022`, установка Visual Studio Build Tools
через bootstrapper канала (`aka.ms/vs/17/release/vs_buildtools.exe`) с компонентами
`Microsoft.VisualStudio.Component.VC.Tools.x86.x64` и компонентом Windows SDK, затем та же команда CI
(`-f net10.0-windows -r win-x64 --self-contained true -p:PublishAot=true -o publish`) без единой правки —
на Windows у тулчейна корректные умолчания, и именно поэтому файла с этим содержимым здесь нет: он
потребовал бы демона в режиме Windows-контейнеров, а пины внутри него (версия MSVC и Windows SDK из канала
Visual Studio) всё равно не закрепляются хешем — bootstrapper публикуется только по плавающей ссылке
канала, и вместо хеша там годится та же проверка, что у CI для `PawnIO_setup.exe`: валидная подпись
Authenticode от Microsoft.

## Что не проверено

**Docker не запускался ни разу.** Владелец не разрешал: движок не поднят, образы весят гигабайты. Всё
ниже подтверждается только первой сборкой, и ничто из этого не выдаётся за проверенное:

1. Что тег фронтенда `docker/dockerfile:1.7.1` разрешается.
2. Что тег `mcr.microsoft.com/dotnet/sdk:10.0.301-noble` существует и что в noble есть `clang-18`,
   `binutils`, `zlib1g-dev`.
3. Что `-p:CppCompilerAndLinker=clang-18` принимается и что линковка находит `objcopy` как запасной
   стриппер: это следует из целей ILCompiler 10.0.9, прочитанных на машине владельца, но не из прогона.
4. Что AOT-линковка под Linux не требует `libicu-dev`: документация Ubuntu для AOT перечисляет только
   `clang` и `zlib1g-dev`, а ICU грузится рантаймом через `dlopen`. Если линковка всё же назовёт символы
   ICU — добавляется `libicu-dev`, и это первое, что надо попробовать.
5. Что URL-схема flatcontainer NuGet и распаковка трёх пакетов работают как прежде: это перенесённый без
   изменений код прежнего `driver/Dockerfile`, но перенос не проверялся.
6. Что `driver/build.sh` внутри стадии находит всё, что ищет, и что `OUT=/out` не мешает подстановке
   токенов INF (скрипт читает INF из `$SRC`, пишет в `$OUT`). Проверка регистра заголовков выполняется на
   этапе сборки образа, а не сборки драйвера.
7. Что `--output type=local,dest=dist` даёт именно ту раскладку, что в таблице выше, и что стадия
   `artefacts` на пустой файловой системе экспортируется без сюрпризов.
8. Что `driver-image` действительно собирается и что `docker run` с монтированием `/src` ведёт себя как
   прежний образ. Это перенос, а не прогон.

Отдельно, и это не «не проверено», а свойство: **бинарник для Linux из этого образа и AppImage из релиза
— не одни и те же байты.** CI собирает AppImage в `fedora:41` (glibc 2.40), образ — на `noble` (glibc
2.39). Native AOT линкуется с glibc хоста сборки, поэтому каждый бинарник работает на своей или более
новой системе. Для «собрать локально и запустить у себя» это безразлично, для сверки хешей с релизом —
нет.
