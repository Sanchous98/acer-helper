# Карта контекстов и словарь

Документ фиксирует **слова, которыми в проекте называют вещи**, и то, где каждая вещь обязана жить.
Он не переименовывает типы: переименование без словаря — это churn по дереву, где инвариант «фичи не
меняются». Словарь нужен там, где одно слово сегодня значит разное, а разные слова — одно и то же.

**Проверяется машиной.** Первая колонка таблицы ниже — имя **существующего типа**; тест
`tests/AcerHelper.Tests/GlossaryTests.cs` читает этот файл и проверяет, что каждое имя резолвится в сборке.
Поэтому словарь не может сгнить: переименованный или удалённый тип красит набор. Вторая и третья
таблицы содержат слова **без типа**, и их первая колонка намеренно не в бэктиках — резолвить там нечего.

---

## 1. Типы

| Тип | Что значит | Слой |
|---|---|---|
| `PerformanceProfile` | Намерение пользователя: `Id` (непрозрачный ключ бэкенда) и `DisplayName`. **Не** аппаратный конверт мощности. Класс профиля и его цвета ушли с записи **2026-09-22** — см. ниже и `IProfileTraits` | Domain |
| `ProfileKind` | Грубый класс профиля. Управляет семантикой «переключить производительность»; им же вендорская таблица помечает свой режим | **Infrastructure** — было Domain, переезд **2026-09-22** (владелец: «Уехать в инфраструктуру») |
| `IProfileTraits` | Ответ **порта, который предлагает профили**, о своих же профилях: класс (`ProfileKind`) и цвета (`ProfileTraits`) каждого. Реализуется портом, а не читается с записи профиля | Infrastructure — рядом с `ProfileKind`; это то, что заменило поля на `PerformanceProfile` |
| `ModeKey` | Идентичность режима, под которой лежат пресеты. Тип выводит её из одного профиля (`For` — пресеты режима лежат под тем, в который переключились); флаг Turbo и слот источника добавляет слой, владеющий свитчем (`LaptopService.ModeKeyFor`). **Не валидирует**, что названный профиль существует | Infrastructure — ключ словаря, под которым лежат пресеты форм хранения |
| `ModeAxis` | Ось, у которой есть пресет на режим: кулеры, GPU-офсеты, CPU power, Curve Optimizer, подсветка | Domain |
| `ModeAxisTable` | Пять осей как **данные**: политика «пресета нет», волатильность, кто переприменяет | Domain |
| `EmptyAxisPolicy` | Что делать, когда у текущего режима нет пресета: оставить / выставить сток / унаследовать вид | Domain |
| `ReassertOwner` | Кто переприменяет ось после того, как платформа её забыла: железо или UI | Domain |
| `OffsetCounts` | Смещение Curve Optimizer в AVFS-«counts». Овервольт этим типом **непредставим** | Infrastructure — инвариант «только андервольт» про счётчики AVFS одного вендора |
| `Settings` | Граф настроек: `*Presets` по осям, слоты источников, скаляры. DTO хранилища | Infrastructure |
| `ProfileMemory` | Режим, запомненный за источником питания: база + флаг Turbo | Infrastructure |
| `FanPreset` | Пресет кулеров одного режима: режим + фиксированные скорости + две кривые | Infrastructure — форма хранения; домен её не читает с 2026-09-17, переезд выполнен 2026-09-18 |
| `GpuOcPreset` | GPU-офсеты одного режима, МГц (0 = сток) | Infrastructure |
| `CoPreset` | Смещения Curve Optimizer одного режима, по рельсам | Infrastructure |
| `LightPreset` | Подсветка одного режима, по зонам | Infrastructure |
| `LightSettings` | Состояние одной зоны: эффект, яркость, скорость, цвет | Infrastructure |
| `FanMode` | Поведение вентилятора: Auto / Max / Custom | Domain |
| `Fan` | Один вентилятор: свои данные (своя кривая или свой фиксированный ход) и последнее применённое к нему дежурство. **Кто он — не его дело**: флага CPU/GPU у модели нет, свою половину пресета выбирает вызывающий | Domain |
| `FanSettings` | Данные одного вентилятора, которыми снабжает его вызывающий: кривая, идти ли по ней или держать фиксированный ход, и сам фиксированный ход. Идентичности вентилятора в типе нет | Domain |
| `FanCurveEngine` | Пара вентиляторов и **парный** дедбенд: решает, писать ли вообще, и отдаёт обе скорости. Кривая, интерполяция и дежурство — в `Fan`; данные каждого вентилятора приходят с каждым `Step` | Domain |
| `SensorSnapshot` | Живая телеметрия температур и оборотов | Domain |
| `BatteryInfoSnapshot` | Живая телеметрия батареи | Domain |
| `AccentColor` | Нейтральный RGB-триплет без зависимости от тулкита | Domain |
| `ChoiceOption` | Один именованный вариант в списке, выбранный вендором | Domain |
| `RgbZone` | Зона подсветки: идентичность (`Name`), лампы, способы записи, «следует за профилем» | Domain |
| `VoltageDomain` | Независимо настраиваемый рельс напряжения: `Label` для показа, `Key` для хранения | Domain |
| `Device` | Подключённый ноутбук, **собранный фабрикой**: возможности — nullable-порты машины, `null` = фичи нет. Батарея — исключение: один объект `Battery`, который объявляет свои свойства сам. Раньше был интерфейсом `IDevice` в домене; стал моделью, которую наполняют бэкенды (`GenericDevice`/`AcerDevice`/`DellDevice`) | Infrastructure — модель этой машины и её инвентарь |
| `Battery` | Батарея этой машины: телеметрия и каждое из зарядных свойств по отдельности (`null` = свойства нет) | Domain |
| `ISettingsStore` | Портируемое хранилище графа настроек | Infrastructure — его сигнатура называет контейнер |

**2026-09-22 — класс профиля и его цвета больше не поля записи.** Строки выше правились по решению
владельца, и прежнее обоснование («класс профиля — доменный словарь») отменено, а не забыто: критерий
владельца — «только значения, важные для логики». Значение, которое домен только **несёт**, чтобы на него
посмотрел слой выше, — это значение, которого домен знать не должен. Замер: ни один файл под `Domain/` или
`Application/` не читал ни одного члена `ProfileKind`, а `Accent`/`FlashColor` читались только там, где
красились (иконка трея, сегмент профиля, палитра световой полосы). Класс уехал в Infrastructure вместе с
таблицей, которая на него отвечает (`IProfileTraits` — порт, предлагающий профили, классифицирует их же),
цвета остались в вендорских таблицах, где и были записаны. **`AccentColor` не переезжал и не переезжает**:
это payload записи подсветки, на нём домен действительно рассуждает. Держит новое правило
`tests/AcerHelper.Tests/DomainNeutralityTests.cs`; спор с прежним обоснованием — в `docs/domain-layering-map.md`.

## 2. Пять каналов «профиля» — самое опасное место словаря

Одно слово стоит перед пятью аппаратными реальностями, и **ни одно из вендорских понятий не получает
типа в Domain**: это была бы протечка ACL. Смежные понятия уже рассечены и закреплены тестом
`TheEcUsageModeIsNotTheProfileByte`.

| Слово | Что это на самом деле | Где |
|---|---|---|
| намерение пользователя | какой режим выбрал человек; несёт `PerformanceProfile` | Domain || индикатор прошивки | **значение** байта misc-setting 0x0B, `0x00`–`0x06`. Само `0x0B` — **индекс**, а не значение | `Infrastructure/Vendors/Acer/AcerProfiles.cs` |
| EC usage mode | то, что реально двигает конверт мощности. Достигается только по HID и ходит **противоположно** индикатору: Turbo — это байт 0x05, но usage mode 0 | `EneHidController`, `AcerEcHidController.ModeFor` |
| platform_profile | токен ядра/PPD на Linux: `low-power`, `quiet`, `balanced`, `balanced-performance`, `performance`. У Acer это **второй словарь тех же пяти режимов**: соответствие «токен ↔ байт EC» живёт в колонке `Choice` файла `AcerProfiles`, и там же ловушка — `performance` у Acer означает **Turbo** (`0x05`, 108 Вт), а Performance — это `balanced-performance` | `Infrastructure/Vendors/Generic/PowerProfiles.Linux.cs`, `Infrastructure/Vendors/Acer/AcerProfiles.cs` |
| power overlay | GUID слайдера ОС (Best efficiency / Balanced / Best performance) | `Infrastructure/Vendors/Generic/OverlayCpuPower.Windows.cs` |

**Запрещено** говорить «профиль» о чём-либо, кроме первого и четвёртого. Про каналы 2, 3 и 5 говорить
«индикатор», «EC usage mode» и «power overlay».

Четвёртый канал — единственный, у которого **две несовпадающие системы имён**, и это самое
опасное столкновение слов в проекте: пять режимов Acer называются по-разному на уровне железа
(байт EC) и на уровне ядра (токен). Перевод написан **один раз** — `AcerProfiles.ToChoiceName` /
`FromChoiceName`, двери между словарями, — и ни один вызывающий не имеет права сопоставлять эти
слова сам. Очевидный поиск по имени неверен в обе стороны: прочитать `performance` как
Performance — показать не тот режим и отправить в EC не тот конверт (93 Вт вместо 108), а записать
Performance, отправив токен `performance`, — попросить у ядра Turbo. Полная таблица, замеры и
причина, по которой у токенов не бывает id, — `docs/acer-linux.md`.

## 3. Слова без типа

| Слово | Значение | Почему без типа |
|---|---|---|
| триггер | Причина, по которой оси переприменяются: `Startup`, `ModeChanged`, `Resume`. Два из трёх — сброс состояния **платформы**, а не изменение модели | Доменного события смены режима нет и быть не может: домен про power-cycle не знает |
| каденция | Тайминг повторных попыток подсветки (400 мс × 8). Политика про руку пользователя и шину, не про железо | Живёт в UI намеренно |
| режим (без уточнения) | Запрещено. Говорить `ModeKey` (пресеты), `FanMode` (кулеры), EC usage mode или power overlay | Четыре разных понятия |

## 4. Граница, которую держит тест

`tests/AcerHelper.Tests/ArchitectureMapTests.cs` проверяет раскладку: namespace = папка, `*.Windows.cs` /
`*.Linux.cs` только под `Infrastructure/`, `Domain` не смотрит вверх, `Application` не называет
`Infrastructure`. Стрелка зависимости — **Infrastructure → Application → Domain**: инфраструктура
реализует то, что объявляет Application, а не наоборот.

Второй файл держит то, чего проверки `using`-ов не видят: **что домену позволено носить**.
`tests/AcerHelper.Tests/DomainNeutralityTests.cs` (добавлен **2026-09-22**) читает дерево как текст и
требует, чтобы `Domain/` не называл `ProfileKind` вовсе, а запись `PerformanceProfile` не несла цвета.
Нарушение здесь проходило сквозь все правила выше, потому что это была не стрелка зависимости, а **тип,
который домен нёс и не читал**. Краснеет он в том числе на строке, возвращающей прежнюю форму записи:
`public sealed record PerformanceProfile(string Id, string DisplayName, AccentColor? Accent = null);`.

Единственное разрешённое исключение — `Localization` для домена (общий кернел ниже него), и
**2026-09-18 оно перестало быть используемым**: контейнер настроек, ради которого домен его и тянул
(`AppLanguage` в `Settings`), уехал в инфраструктуру, поэтому сейчас ни один файл под `Domain/` не
импортирует вообще ничего. Разрешение в правиле намеренно **не сужено**: сужение было бы правкой
правила, сделанной попутно с переездом, а не решением о правиле.
