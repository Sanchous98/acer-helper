# План рефакторинга Acer Helper

Рабочий документ. Держит решения и порядок волн вне контекста одной сессии:
после компактификации достаточно перечитать этот файл.

**Номера строк здесь не поддерживаются (отмечено 2026-09-14).** Они писались
против ревизии, актуальной на момент каждого абзаца, и часть уже устарела —
в том числе из-за самого рефакторинга. Якорь — имя символа, а не число:
искать по имени. Что изменилось в дереве: `LaptopService` теперь шесть частичных
файлов `LaptopService*.cs` (в `Application/`), а `OptionsAssembler` переехал из
`UI/` в `Application/`. С 2026-09-15 namespace'ы совпадают с путями дословно —
см. «Целевая структура».

## Зачем

Две независимые проблемы, которые сейчас смешаны:

1. **Читаемость.** 12 461 строка C#, 23 % комментариев. Самые длинные блоки —
   археология железа (почему именно такой байт в SMU-мейлбоксе), которая
   уместна в `docs/`, а не в теле метода.
2. **Архитектура.** Слои существуют по дисциплине, а не по решению компилятора.

Механизм второй проблемы: `AcerHelper.Domain` / `.Application` / `.Infrastructure`
вложены в `AcerHelper`, поэтому **любой тип, объявленный в корневом `AcerHelper`,
виден всем слоям неявно**. Скрытая зависимость не видна ни в `using`-ах, ни в
грепе. Отсюда 91 примитив синхронизации в 22 файлах и разрастание фичи на 5–12
файлов.

**Вывод:** корневой namespace должен стать пустым. Это заставляет каждую
кросс-слойную ссылку иметь явный `using`, то есть делает зависимости
**явными и грепаемыми**.

Честная граница: это обеспечивает *явность*, но не *направление*. Ничто не
мешает `Infrastructure` добавить `using AcerHelper.Application;`. Физический
запрет требует отдельных сборок (4 `.csproj`) — отложено, Волна 1 даёт ~90 %
ценности за малую долю работы.

## Принцип: инвариант — фичи, а не форма кода

Приложение **функционально полностью рабочее**. Есть известные баги, их
сохранение допустимо. Инвариант: **после рефакторинга все фичи работают как
сейчас**. Форма кода при этом меняться может — архитектуру перекраивать можно.

Проблема в том, что «фичи сохранились» почти нечем проверить: логика
железозависимая, тестов на неё нет и без живого железа не будет. Поэтому вместо
проверки — **атомарность отката**:

- **один коммит на одно архитектурное изменение**; приложение собирается и
  запускается на каждом коммите;
- сломалась фича → виновник локализуется откатом одного коммита, а не разбором
  общего диффа на сотню файлов;
- тесты — там, где они возможны (чистая логика); на остальное не полагаться;
- изменения, которые нельзя оценить не запустив приложение (старт, смена языка,
  реакция на горячие клавиши), помечать в сообщении коммита явно.

Следствия для отдельных правок:

- Дефекты, которые **не проявлялись**, чиним попутно и отдельным коммитом:
  выигрыш ненаблюдаем, поэтому цена ошибки выше пользы. Записанные дефекты не
  теряются — они в `docs/hardware-actor-design.md` с точными строками.
- **Никаких «заодно почищу»**: каждое изменение должно откатываться в одиночку.

## Целевая структура

**Сделано 2026-09-15.** Правило: namespace выводится из **папки** — корневой
namespace плюс относительный путь, дословно. Исключений нет, «по слоям» больше
ничего не раскладывается.

Причина правки: до неё namespace'ы были выведены из **слоя**, а не из папки, и
это уже разъехалось — `Diagnostics/**` и `Composition/**` лежали в
`AcerHelper.Infrastructure.*`, а `Os/**` — в `AcerHelper.Os`; файлы же,
переехавшие в корень в Волне 1, остались без слоя. То есть таблица ниже не
описывала дерево, а задавала желаемое, и расхождение никто не проверял. Теперь
инвариант — `folder == namespace`, и он проверяем одной командой.

Почему это **сначала, а не после Волны 5**: правка трогает почти каждый `.cs`
(85 переименований), а правки Волны 5 в `LaptopService.*` ещё не начаты. Сделав
её первой, диффы Волны 5 остаются чистыми — иначе каждый из них тянул бы за
собой переезд.

Namespace **не выводится из имени файла**: проект разделяет платформы по суффиксу
(`*.Windows.cs` / `*.Linux.cs`) через `<Compile Remove>`, и попадание суффикса в
namespace сломало бы это разделение.

Отсюда же — **правило для частей `LaptopService.*.cs`**: их суффиксы (`.Profiles`,
`.Tuning`, `.Fans`, `.Lighting`, `.Toggles`) выбраны так, чтобы не совпасть ни с
`*.Windows.cs`, ни с `*.Linux.cs`. Переименование любой части в такой суффикс
молча выкинуло бы её из одной из двух сборок — то есть из компиляции исчезла бы
часть класса, а вторая TFM осталась бы зелёной. Это единственная причина, по
которой имена частей не совпадают с именами фич.

| Папка | Namespace |
|---|---|
| `Domain/**` | `AcerHelper.Domain` |
| `Application/**` | `AcerHelper.Application` |
| `Infrastructure/**` (сама папка) | `AcerHelper.Infrastructure` |
| `Infrastructure/Composition/**` | `AcerHelper.Infrastructure.Composition` |
| `Infrastructure/Diagnostics/**` | `AcerHelper.Infrastructure.Diagnostics` |
| `Infrastructure/Vendors/{Acer,Dell,Generic}/**` | `AcerHelper.Infrastructure.Vendors.**` |
| `Bootstrap/**` | `AcerHelper.Bootstrap` |
| `UI/**` | `AcerHelper.UI.**` — **без изменений** |
| `Localization/**` | `AcerHelper.Localization` — **без изменений** |

Корень `AcerHelper` теперь пуст: в нём не объявлено ни одного типа, и это то,
ради чего Волна 1 существовала. Тесты (`tests/AcerHelper.Tests`, namespace
`AcerHelper.Tests`) — единственное место, где папка и namespace расходятся по
регистру `T`; это стандартная раскладка `tests/<ProjectName>/`, и трогать её
незачем.

### Следствие, которое стоит назвать

`Vendors/Generic/**` — это бывшая папка `Os/`: **сервисы на стандартных API ОС**
(power-mode overlay, гамма, автостарт, clamshell, hwmon). Они попали под
`Vendors/`, потому что их namespace уже был `AcerHelper.Infrastructure.Vendors.Generic`
и переезд делался «файлы к namespace'ам», а не наоборот. Читается это странно:
«vendor», у которого вендор — операционная система.

Это принято сознательно, а не проглядено. Обратный вариант (папка `Os/` +
namespace `AcerHelper.Infrastructure.Os`) означал бы переименование namespace у 36
файлов и правку всех `using` — то есть ровно тот дифф, который эта правка
убирала. Если название начнёт мешать, это отдельный коммит «`Generic/` → `Os/`»,
и он же — единственный случай, когда переезд папки оправдан. Функционально оба
варианта эквивалентны, поэтому решено не платить сейчас.

### Отклонено: `UI/ → AcerHelper.Presentation`

`AcerHelper.UI.*` и `AcerHelper.Localization` уже существуют как под-namespace'ы,
и на них ссылаются ~40 `.axaml` через `x:Class` / `clr-namespace`. Для опустошения
корня их переименование **не требуется** — они и так не корень, а после правки
2026-09-15 ещё и совпадают с путём дословно. То есть это ~80 правок XAML, каждая
из которых может сломать компилируемые биндинги
(`AvaloniaUseCompiledBindingsByDefault=true`), ради нулевого выигрыша в изоляции.
Косметика не стоит риска.


## Ворота проверки

**Ворота — сборка плюс тесты, и это изменилось по ходу работы.** Изначально
поведенческих тестов не было, и единственными воротами была сборка. Затем появился
проект тестов (`7dcf6b4`) и покрытие `LaptopService`; сейчас ворота такие: обе TFM

старте было 268, сейчас 454+ (точное число — в журнале). «Предупреждения были и
раньше» не принимается: базовая линия — ноль, и она держится.

Две ловушки, дававшие здесь **ложную зелень**:

- `dotnet test --no-build` после пересборки одного приложения прогоняет **старую**
  копию сборки из выходной папки проекта тестов. Тесты обязаны пересобираться сами:
  `--no-build` не использовать.
- «Агент сказал, что зелено» — не проверка. Пересобирать и перезапускать самому.
- **Одна проба — не доказательство.** Проба «`Dispatcher.UIThread.RunJobs(null)`
  работает из голого xUnit-процесса» прошла **и была ложной зеленью**: диспетчер

  процесс-глобальному объекту, обязано проверяться **в том же составе**, в котором

## Волны

### Волна 1 — Границы *(сделана — `1a7a570`)*

Трогает все `.cs`, поэтому строго последовательна.

1. `AcerHelper.csproj`: генератор `AppInfo` (target `GenerateAppVersion`, ~строка 114)
   перевести на `namespace AcerHelper.Domain%3B`.
2. Миграция объявлений namespace по таблице выше.
3. Миграция `using`-директив.
4. Сборка обеих TFM → ошибки «type not found» **и есть список скрытых
   зависимостей**, которые до этого маскировались вложенностью. Известный пример:
   `Domain/FanCurveEngine.cs` использует `FanPreset` (объявлен в `Settings.cs`)
   без `using`.

Только namespace и using. Ни одной правки логики, форматирования или тела
комментария. Нарушения слоёв (например `Domain` → `Infrastructure`) — сообщать,
не чинить: это следующая волна.

Осложнение, обнаруженное на практике: миграция **не сводится к правке
`using`-директив** — в коде есть полностью квалифицированные inline-ссылки и
alias-`using` (`using X = ...;`). Плюс появляется риск CS0104 (неоднозначность),
когда два слоя экспонируют одноимённый тип; лечится полной квалификацией или
алиасом, но не удалением и не переименованием публичного типа.

### Волна 2 — Тесты и декомпозиция *(тесты сделаны — `7dcf6b4`; остальное в работе)*

Сеть безопасности.

- Отдельный проект тестов + `<Compile Remove="tests/**" />` в `.csproj`.
  Без этой строки неявный glob `**/*.cs` SDK скомпилирует тесты внутрь
  приложения.
- Целиться туда, где отказ **молчаливый**: `FanCurveEngine.EvalCurve`
  (якоря `[50,60,70,80,90]`, дефолтная кривая `[30,45,60,80,100]`, дедбенд 4),
  `Encode`/`CoreArg`/`GpuMargin` (20-битная форма `-5` у CPU это `0xFFFFB`, у
  GPU `0xFFFB` — мейлбокс принимает обе молча, означая разное),
  `LaptopService.NextSelectable`, `ParseBstr`/`ToU64`.
- `ModePresets<T>` → `GetOrAdd<T>` — **сделано в `a39bfb5`, и число в плане было
  неверным: повторов пять, а не двенадцать.** Настоящий идиом
  (`TryGetValue` + вставка созданного) нашёлся в `StoredFan`,
  `LightsForCurrentMode`, `EnsureLightZone`, `StoredGpuOc`, `StoredCo`. Остальные
  семь адресов из плана — **другая форма, и сворачивать их значило бы менять
  поведение:**
  - `CurrentFan`, `CurrentGpuOc`, `CurrentCo`, `ApplyModeCo` создают значение по
    умолчанию, но **не сохраняют** его (в документации прямо «not stored»:
    чтение не должно менять настройки). `GetOrAdd` вставил бы пресет при каждом
    чтении;
  - `CurrentCpuPower`, `ApplyModeCpuPower` — `Dictionary<string,string>`, где
    `new()` не существует вовсе; обе только ищут и падают на живое чтение железа;
  - `ApplyModeFan`, `ApplyCustom` используют `TryGetValue` как **сторож**, где
    «пресета для режима нет» — значимый результат.

  Это тот случай, когда послушное исполнение плана внесло бы восемь ошибок:
  ошибка была в плане, а не в работе. Проверено построчно мной: идиом в пяти
  местах идентичен, `CurrentModeKey()` по-прежнему вызывается ровно один раз до
  поиска, покрытие блокировок не изменилось (33 `lock (_state)` до и после).
  Тесты `LaptopService` не покрывают, поэтому зелёный гейт доказывает
  компилируемость, а не сохранение поведения — здесь работает именно построчная
  сверка.
- **Декомпозиция `LaptopService` — раскол сделан (`0fe97ca`, `6f92842`), вынос
  в классы-контроллеры ОТЛОЖЕН.** Файл был 814 строк и 57 публичных членов при
  38 вхождениях `lock (_state)`; теперь это шесть partial-частей по фичам
  (главная = тождество + общая инфраструктура, Lighting, Profiles, Fans, Tuning,
  Toggles). Число в плане (758 строк / 33 блокировки) устарело ещё до правок
  корректности — верные числа на момент раскола: 814 строк, 38 вхождений.
  - **Что разблокировало раскол:** параметры primary-конструктора видны только в
    объявляющей partial-части. Пока он в силе, `partial` невозможен; `0fe97ca`
    заменил его явными полями, сохранив имена, поэтому ни один вызов не
    сдвинулся, а диф — конструктор плюс одно присваивание.
  - **Почему раскол безопасен и как это проверено.** Блоки нарезаны из исходника
    по номерам строк, а не перепечатаны; конкатенация блоков в исходном порядке
    воспроизводит тело строка-в-строку; каждый новый файл равен своим блокам в их
    порядке (6/6); мультимножество непустых строк тела совпало с исходным. В
    диффе главного файла 19 добавленных строк — все документация и объявление
    класса. Экземпляр `_state` и его покрытие те же, поэтому контракт блокировок
    из комментария в главной части не изменился: изменилась только достижимость
    поля. Это ровно та техника, которую план и предписывал («не заводить каждому
    контроллеру свой лок»), доведённая до конца в той части, которая проверяема.
  - **Что отложено и почему.** Настоящие классы-контроллеры требуют общего
    объекта-держателя, а он упирается в две вещи, которые тестами не
    проверяются: `LastError` — **изменяемый** канал ошибок, который пишут почти
    все методы и читает UI, поэтому у каждого контроллера должна быть ссылка на
    один и тот же экземпляр, иначе ошибки молча теряются; и тождество самого
    `_state`. Промах здесь ломает ровно то, что план называет главным, —
    фичи, — и ловится только на железе, которого у меня нет. Части по фичам дают
    тот же выигрыш в читаемости, но доказуемо нейтральны. Отдельный коммит,
    когда будет человек за экраном.
  - **Ловушка имён, записанная в коде:** суффиксы `.Profiles.cs` и т. п. выбраны
    так, чтобы не столкнуться с `*.Windows.cs`/`*.Linux.cs`, по которым
    `.csproj` выбирает файлы под TFM. Переименование любого из этих файлов в
    такой суффикс молча выкинуло бы часть класса из одной из сборок.

**Правки корректности.** Незаблокированные чтения закрываются **не снимком** —
снимок вместо живой ссылки молча ломает любой путь, который пишет через неё, —
а узкими доступами под блокировкой плюс сужением публичной поверхности
`LaptopService`. Область захвата сокращается осторожно: не держать блокировку
через обращение к железу, не меняя при этом, **что именно** она охраняет.
Отдельный коммит на каждое изменение, чтобы откат был точечным.

  блокировка отпускается, и ссылка разыменовывается уже без неё.**

  | то же | `ApplyModeCo` | то же |

  авто-свойства, заполняемые в конструкторе (`RyzenCurveOptimizer.Windows.cs:187`),

  **Публичная граница не меняется.** Живые ссылки, уходящие наружу (`CurrentCo()`,

  — ровно та ловушка, о которой предупреждает раздел о снимках выше.

  **Сделано в `303beca`.** Все пять закрыты одним приёмом: значения копируются
  под блокировкой, вызов порта остаётся снаружи. Блокировок 36 → 38 — ровно два
  новых оператора (`CurrentCoDomains`, `ApplyModeGpuOc`); `ApplyModeCo`
  переиспользует свой блок, `LaptopService.cs` `ApplyStartupState` — свой. Дифф сверен построчно: **ни один**
  вызов порта (`SetDomains`, `Set`, `GpuOverclock?.Set`) внутрь блокировки не
  переехал, то есть D17 не заведён. Чтение `co.Domains` под блокировкой I/O не
  добавляет — это get-only список дескрипторов из конструктора порта.
  **Доказательство сохранения поведения, а не компилируемости:** 186 тестов
  написаны против кода **до** правки (`21b7bf1`, `7b9155d`), и все 454 проходят
  после неё.

- **`CurrentModeKey()` делает EC-чтение и вызывается из-под `_state`.** Это
  наблюдение шире правки выше и **не** ею заведено: `CurrentModeKey()` (`LaptopService.Profiles.cs`)
  вызывает `device.PowerProfiles?.Current()`, а его собственная документация
  (`LaptopService.Profiles.cs` `CurrentModeKey`) называет это EC-round-trip. Аргумент `TryGetValue(CurrentModeKey(),
  …)` вычисляется **внутри** `lock`, поэтому `CurrentGpuOc`, `CurrentCo`,
  `CurrentFan`, `SetGpuOc` и соседи держат `_state` поверх обращения к железу —
  причём в самом частом пути, а не в экзотическом. Перечень D17 в
  дизайн-документе (`ApplyCustom`, `ApplyStartupState`, `SetGpuOc`) этой широты
  не передаёт. Не моя правка и не на эту ночь: сокращение области захвата здесь
  и есть предмет отложенных Волн 5–6.

- **Четыре находки тестов Curve Optimizer — оставлены как есть.** Все четыре
  **недостижимы из поставляемого UI**, поэтому записаны, а не починены: правка
  недостижимого пути непроверяема, а правило здесь — «фичи важнее».
  `SetCo` пишет значение **без клампа** и возвращает `false`, когда порта нет,
  тогда как `SetCoDomains` отказывает **до** записи — там кламп стоит внутри
  `if (co != null)`, то есть сторожит не тот путь, ради которого написан;
  `SetCoDomains([])` на CPU без доменов проходит мимо проверки `0 != 0`,
  вставляет пресет и тем **навсегда разоружает** намеренную защиту
  `ApplyModeCo` «пустое хранилище → не трогать SMU» (`LaptopService.Tuning.cs`);
  `ApplyModeCpuPower` отдаёт `null` для **настроенного** режима, когда порта нет,
  в отличие от `ApplyModeGpuOc`/`ApplyModeCo`, которые возвращают сохранённый
  пресет; `SetCo` возвращает `false` для «нет порта», не выставив `LastError`.

- **`LastError` — план был неверен, правка ОТМЕНЕНА; решение за владельцем.**
  Отдельный разбор (2026-09-14) опроверг и список, и лекарство.
  **Список был не тот.** В плане стояло «четыре», перечислялось семь, а
  кросс-поточно читается вообще другое. Проверено мной по дереву:
  `AcerEcHidController.LastError` не читает **никто** (все ссылки на класс —
  объявления, конструктор и partial-заголовки; ни одного `_ec.LastError`) — это
  мёртвое поле, а не гонка; пять полей `DelegatePorts` пишутся и читаются на
  **одном** потоке (`HwSerial`-продолжение, у каждой строки свой экземпляр
  порта); у `LampArrayBridge` запись воркера и чтение не пересекаются, потому что
  воркер живёт только между успешным `Enable` и своим выходом, а `Enable` при
  живом воркере выходит сразу (`if (Enabled) return true`).
  **Единственное поле, читаемое кросс-поточно, — `LaptopService.LastError`**
  (`AppController` — в `ApplyProfile`, `SetTurbo`, `SetGpuOc`, `SetCpuPower`, `SetCo`; `OptionsAssembler.cs` `RunSet`), и `_state`
  тут не помогает: **ни один читатель его не берёт**, а блокировка упорядочивает
  потоки только когда её берут обе стороны. Запись идёт и с UI (`LaptopService.Profiles.cs` `ApplyProfile`, `SetTurbo`), и с
  фонового прохода (`LaptopService.Fans.cs` `ApplyFan`), и с пул-задач (`LaptopService.Tuning.cs` `SetCo`, `SetCoDomains` — в том числе
  из `ApplyModeCo`, который `LaptopService.cs` `ApplyStartupState` намеренно пускает мимо `_state`).
  **`volatile` — неверное лекарство, а не недостаточное.** К свойству его
  применить нельзя вовсе (нужно переписывать в backing-поле), а на x64 он не
  меняет ничего наблюдаемого: запись и чтение одного адреса из одного потока не
  переупорядочиваются, так что читатель и так видит минимум собственную запись.
  Все шесть найденных гонок — вида «читатель подхватил ошибку **чужого** вызова»;
  `volatile` делает это **детерминированнее**, а не реже, потому что гарантирует
  видимость самой свежей записи, в том числе чужой.
  **Правильная правка — убрать побочный канал, а не расширять его видимость:**
  вернуть ошибку из вызова (`SetCpuPower(...)` → `(bool ok, string? error)`),
  тогда общего поля не остаётся. Объём: ~8 сигнатур, ~10 мест вызова плюс
  плумбинг делегатов в `UiActions`/`OptionsAssembler`.
  **Почему не сделано этой ночью.** Симптом гонки косметический (неверный текст
  ошибки при окне в несколько инструкций), а цена ошибки в самой правке —
  «ошибка перестала показываться», то есть молчаливая регрессия ровно там, куда
  моя проверка не достаёт: тесты покрывают `FanCurveEngine`, конверсию WMI и
  кодирование SMU, но **не путь сообщений об ошибке в UI**, а железа у меня нет.
  По принципу «инвариант — фичи» такая правка помечается, а не делается вслепую.
  **Рекомендация владельцу:** делать, отдельным коммитом, с проверкой глазами,
  что все шесть сообщений об отказе по-прежнему показываются.
- **НЕ в этой волне:** снятие блокировки UI-потока на EC-`Gate` в `BuildUi`
  (`AppController.cs:134-173`) — вынесено в отдельную Волну 6. Причина: меняет
  поведение при старте (`:63`) и при **каждой смене языка** (`:198`) — это живой

  зафиксирован: 6–10 сериализованных WMI-транзакций, обычно 10–50 мс, но
  **неограниченно** при зависшем EC — то есть ровно тот столл, ради выживания

### Волна 5 — Hardware actor — ОТЛОЖЕНА (решение от 2026-09-14); критерий пересмотра — ниже

Дизайн **готов и не выбрасывается**: `docs/hardware-actor-design.md` (679 строк) —
инвентаризация 137 мест синхронизации в 22 файлах, инвентаризация потоков,
10 рисков и инкрементальный порядок из 8 шагов, каждый из которых собирается и
откатывается отдельно.

Решение — **не делать сейчас**. Обоснование получено независимым анализом:

- Подтверждённые дефекты актора не требуют: это незаблокированные чтения и
  свойства без `volatile`. Их правки перенесены в Волну 2 и дают ~90 % ценности
  за дюжину строк. Актор даёт **читаемость, а не корректность**, и его список
  рисков длиннее и тяжелее списка дефектов, которые он убирает.
- `WmiSession.Gate` — это **уже почти актор**, и лучшее по качеству конкурентное
  место в дереве: одна статическая реентерабельная блокировка, одна EC-транзакция
  за раз, с выписанным рассуждением об интерливингах. Для EC-пути актор —
  движение вбок.
- Проблема не в сериализации, а в **приоритете**: `BuildUi` блокирует UI-поток на
  EC-`Gate`, и это лечится правилом приоритета и таймаутом на существующих местах
  вызова, а не переписыванием модели конкурентности.

**Ограничения, которые обязаны пережить любые будущие правки** — иначе актор
сделают неправильно:

- Два HID-`Gate` (`EneHidController`, `AcerEcHidController`) — это **сглаживание
  темпа и коалесинг, а не сериализация**. Втягивание их в один актор поставит
  10-мс-размеренные записи за 5-секундным ожиданием SMU-мейлбокса. **53
  примитива обязаны остаться снаружи.**
- **2 примитива межпроцессные** и актором не заменяются в принципе:
  `Global\Access_PCI` (`RyzenCurveOptimizer.Windows.cs:137`, держится на всей
  транзакции `:410-448`) и мьютекс единственного экземпляра (`Program.cs:11`).
  Плюс 4 межприложенческие точки координации вне области: драйвер PawnIO, узел
  устройства LampArray (другие процессы пишут туда кадры), SMU-мейлбокс на
  кристалле, доставка `SystemEvents`/`RegisterPowerSettingNotification`.

**Пересматривать только по замерам**, не по вкусу: шаг 0 дизайна —
инструментировать ожидания на `Gate`, чтобы решение опиралось на числа.

**Шаг 0 сделан — `4ba84cf`.** `Infrastructure/Diagnostics/GateStats.cs` (без суффикса платформы;
на Linux счётчики остаются нулевыми, `WmiSession` там нет) считает захваты,
суммарное и максимальное ожидание, удержание и «стойла» (удержание > 50 мс) в
двух корзинах — пул и не-пул (`IsThreadPoolThread`). Инструментированы оба
`lock (Gate)` в `Infrastructure/Vendors/Generic/WmiSession.Windows.cs`; вложенный захват
(`InvokeMethod` → `QueryFirst`, реентерабельный) считается один раз — флаг
`[ThreadStatic]`, образец принадлежит внешней области, иначе одна EC-транзакция
дала бы два числа. `AppController` снимает дельту не-пуловой корзины вокруг
`ApplyStartupState` и `BuildUi`: это «до» для Волны 6, и это время,
**заблокированное на EC**, а не стенное. Строка дописывается в
`%AppData%\AcerHelper\gate-stats.log` раз в минуту (на таймере самого опроса) и
в `ExitApp` — периодическая запись нужна потому, что убитый процесс до `ExitApp`
не доживёт, а интересна именно живая сессия. Счётчики **всегда включены**, не под
`#if DEBUG`: замеры обязаны идти с той сборки, которой пользуется владелец.

**Критерий решения зафиксирован ДО замеров** — чтобы «пересмотреть по замерам»
не превратилось в «пересмотреть по вкусу, приложив замеры». Волна 5 делается,
если подтвердится хотя бы одно:

| # | наблюдение | почему это довод за актора |
|---|---|---|
| 1 | ожидание `Gate` на UI-потоке регулярно > 100 мс | 10-50 мс терпимо (D16), сотни — нет |
| 2 | заметная доля транзакций ушла в стойло EC (> 50 мс удержания) | тогда очередь всё равно одна, и отсрочка чтений не спасает |
| 3 | проход опроса выдаёт много транзакций подряд, UI-чтение вклинивается редко | линия приоритета — настоящая потребность |

Если ни одно не подтвердится — Волна 6 закрывает вопрос, актор не делается, и
это тоже записывается как решение с обоснованием, а не остаётся висеть.

**Состояние решения (2026-09-14, после Волны 6): замеров нет, вопрос открыт —
но он сузился до критерия 2.** Это надо записать точно, потому что «нет чисел»
легко прочитать и как «критерий не сработал».

**Чисел не собрано.** `%AppData%\AcerHelper\gate-stats.log` не существует:
инструментированная сборка (`4ba84cf`) на машине владельца **ни разу не
запускалась**. Лог пишется и по таймеру опроса, и в `ExitApp`, так что отсутствие
файла — это «не запускалась», а не «не дожила до записи». То есть вопрос
«оправдан ли актор» по-прежнему не имеет ответа, и **никакого решения «актор не
нужен» здесь не записывается** — записывается, что мерить ещё нечем.

Почему не запустил сам: запуск приложения на живой машине владельца — это не
измерение, а управление железом. Оно регистрирует автозапуск на путь отладочной
сборки, перезаписывает `settings.json` и начинает вести вентиляторы по кривой
текущего режима. Ничего из этого нельзя делать без человека за экраном, и ничего
из этого не требуется для критерия: шаг 0 и был задуман как замер **его** сессии,
а не моей.

**Что Волна 6 всё же даёт решению, не прибегая к числам.** Критерии 1 и 3
сформулированы про **чтения UI-потока**, встающие в очередь за опросом. После
шагов 1–4 UI-поток на пути сборки UI не выпускает больше ни одной пачки чтений, и
это не оценка, а перечень. Весь путь старта стоит теперь **двух** транзакций
`Gate`:

1. чтение текущего профиля — то, что шаг 4 поднял **выше** `BuildUi`, так что оно
   одно на весь путь вместо трёх;
2. чтение яркости читаемой RGB-зоны в конструкторе `LightViewModel` — по одному на
   зону, и это то самое чтение, которое шаг 2 **намеренно** не тронул: его значение
   уходит в стартовый ре-апплай, и отсрочить его вместе с записью — видимое
   железом изменение.

Всё остальное в `BuildUi` — проверено по каждому вызову, а не на глаз: строки
опций и батареи строятся плейсхолдерами с `Read`-делегатами (Ворота 1),
`CurrentFan`/`CurrentGpuOc`/`CurrentCoDomains`/`SourceProfile`/`TurboToggles`/
`GetDeviceFlag` читают только граф `Settings`, а `Modes`/`Domains`/`BatteryInfo` —
это свойства портов, построенные в их конструкторах. Плюс ушло пятисекундное
ожидание `schtasks.exe` на строке автостарта.

То есть линия приоритета (критерий 3) осталась бы арбитром между опросом и
**двумя** чтениями на старте — покупать ей нечего; а критерий 1 в его исходной
форме («регулярно > 100 мс») описывал именно ту пачку чтений, которой больше нет.
Оба — следствие структуры, видимое чтением кода, и оба **проверяемы теми же
воротами**, что уже стоят (Ворота 1: сборка строк не трогает ни одного порта).

**Критерий 2 Волна 6 не задела вовсе.** «Заметная доля транзакций ушла в стойло
EC (> 50 мс)» — это свойство самого EC: держит ли он замок на десятки
миллисекунд. Отсрочка чтений от этого не спасает (план и говорит это в таблице
прямо), и именно поэтому критерий 2 — единственный, что остался доводом за
актора. Мерить его надо там же: `hold_pool_stalls` и `hold_pool_max_ms` в
`gate-stats.log`, плюс `tx_pool` за тот же интервал для доли.

**Как получить числа** (одна сессия, ничего запускать не нужно отдельно — счётчики
всегда включены, не под `#if DEBUG`):

1. собрать и запустить текущее дерево обычным для владельца способом (или
   обновиться на свежий publish) — числа обязаны идти с той сборки, которой он
   пользуется, включая запуск на входе в систему;
2. поработать несколько минут как обычно (строка дописывается раз в минуту, так
   что двух-трёх хватает) и выйти;
3. посмотреть `%AppData%\AcerHelper\gate-stats.log` — строки кумулятивные, интересна
   последняя.

Читать так: `startup_hw_ms` обязан быть ~0 (это проверка утверждения «в
`ApplyStartupState` нет ни одной `Gate`-транзакции» — если он не ноль,
утверждение неверно и волну надо продолжать); `build_hw_ms` — «после» для Волны 6
против `startup_hw_ms`-подобного «до», которого уже не снять; `wait_ui_max_ms` —
критерий 1 на остатке; `hold_pool_stalls` / `tx_pool` — критерий 2.

Порядок, который из этого следует: **решение по актору — после одного запуска на
машине владельца**, и оно может закрыться как «нет» (если стойл мало и `wait_ui`
мал), так и «да» (если доля стойл заметна) — что и есть то, ради чего критерий
фиксировался заранее. Отдельная ветка, которая от этих чисел не зависит вовсе:
**UI-потоковые ЗАПИСИ** (`ApplyProfile`/`SetFan`/`SetTurbo`) — записаны в «вне
области» выше как настоящее, но это изменение поведения, и они не чтения
`BuildUi`, ради которых волна затевалась.

**Риски, которые не закрываются тестами в принципе** — важно для честных
ожиданий от Волны 2: мок-транспорт не проверяет потерянный ре-апплай (Curve
Optimizer / GPU OC / CPU power), гонку владения LampArray и PCI-мьютекс.
Волны 2→5 оставляют эти решения проверяемыми только на живом железе — то есть
там же, где они сейчас. Тесты повышают надёжность, но не превращают переписку
модели конкурентности в безопасную.

#### Шаг 5 сделан частично — по запросу владельца, поверх открытого решения

Владелец попросил «и волну 5», не дожидаясь замеров. Это **отменяет порядок**
(«решение — после одного запуска»), но не отменяет сами числа, поэтому шаг
берётся ровно тот, который дизайн-документ сам называет стоящим **даже если
остальное брошено**: его шаг 5 — «снять аппаратные вызовы из-под G2 и заменить
`public Settings Settings { get; }`». Шаги 1–4 и 6–8 (сам актор) **не начаты**, и
решение по ним остаётся открытым: этот шаг ничего про критерий 2 не говорит.

**Сделано:**

1. **`LaptopService.Settings` → `internal`** — и записано честно, что это
   **указатель, а не забор**. Проект — **одна сборка** (`AcerHelper.csproj`
   компилирует `Domain/`, `Application/`, `Infrastructure/`, `UI/`, `Bootstrap/`
   вместе), поэтому `internal` виден всем им и внутри репозитория не запрещает
   ничего. Что он даёт: убирает свойство с публичной поверхности (перестаёт быть
   приглашением — именно так возникли D1–D5) и делает будущий раскол на сборки —
   единственное, что **действительно** провело бы границу слоя, — механическим.
   Что не даёт: не компилятор. Проверка «`Settings` вне `Application/` — 0»
   остаётся **грепом** (`grep -rn '\.Settings\b' Domain/ Infrastructure/ UI/`),
   а не воротами сборки. По дороге нашлась и починена одна настоящая читалка:
   `UI/App.axaml.cs` читал `service.Settings.Language` — теперь `service.Language`
   (под замком, свойство для этого уже существовало).

   **Дверь, которую это не закрывает** (и она шире, чем кажется):
   восемь аксессоров отдают **живую** ссылку внутрь графа — `CurrentFan`,
   `ApplyModeFan`, `CurrentGpuOc`, `ApplyModeGpuOc`, `CurrentCo`, `ApplyModeCo`,
   обе формы `LightsForCurrentMode` и `EnsureLightZone`. Самая широкая —
   световая: `LightingViewModel` **держит возвращённый словарь и пишет в него
   на месте**. Закрыть их значит возвращать копии, а это переделка светового
   пути (там запись в граф и есть фича, `EnsureLightZone` — её структурная
   часть), а не правка видимости. Записать, не чинить.

2. **`ApplyStartupState`: значения — под замком, четыре вызова — снаружи.**
   Метод вызывается ровно из одного места (`AppController`, конструктор, UI-поток)
   и держал `_state` через четыре аппаратных вызова (два powrprof, gdi32, NvAPI) —
   это D17, и его называет шаг 5. Теперь читаются три скаляра под замком, а
   вызовы идут после.

   **Почему это безопасно именно здесь, и почему это НЕ общий рецепт.**
   Снятие **вызовов** из внешнего замка короче держит замок и ничего не
   устаревает: `ApplyModeGpuOc` и `ApplyModeCpuPower` перечитывают текущий режим
   под собственным захватом `_state`. Снятие **аргумента** аппаратной записи — другое
   изменение и в общем случае небезопасное: пока значение читалось под замком,
   конкурентный писатель и наша запись упорядочены, а после снятия писатель может
   встать первым и быть перезаписан устаревшим исполнением. Правило, которым
   закрыты остальные места:

   > Не выносить аппаратную запись из-под `_state`, если её аргумент прочитан под
   > тем же замком, — **кроме** случая, когда вызываемый метод перечитывает
   > значение под собственным захватом. Иначе получаем не «короче замок», а
   > «переупорядочивание», и это тот же класс, что потерянный ре-апплай.

   По этому правилу **не тронуты** три места, каждое осознанно:

   - **`ApplyCustom`** (`LaptopService.Fans.cs`) — держит `_state` через запись
     вентиляторов. Разнести `Step → ApplyFan → Commit` на два региона нельзя:
     `FanCurveEngine` двигает состояние дедбенда **только** через `Commit`, и
     `SetFan` с UI-потока успеет вклинить `Reset()` между ними, а устаревший
     `Commit` перезапишет новую базу — то есть подавит корректирующую запись.
     Нужен версионный токен на `FanCurveEngine`; это отдельная правка.
   - **`ApplyModeCpuPower`** — его собственный `cp.Set(id)` под замком остаётся.
     Сосед `ApplyModeGpuOc` уже делает «скопировать под замком, записать снаружи»,
     и здесь напрашивается то же, но вызывается метод **конкурентно**: UI-потоком
     (смена режима) и `LightingCoordinator` на `Task.Run`. Снятие записи даёт
     «последний исполнитель побеждает» вместо «последний взявший замок», а
     исправлять это нечем: проход опроса CPU power **не** переприменяет, так что
     неверный overlay дожил бы до следующей смены режима. Это единственное
     оставшееся место D17, и оно записано, а не спрятано.
   - **`CurrentModeKey()`** в вызывающих, которые держат `_state`
     (`StoredFan`/`StoredGpuOc`/`StoredCo`/`ApplyModeFan`) — EC-чтение под замком
     остаётся. Санкционированный приём для этого уже есть и это **не** вынос
     чтения: `CurrentModeKey(PerformanceProfile? cur)` переиспользует профиль,
     прочитанный вызывающим один раз (так сделал шаг 4 Волны 6), и ключ
     выводится под замком вместе с поиском пресета. Вынос EC-чтения наружу
     разорвал бы пару «прочитать режим → взять его пресет», которая сегодня
     атомарна.

3. **D8 — мёртвое поле удалено.** `AcerEcHidController.LastError` писался и не
   читался нигде (проверено грепом: все упоминания класса — объявление,
   конструктор и заголовки partial-частей), а его XML-комментарий **утверждал
   обратное** («read by the UI»). Удалено вместе с ложным комментарием, и на месте
   записи оставлено честное: отказ EC-записи **не** выводится никуда, и это
   состояние было до правки. `Apply` возвращает «принято к отправке», а не «EC
   применил», и его `bool` — про очередь, а не про запись.

**Как это проверено.** Новый `tests/AcerHelper.Tests/StartupLockScopeTests.cs`
(3 теста, 532 → **535**) плюс шов `LaptopService.StateHeld` (`_state.IsHeldByCurrentThread`).
Шов понадобился потому, что фейк видит **вызов**, а не состояние замка вокруг
него, — без него «этот вызов идёт вне замка» невыразимо, и правка была бы
непроверяемой. Тест **проверен мутацией**: если вернуть два вызова под `lock`,
падает с «2 out of 2 items did not pass» — то есть он падает именно на том
поведении, которое правка убрала, а не зелен по построению. Третий тест
(«шов честен») держит обе половины: `true` из-под чужого замка
(`ApplyModeCpuPower` — настоящий свидетель, а не синтетический) и `false` снаружи.

**Что этот шаг закрыл и что нет.** Закрыл: две из четырёх аппаратных записей
на старте вышли из `_state`; мёртвое состояние удалено; корневое приглашение
(D1–D5) убрано с публичной поверхности. Не закрыл и не собирался: сам актор
(шаги 1–4/6–8), критерий 2, `ApplyCustom`, `ApplyModeCpuPower`, `CurrentModeKey`,
живые ссылки из восьми аксессоров. **Замеры всё ещё нужны ровно так же**, как
описано выше, — этот шаг их не заменяет и решения не подменяет.

**Побочно: два утверждения дизайн-документа были устаревшими** и это записано:
его §3.1 (D1–D5 в `AppController`/`OptionsAssembler`) описывает состояние **до**
`303beca` — в `UI/AppController.cs` сегодня **ноль** обращений к `.Settings`, а
`OptionsAssembler` читает `svc.Bluelight` (под замком), а не граф. То есть
D1–D5 давно починены Волной 2, а §3.1 остался их перечислять.

### Волна 6 — Отсрочка чтений вместо приоритета *(сделана — шаги 1–4: `b51c38d`, `46a3600`, `cc145c9`, `4f41cfc`)*

Формулировка «правило приоритета и таймаут» при разборе **не подтвердилась**, и
это стоит зафиксировать отдельно, потому что волна была названа по ней. По
`WmiSession.Windows.cs:19-27` замок берётся **на транзакцию** и отпускается
между ними, поэтому UI-чтение встаёт в очередь максимум за одной транзакцией, а
не за проходом опроса. Схема приоритетов купила бы ровно эту одну транзакцию,
которую мьютекс уже даёт бесплатно, — и в том самом замке, который эта же волна
запрещает перестраивать. Абзац про «два приоритета» в
`docs/hardware-actor-design.md` §4.4 — требование к **будущему актору** (одна
FIFO-очередь команд), а не к сегодняшнему дереву, где опрос уже идёт с пула.

Честное прочтение задачи: не сериализовать UI за опросом, а сделать так, чтобы
UI от опроса **не зависел**. Значит — снять с UI-потока те чтения, которые он
делает при сборке UI, на уже существующую машинерию: у строки уже есть `Sync()`
(«перечитать железо вне UI-потока и поправить контрол»), и он уже вешается на
открытие ящика. `Prime` — это тот же `Sync`, вызванный на старте; для строк, у
которых `Read` уже задан, отдельный делегат не нужен (`Prime ?? Read`). Нового
потока, нового замка и новой точки `Dispatcher.UIThread.Post` не заводится.

Плейсхолдер на время отсрочки берётся равным **сегодняшнему ответу на неудачное
чтение** (`false` / `0` / `null`), а не выдумывается: тогда отсрочка не создаёт
нового вида лжи, а на машинах с мёртвым портом строка выглядит ровно как
сегодня. Отдельный случай — яркость подсветки: плейсхолдер **читаемой** зоны
обязан быть `0`, а не `state.Brightness`, иначе сторож ложного нуля
(`LightingViewModel.cs:279`) проглотит первый честный нуль от железа и слайдер
соврёт до конца сессии.

`ApplyStartupState` **не переезжает**: внутри нет ни одной `Gate`-транзакции
(powrprof, gdi32 `SetDeviceGammaRamp`, NvAPI), а два действительно медленных
члена уже уведены с UI-потока внутри самого метода. Переезд не убрал бы ни
одного EC-ожидания, но сломал бы порядок «apply до чтений», который защищает
строку clamshell.

Шаги (каждый отдельным коммитом, с пометкой `[M]` — «проверяется только
человеком за экраном»): 1) строки опций — `Prime`, плейсхолдеры, вызов после
`BuildUi`; 2) подсветка; 3) CPU power — через `Tick`/`BackgroundPass`, только
чтение, не `ApplyModeCpuPower`; 4) соседние чтения профиля в конструкторе
(в задании их не было) — последним и опционально.

**Шаг 1 сделан — `b51c38d` (строки опций).** `Prime` лёг на `OptionToggle`
(`Options.cs:18`) и на `OptionChoice` (`:27`); `Prime()` есть у обеих строк и у
`OptionsViewModel` (`OptionsViewModel.cs:130`), зовётся из `AppController` сразу
после `BuildUi` — в конструкторе и в `RebuildForLanguage`, рядом с
`_lightingCoord.Attach`. `Initial`/`InitialIndex` в `OptionsAssembler` стали
плейсхолдерами по таблице выше; явный `Prime: lcd.Get` заведён только LCD
overdrive (`:31`), и только потому, что у него нет `Read`.

Три ворот пройдены (`tests/AcerHelper.Tests/OptionsPrimeTests.cs`): сборка строк
не трогает ни одного порта (`GetCount == 0` по восьми фейкам, плюс
`FakeAutostart.IsEnabledCalls == 0`); значение доезжает — `Prime()` → серийный
воркер строки → пост → контрол; клик между сборкой и приходом чтения не теряется.
**Утверждение «диспетчер сливается из голого xUnit-процесса» проверено
исполнением, а не чтением** — `Dispatcher.UIThread.Post` +
`RunJobs(null)` работают без платформы, так что точка инъекции `post` не
понадобилась (она была названа запасным вариантом; тест-проба удалён).
**[ОПРОВЕРГНУТО шагом 2 — см. ниже: это была ложная зелень, `RunJobs` не
работает, `post` заведён.]** Ассерты
`GetCount` в `OptionsAssemblerTests` действительно поехали 1 → 0 — это и есть
предмет изменения, а не побочный ущерб.

Новые фейки — `tests/AcerHelper.Tests/Fakes/FakeShellPorts.cs`. `FakeClamshell`
считает **чтения** `Enabled`, чтобы разница была проверяемой: строка clamshell
по-прежнему берёт значение из поля порта при сборке (`EnabledReads == 1` и после
прайма), тогда как автостарт — единственная строка, чьё чтение отсрочено, потому
что `schtasks.exe` там настоящий.

`[M]` для этого шага, чего тесты не показывают: что отсроченные чтения
возвращают то же, что возвращали синхронные; что плейсхолдер нигде не виден
(тайминги холодного старта); что clamshell-перехват по-прежнему предшествует
чтению строки; что смена языка перестраивает все строки.

**`RunJobs` не сработал — и это записано, потому что порядок был задан заранее.**
«Сначала попробовать `Dispatcher.UIThread.RunJobs(null)`, и только если не
выйдет — заводить `post`». Не вышло, и по причине, которую по коду не видно:
диспетчер **привязан к потоку**. `Dispatcher.UIThread` создаётся при первом
обращении, а первым его трогает **рабочий поток строки**, выпускающий пост, — не
поток теста. Поэтому `RunJobs` из теста бросает `The calling thread cannot access
this object because a different thread owns it`. Проба, которую я прогнал перед
шагом 1, была зелёной **и это была ложная зелень**: она одна трогала диспетчер и
он достался её потоку; как только ворот стало несколько, они начали падать по
расписанию потоков xUnit. Отсюда вывод в общий список ловушек ниже.

Заведён `post`, как и было предписано запасным вариантом: необязательный
`Action<Action>?` у `ToggleRowViewModel`, `ChoiceRowViewModel`,
`BacklightViewModel` и у `OptionsViewModel.TryCreate` (тот же приём и то же
обоснование, что у `OptionsAssembler`). Прод ничего не передаёт — шина остаётся
`Dispatcher.UIThread.Post`; тесты передают `Eventually.Sync`. Сама асинхронность
не убрана: чтение по-прежнему идёт на серийном воркере строки, тест его
**дожидается** — ушла только очередь Avalonia.

**Шаг 2 сделан — `46a3600` (подсветка), и от плана пришлось отступить.** План
предписывал для `LightViewModel` плейсхолдер `0` («читаемая зона — `0`, иначе
сторож ложного нуля проглотит первый честный нуль»). **Это неверно, и вот
почему:** `Brightness` у панели — не только то, что показывает слайдер, но и то,
что **отправляется в железо**: конструктор при `state.Configured` зовёт
`ApplyNow()`, который пишет `(byte)Brightness`. Плейсхолдер `0` означал бы запись
яркости 0 при каждом старте на настроенной зоне — клавиатура поднималась бы
погасшей и **не переприменялась бы**: прайм только перечитывает слайдер, он не
пишет. Это потеря фичи, а не косметика, и проверить это без машины нечем.

Правильный ответ даёт само правило волны: плейсхолдер = то, что дало бы
**неудачное** чтение, а неудачное чтение здесь даёт `state.Brightness`
(`readBrightness?.Invoke() ?? state.Brightness`). Но и он меняет то, что
записывается в железо (сегодня при старте пишется живое значение, прочитанное
только что). Поэтому **чтение оставлено синхронным** — это единственное
конструкторское чтение в файле, которое волна не тронула, и цена этого — одна
EC-транзакция на UI-потоке на `BuildUi`. Снятие её требует отложить вместе с
чтением и стартовый ре-апплай, а это уже видимое железом изменение. Записано и в
коде (`LightingViewModel.cs`, над строкой), и закреплено тестами
(`LightingPrimeTests`), включая **сохранённое как есть** поведение на ложном нуле
профиль-вспышки: сегодня конструктор его не фильтрует, и волна это не меняет.

Отсрочено в этом шаге ровно одно: уровень простой (не-RGB) подсветки
(`BacklightViewModel`) — его конструктор **не пишет ничего**, поэтому плейсхолдер
`0` доказанно никуда не утекает. Прайм — `SyncFromHardware()`, уже висящий на
открытии ящика и на Fn-клавишах; из `AppController` после `BuildUi` зовётся
`_lighting?.Sync()` — в конструкторе и в `RebuildForLanguage`, рядом с
`OptionsViewModel.Prime()`. RGB-панели этот же `Sync` перечитывает заодно, вне
UI-потока.

`[M]` для шага 2, чего тесты не показывают: что подсветка на живой машине
поднимается в том же состоянии, что и до волны (в частности, что ложный нуль
профиль-вспышки ведёт себя как раньше); что плейсхолдер слайдера подсветки никто
не видит до открытия ящика.

**Шаг 3 сделан — CPU power.** `CpuSection.Initial` в `BuildUi` стал `null`
(плейсхолдер: `CpuViewModel.IndexOf(null)` → Balanced, как и было обещано
таблицей), `_svc.CurrentCpuPower()` переехал в `BackgroundPass` — **чтение**, не
`ApplyModeCpuPower`; в `Tick` добавлен `bool CpuPrimed`, флаг `_cpuPrimed` сброшен
в `RebuildForLanguage` рядом с `_lastModeKey`/`_lastProfileId`. В `UiPass`
`ReloadCpuPower` вышел из-под `if (t.ModeChanged)` и висит на своём флаге —
иначе первый проход после сборки UI (а он не смена режима) не заполнил бы
плейсхолдер, и строка просидела бы на Balanced до первой смены профиля.

Одна тонкость, найденная при написании, а не при отладке: флаг пришлось
заводить от `modeChanged`, а не от «чтение вернуло не-null». На смене режима
`ApplyModeCpuPower` может вернуть `null` (оверлей нечитаем), и раньше строка в
этом случае **перезагружалась** в Balanced; условие «значение есть» молча
отменило бы эту перезагрузку. То есть различие между «есть что показать» и
«строку надо перезагрузить» здесь настоящее, и оно записано в коде.

Проверено без железа только то, на чём стоит плейсхолдер, — и это первый тест
`CpuViewModel` вообще (до шага 3 у него покрытия не было):
`tests/AcerHelper.Tests/CpuPrimeTests.cs` закрепляет, что `null` попадает в
Balanced, а не в `_modes[0]` (Best power efficiency — туда увели бы фолбэки
строк опций), и что ни конструктор, ни `Load` не доходят до `SetCpuPower`.
Вторая половина проверена **мутацией**: снятие сторожа `_loading` в `Load` роняет
4 из 5 случаев теории — то есть тест действительно держит утверждение, а не
соглашается с кодом. Прогон после отката мутации — побайтово тот же файл
(`diff` чист), 527/527.

Сама логика прохода (`cpuPrimed`, флаг, его сброс) теста не имеет и не может
иметь: `AppController` требует desktop lifetime и живого цикла опроса. Это
`[M]`.

`[M]` для шага 3, чего тесты не показывают: что строка CPU power на живой машине
показывает то же, что до волны (в частности, на неконфигурированном режиме —
живой оверлей, а не Balanced); что плейсхолдер не виден — окно тут узкое по
устройству: строка живёт в ящике «Tuning», который открывается кнопкой в футере,
а первый проход стартует из конструктора до `OpenMain`, так что увидеть Balanced
можно, только успев открыть ящик в первые миллисекунды после запуска; и что смена
языка пересобирает строку через сброшенный `_cpuPrimed`.

**Шаг 4 сделан — `4f41cfc` (соседние чтения профиля).** Заведена вторая половина
пары, у которой первая (`CurrentModeKey(cur)`) уже была:
`LightsForCurrentMode(PerformanceProfile? cur)` с тем же обоснованием — «переиспользовать
уже прочитанный профиль, чтобы не делать второй EC-раунд-трип». Параметрless-форма
теперь делегирует ей, так что поведение прежнее (это проверено тестом на
тождество словаря, а не глазами).

Три места на пути старта и одно в проходе опроса:

- **конструктор** — чтение поднято ВЫШЕ `BuildUi` и протянуто в `BuildUi(cur)`,
  в оба засева и в `ApplyFollowLighting`: три чтения профиля стали одним;
- **`RebuildForLanguage`** — тот же подъём, чтобы смена языка не стоила трёх;
- **`BackgroundPass`** — поиск подсветки теперь берёт ключ от `current`, который
  проход уже прочитал. Это делает существующий комментарий «the ONE hardware
  profile read this pass» **правдой**: до этого он был неправдой, потому что поиск
  делал своё чтение внутри того же замка.

Подъём выше `BuildUi` безопасен, потому что `BuildUi` только читает устройство —
изменения состояния живут в `ApplyStartupState`, и он по-прежнему идёт первым. Он
же выводит чтение из окна `GateStatsLog.RecordBuild`, предмет которого — время,
которое `BuildUi` сам проводит в железе (Волна 5, шаг 0): число остаётся
сравнимым, уменьшаясь.

Проверка без железа: `FakePowerProfiles` получил счётчик чтений `CurrentCount`
(замена EC-раунд-трипа), и `LightsForCurrentModeTests` закрепляет **обе**
половины — что перегрузка НЕ читает порт и что она берёт профиль, который ей
**передали**. Вторая половина и есть то, что придаёт смысл первой; проверено
мутацией: замена `CurrentModeKey(cur)` на parameterless-форму (то есть
перегрузка, игнорирующая свой параметр) роняет 3 теста из 5, включая тест про
отсутствие чтения. Откат мутации сверен грепом по маркеру.

Побочный вывод, который стоит записать: **счётчик чтений — единственное, что
превращает «мы убрали лишнее чтение» из утверждения в проверку.** Без него
перегрузка, игнорирующая параметр, выглядит ровно как правильная — ровно тот же
класс ложной зелени, что и проба с `RunJobs` (см. выше), только обнаруженный до,
а не после.

`[M]` для шага 4, чего тесты не показывают: что на живой машине старт и смена
языка по-прежнему ключуют подсветку по тому режиму, в котором пользователь на
самом деле находится. Отказ здесь выглядит не исключением, а **не теми цветами
зон после смены профиля**. Свёртка Turbo (при Turbo-как-переключателе ключ —
базовый профиль) покрыта тестом через настоящий `ApplyProfile`, потому что это
тот случай, где неверный ключ был бы виден.

## Известные особенности (решение ожидается)

Найдено тестами (Волна 2 и последующие). Часть находок **латентные** — на
текущих путях вызова недостижимы, поэтому в проде не проявляются; часть
достижимы, но выглядят как осознанные решения, а не как ошибка (это у каждой
отмечено). Тесты зафиксировали текущее поведение под именами, которые **не
выдают его за правильное**. Решение за владельцем: менять поведение прод-кода
или принять как есть. Набор тестов зелёный намеренно — чтобы он продолжал
ловить настоящие регрессии.

### 1. `Encode` схлопывает любой неотрицательный вход в 0

`Infrastructure/Vendors/Generic/RyzenCurveOptimizer.Windows.cs:388`:

```csharp
=> (counts >= 0 ? 0u : 0x100000u - (uint)(-counts)) & 0xFFFFFu;
```

Ветка «неотрицательное» — литерал `0u`, поэтому `Encode(5)` возвращает `0`, а не
`5`. **Обе трактовки защитимы, и код их не различает:**

- *Намеренная защита от овервольта.* Приложение умеет только андервольт, всё
  клампится в `[MinCounts, 0]`, значит положительный запрос безопасно
  схлопывается в «без смещения».
**Проверено дополнительно, и это меняет вероятный ответ.** Файл сам
документирует политику в `:145-146`: «Negative only: a positive offset RAISES
voltage, which buys nothing here and is a thermal and stability risk, so it is
not offered». Обе шкалы (`MinCounts = -40`, `GpuMinCounts = -50`) выставляют
только отрицательные значения. Отсюда:

- `Encode` со своим `0u` **согласуется** с документированной политикой:
  положительный запрос, который не должен приходить, схлопывается в «без
  смещения». Это безопасное поведение.
- `GpuMargin` — ведёт себя **небезопасно**: пропускает положительное значение
  как есть, а значит, дойди оно до мейлбокса, подняло бы напряжение.

Вероятный вывод: не «чинить» `Encode` под `GpuMargin`, а наоборот — **снабдить
`GpuMargin` той же защитой**, что в `Encode` уже есть. Моя прежняя формулировка
(«приведение `Encode` к `GpuMargin` уведёт положительное в мейлбокс») верна, но
указывала не на того виновника.

Недостижимо и то, и другое: `Set` (`:256`), `SetDomains` (`:319,:323`),
`Range` (`:174`), `CoViewModel.cs:115`, `LaptopService.Tuning.cs` `SetCo` — все клампят
отрицательным диапазоном.

**Что решить.** Снабдить ли `GpuMargin` защитой `Encode` — выглядит правильно и
на достижимых путях не меняет ничего, — или оставить как есть, раз недостижимо.

### 2. `EvalCurve` берёт `duties[^1]` вместо дежурства последнего якоря

`Domain/FanCurveEngine.cs:45`. Все остальные обращения по якорям в том же
методе индексируются **якорным** индексом (`duties[0]` в `:43`/`:44`,
`duties[i-1]`/`duties[i]` в цикле), а ветка «на последнем якоре и выше» берёт
последний элемент массива. Ограничитель в `:42` отбраковывает только
`Length < 5`, поэтому кривая длиной 6 берёт плоскую вершину из элемента, не
относящегося ни к одному якорю: `[10,20,30,40,50,999]` при температуре ≥ 90 даёт
`100`, а не `50`.

Для корректной кривой длины 5 незаметно — индексы совпадают. Достижимо только из
рукописного `settings.json`: UI всегда пишет 5 значений
(`FansViewModel.Duties`).

**Что решить.** Починить индекс — но тогда меняется поведение вентиляторов при
испорченных данных, — либо ужесточить ограничитель и падать на дефолтную кривую.

### 3. Дедбенд `Step` проверяет только `_cpu` (наблюдение, тестами не закреплено)

`Domain/FanCurveEngine.cs:33` — ограничитель проверяет лишь `_cpu >= 0`,
поэтому состояние `_cpu >= 0 && _gpu == -1` отключило бы дедбенд GPU целиком.
Недостижимо: `Commit` пишет оба вентилятора, `Reset` очищает оба. Закреплять
тестом не стали — недостижимый путь, а утверждение про него было бы
спекулятивным.

### 4. `RunSet`'s `catch` недостижим для строк-флагов и строк-списков

`OptionsAssembler` `RunSet` ловит исключение из сеттера (`catch { ok = false; }`),
но до него исключение почти никогда не доходит: строки-флаги и строки-списки
идут через `LaptopService.SetFlag`/`SetChoice` → `Run`, а `Run` уже ловит
(`LaptopService.cs` `Run`). Единственный настоящий вход в этот `catch` —
`PowerSourceProfiles`: там `ApplyProfile` зовёт порт напрямую
(`LaptopService.Profiles.cs` `ApplyProfile`), без `try`. Оба пути закреплены
тестами, так что слоёность теперь видна, а не подразумевается.

Отказа нет и менять нечего — это наблюдение о двух уровнях обработки одного и
того же. **Что решить:** оставить как есть или убрать недостижимый `catch` как
мёртвый код (второе сделает падение порта в `PowerSourceProfiles` необработанным
внутри `RunSet` — суди по тому, полагается ли кто-то на внешний обработчик).

### 5. Имя в сообщении об ошибке — не подпись строки (достижимо, видит пользователь)

Строка, которую пользователь видит как `Keyboard backlight timeout:`, падает с
сообщением `Backlight timeout`; `Charge limit (~80%)` — с `Battery limit`.
Английские имена контролов в `RunSet` не совпадают с подписями строк, и
локализация применяется к обоим (`Loc.T(what)`), так что расхождение
сохраняется и в русском: «Тайм-аут подсветки клавиатуры:» против «Тайм-аут
подсветки», «Ограничение заряда (~80%)» против «Ограничение заряда» (обе пары
есть в `Localization/Strings.Ru.cs`). Пользователь получает сообщение про
контрол, которого интерфейс ему не показывал — но получает, то есть это не
молчаливый отказ.

**Что решить:** брать имя из подписи строки (то есть перестроить `RunSet` так,
чтобы он получал уже локализованный label) или принять как есть.

   прямо над не относящимся к делу полем `private readonly IRgbDevice _rgb;`.
   `WorkerLoop` просто выходит из цикла.
3. **`Domain/Ports.cs:160-169` верен наполовину** — «no trustworthy
   read-back» верно для кластеров CPU, но неверно для iGPU, который

4. **Числовой разъезд.** Один и тот же эксперимент «all-core −30» описан как

5. **`RyzenCurveOptimizer.Windows.cs:419`** — после 5-секундного ожидания
   PCI-мьютекса смещение **молча отбрасывается**, и комментарий об этом не
   говорит. Пользователь читает это как «андервольт не держится».

## Что признано хорошим и не трогается

- `Infrastructure/Vendors/Generic/DelegatePorts.cs` — 5 тонких классов (`FlagPort`,
  `ChoicePort`, `FanPort`, `ProfilesPort`, `LevelPort`, `SensorsPort`) делят одну
  реализацию между несколькими портами.
- `Domain/Ports.cs` — один узкий интерфейс на возможность, `null`-порт
  означает отсутствие возможности.
- WMI через source-generated COM interop вместо `System.Management` (тот не
  AOT-совместим).
- `Loc` на встроенных таблицах вместо `.resx` (спутниковые сборки ломают
  Native AOT, dotnet/runtime#86651).

**Про покрытие `JsonSettingsStore` — что здесь проверено, а что нет.** Стоит
записать, потому что ценность этого блока не в зелёности, а в том, какие
утверждения оказались нагрузочными:

- Мутации (каждая — временная правка прод-кода, потом откат): `[JsonIgnore]` на
  поле `Settings` краснит **два** теста; удаление спасения в `.bad` краснит два;
  `overwrite: true` → `false` краснит **ровно один** (`ASecondCorruptionReplacesTheEarlierRescue`);
  `UseStringEnumConverter = true` краснит **ровно один** (`TheLanguageIsWrittenAsANumber_NotAName`).
- **Ложное утверждение нашлось у меня же.** Комментарий к
  `NoPropertyOfSettingsIsLeftOutOfTheJson` обещал, что тест поймает «свойство,
  добавленное в `Settings`». Мутация это опровергла: добавление поля оставило
  **все** тесты зелёными — source-gen подхватывает новое свойство сам. Реальная
  область теста уже: он ловит свойство, переставшее персиститься, оставшись на
  типе (`[JsonIgnore]`, непригодный сеттер). Формулировка исправлена на узкую.
- **Вторая ложь, поймана той же мутацией.** Комментарий к
  `AFileWrittenByAnEarlierVersionStillLoads` обещал, что переход на строковый
  конвертер сделает существующие файлы нечитаемыми. Мутация показала, что
  **чтение** при этом остаётся зелёным: `JsonStringEnumConverter` принимает
  целые по умолчанию. Настоящий риск — в **записи** (старая сборка не прочтёт
  файл новой), поэтому утверждение разделено на два теста: чтение числа и
  запись числа. Один только первый запрещал бы меньше, чем обещал.
- **Живой файл владельца проверен, но read-only и намеренно не через `Load()`.**
  `%AppData%\AcerHelper\settings.json` существует (4.3 КБ, от 11 сентября) и
  содержит все 13 текущих свойств, `"Language": 0` как **число**, цвета как

  формат на диске совпадает с тем, что закрепляют оба новых теста. Через `Load()`
  его прогонять **нельзя и не прогонялось**: будь он повреждён, `Load()` увёл бы
  его в `.bad`. Из этого же файла взяты настоящие ключи для `Populated()` —
  прежние были выдуманы.

  хранит настройки» оказалась правкой в **две строки**, ничего не меняющей в

**Ещё один экземпляр D17, не перечисленный в дизайн-документе:**

**`LastError` из очереди выведен** — его судьба решается владельцем.

**Проверка EOL — результат отрицательный, оставлено как есть.** Девять файлов в
рабочем дереве имеют чистый LF там, где `core.autocrlf=true` ожидал бы CRLF.
Смешанных переводов строк нет ни в одном файле, а на коммит это не влияет вовсе:
`* text=auto` нормализует в LF, и дифф показывает только строки комментариев.
Установить, были ли эти файлы LF **до** правки, невозможно — блоб в HEAD всегда
LF по нормализации, поэтому равенство `HEAD_blob_CR = 0` не доказывает ничего.
Первая моя формулировка («LF был и раньше») опиралась именно на эту негодную
проверку и была снята.
