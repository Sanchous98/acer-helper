# План рефакторинга Acer Helper

Рабочий документ. Держит решения и порядок волн вне контекста одной сессии:
после компактификации достаточно перечитать этот файл.

**Номера строк здесь не поддерживаются (отмечено 2026-09-14).** Они писались
против ревизии, актуальной на момент каждого абзаца, и часть уже устарела —
в том числе из-за самого рефакторинга. Якорь — имя символа, а не число:
искать по имени. Что изменилось в дереве: `LaptopService` теперь шесть частичных
файлов `LaptopService*.cs`, а `OptionsAssembler` переехал из `UI/` в корень
(`namespace AcerHelper.Application`).

## Зачем

Две независимые проблемы, которые сейчас смешаны:

1. **Читаемость.** 12 461 строка C#, 23 % комментариев. Самые длинные блоки —
   археология железа (почему именно такой байт в SMU-мейлбоксе), которая
   уместна в `docs/`, а не в теле метода.
2. **Архитектура.** Слои существуют по дисциплине, а не по решению компилятора.

Механизм второй проблемы: `AcerHelper.Domain` / `.Application` / `.Infrastructure`
вложены в `AcerHelper`, поэтому **любой тип, объявленный в корневом `AcerHelper`,
виден всем слоям неявно**. Скрытая зависимость не видна ни в `using`-ах, ни в
грепе. Отсюда 91 примитив синхронизации в 22 файлах и разрастание фичи на 5–12
файлов.

**Вывод:** корневой namespace должен стать пустым. Это заставляет каждую
кросс-слойную ссылку иметь явный `using`, то есть делает зависимости
**явными и грепаемыми**.

Честная граница: это обеспечивает *явность*, но не *направление*. Ничто не
мешает `Infrastructure` добавить `using AcerHelper.Application;`. Физический
запрет требует отдельных сборок (4 `.csproj`) — отложено, Волна 1 даёт ~90 %
ценности за малую долю работы.

## Принцип: инвариант — фичи, а не форма кода

Приложение **функционально полностью рабочее**. Есть известные баги, их
сохранение допустимо. Инвариант: **после рефакторинга все фичи работают как
сейчас**. Форма кода при этом меняться может — архитектуру перекраивать можно.

Проблема в том, что «фичи сохранились» почти нечем проверить: логика
железозависимая, тестов на неё нет и без живого железа не будет. Поэтому вместо
проверки — **атомарность отката**:

- **один коммит на одно архитектурное изменение**; приложение собирается и
  запускается на каждом коммите;
- сломалась фича → виновник локализуется откатом одного коммита, а не разбором
  общего диффа на сотню файлов;
- тесты — там, где они возможны (чистая логика); на остальное не полагаться;
- изменения, которые нельзя оценить не запустив приложение (старт, смена языка,
  реакция на горячие клавиши), помечать в сообщении коммита явно.

Следствия для отдельных правок:

- Дефекты, которые **не проявлялись**, чиним попутно и отдельным коммитом:
  выигрыш ненаблюдаем, поэтому цена ошибки выше пользы. Записанные дефекты не
  теряются — они в `docs/hardware-actor-design.md` с точными строками.
- **Никаких «заодно почищу»**: каждое изменение должно откатываться в одиночку.

## Целевая структура

Namespace выводится из **папки**, никогда из имени файла: проект разделяет
платформы по суффиксу (`*.Windows.cs` / `*.Linux.cs`) через `<Compile Remove>`,
и попадание суффикса в namespace сломало бы это разделение.

Отсюда же — **правило для частей `LaptopService.*.cs`**: их суффиксы (`.Profiles`,
`.Tuning`, `.Fans`, `.Lighting`, `.Toggles`) выбраны так, чтобы не совпасть ни с
`*.Windows.cs`, ни с `*.Linux.cs`. Переименование любой части в такой суффикс
молча выкинуло бы её из одной из двух сборок — то есть из компиляции исчезла бы
часть класса, а вторая TFM осталась бы зелёной. Это единственная причина, по
которой имена частей не совпадают с именами фич.

| Папка | Namespace |
|---|---|
| `Features/**` | `AcerHelper.Domain` |
| `Settings.cs`, `Options.cs` | `AcerHelper.Domain` |
| `LaptopService.cs` + его части `LaptopService.*.cs` | `AcerHelper.Application` |
| `OptionsAssembler.cs` | `AcerHelper.Application` |
| `Vendors/**` | `AcerHelper.Infrastructure.Vendors.**` |
| `Composition/**`, `Os/**`, прочие корневые инфра-папки | `AcerHelper.Infrastructure.**` |
| `Program.cs` | `AcerHelper.Bootstrap` |
| `UI/**` | `AcerHelper.UI.**` — **без изменений** |
| `Localization/**` | `AcerHelper.Localization` — **без изменений** |

### Отклонено: `UI/ → AcerHelper.Presentation`

`AcerHelper.UI.*` и `AcerHelper.Localization` уже существуют как под-namespace'ы,
и на них ссылаются ~40 `.axaml` через `x:Class` / `clr-namespace`. Для опустошения
корня их переименование **не требуется** — они и так не корень. То есть это ~80
правок XAML, каждая из которых может сломать компилируемые биндинги
(`AvaloniaUseCompiledBindingsByDefault=true`), ради нулевого выигрыша в изоляции.
Косметика не стоит риска.

## Волны

### Волна 1 — Границы *(сделана — `1a7a570`)*

Трогает все `.cs`, поэтому строго последовательна.

1. `AcerHelper.csproj`: генератор `AppInfo` (target `GenerateAppVersion`, ~строка 114)
   перевести на `namespace AcerHelper.Domain%3B`.
2. Миграция объявлений namespace по таблице выше.
3. Миграция `using`-директив.
4. Сборка обеих TFM → ошибки «type not found» **и есть список скрытых
   зависимостей**, которые до этого маскировались вложенностью. Известный пример:
   `Features/FanCurveEngine.cs` использует `FanPreset` (объявлен в `Settings.cs`)
   без `using`.

Только namespace и using. Ни одной правки логики, форматирования или тела
комментария. Нарушения слоёв (например `Domain` → `Infrastructure`) — сообщать,
не чинить: это следующая волна.

Осложнение, обнаруженное на практике: миграция **не сводится к правке
`using`-директив** — в коде есть полностью квалифицированные inline-ссылки и
alias-`using` (`using X = ...;`). Плюс появляется риск CS0104 (неоднозначность),
когда два слоя экспонируют одноимённый тип; лечится полной квалификацией или
алиасом, но не удалением и не переименованием публичного типа.

### Волна 2 — Тесты и декомпозиция *(тесты сделаны — `7dcf6b4`; остальное в работе)*

Сеть безопасности.

- Отдельный проект тестов + `<Compile Remove="tests/**" />` в `.csproj`.
  Без этой строки неявный glob `**/*.cs` SDK скомпилирует тесты внутрь
  приложения.
- Целиться туда, где отказ **молчаливый**: `FanCurveEngine.EvalCurve`
  (якоря `[50,60,70,80,90]`, дефолтная кривая `[30,45,60,80,100]`, дедбенд 4),
  `Encode`/`CoreArg`/`GpuMargin` (20-битная форма `-5` у CPU это `0xFFFFB`, у
  GPU `0xFFFB` — мейлбокс принимает обе молча, означая разное),
  `LaptopService.NextSelectable`, `ParseBstr`/`ToU64`.
- `ModePresets<T>` → `GetOrAdd<T>` — **сделано в `a39bfb5`, и число в плане было
  неверным: повторов пять, а не двенадцать.** Настоящий идиом
  (`TryGetValue` + вставка созданного) нашёлся в `StoredFan`,
  `LightsForCurrentMode`, `EnsureLightZone`, `StoredGpuOc`, `StoredCo`. Остальные
  семь адресов из плана — **другая форма, и сворачивать их значило бы менять
  поведение:**
  - `CurrentFan`, `CurrentGpuOc`, `CurrentCo`, `ApplyModeCo` создают значение по
    умолчанию, но **не сохраняют** его (в документации прямо «not stored»:
    чтение не должно менять настройки). `GetOrAdd` вставил бы пресет при каждом
    чтении;
  - `CurrentCpuPower`, `ApplyModeCpuPower` — `Dictionary<string,string>`, где
    `new()` не существует вовсе; обе только ищут и падают на живое чтение железа;
  - `ApplyModeFan`, `ApplyCustom` используют `TryGetValue` как **сторож**, где
    «пресета для режима нет» — значимый результат.

  Это тот случай, когда послушное исполнение плана внесло бы восемь ошибок:
  ошибка была в плане, а не в работе. Проверено построчно мной: идиом в пяти
  местах идентичен, `CurrentModeKey()` по-прежнему вызывается ровно один раз до
  поиска, покрытие блокировок не изменилось (33 `lock (_state)` до и после).
  Тесты `LaptopService` не покрывают, поэтому зелёный гейт доказывает
  компилируемость, а не сохранение поведения — здесь работает именно построчная
  сверка.
- **Декомпозиция `LaptopService` — раскол сделан (`0fe97ca`, `6f92842`), вынос
  в классы-контроллеры ОТЛОЖЕН.** Файл был 814 строк и 57 публичных членов при
  38 вхождениях `lock (_state)`; теперь это шесть partial-частей по фичам
  (главная = тождество + общая инфраструктура, Lighting, Profiles, Fans, Tuning,
  Toggles). Число в плане (758 строк / 33 блокировки) устарело ещё до правок
  корректности — верные числа на момент раскола: 814 строк, 38 вхождений.
  - **Что разблокировало раскол:** параметры primary-конструктора видны только в
    объявляющей partial-части. Пока он в силе, `partial` невозможен; `0fe97ca`
    заменил его явными полями, сохранив имена, поэтому ни один вызов не
    сдвинулся, а диф — конструктор плюс одно присваивание.
  - **Почему раскол безопасен и как это проверено.** Блоки нарезаны из исходника
    по номерам строк, а не перепечатаны; конкатенация блоков в исходном порядке
    воспроизводит тело строка-в-строку; каждый новый файл равен своим блокам в их
    порядке (6/6); мультимножество непустых строк тела совпало с исходным. В
    диффе главного файла 19 добавленных строк — все документация и объявление
    класса. Экземпляр `_state` и его покрытие те же, поэтому контракт блокировок
    из комментария в главной части не изменился: изменилась только достижимость
    поля. Это ровно та техника, которую план и предписывал («не заводить каждому
    контроллеру свой лок»), доведённая до конца в той части, которая проверяема.
  - **Что отложено и почему.** Настоящие классы-контроллеры требуют общего
    объекта-держателя, а он упирается в две вещи, которые тестами не
    проверяются: `LastError` — **изменяемый** канал ошибок, который пишут почти
    все методы и читает UI, поэтому у каждого контроллера должна быть ссылка на
    один и тот же экземпляр, иначе ошибки молча теряются; и тождество самого
    `_state`. Промах здесь ломает ровно то, что план называет главным, —
    фичи, — и ловится только на железе, которого у меня нет. Части по фичам дают
    тот же выигрыш в читаемости, но доказуемо нейтральны. Отдельный коммит,
    когда будет человек за экраном.
  - **Ловушка имён, записанная в коде:** суффиксы `.Profiles.cs` и т. п. выбраны
    так, чтобы не столкнуться с `*.Windows.cs`/`*.Linux.cs`, по которым
    `.csproj` выбирает файлы под TFM. Переименование любого из этих файлов в
    такой суффикс молча выкинуло бы часть класса из одной из сборок.

**Правки корректности.** Незаблокированные чтения закрываются **не снимком** —
снимок вместо живой ссылки молча ломает любой путь, который пишет через неё, —
а узкими доступами под блокировкой плюс сужением публичной поверхности
`LaptopService`. Область захвата сокращается осторожно: не держать блокировку
через обращение к железу, не меняя при этом, **что именно** она охраняет.
Отдельный коммит на каждое изменение, чтобы откат был точечным.

  переиспользует свой блок, `LaptopService.cs` `ApplyStartupState` — свой. Дифф сверен построчно: **ни один**
  вызов порта (`SetDomains`, `Set`, `GpuOverclock?.Set`) внутрь блокировки не
  переехал, то есть D17 не заведён. Чтение `co.Domains` под блокировкой I/O не
  добавляет — это get-only список дескрипторов из конструктора порта.
  **Доказательство сохранения поведения, а не компилируемости:** 186 тестов
  написаны против кода **до** правки (`21b7bf1`, `7b9155d`), и все 454 проходят
  после неё.

- **`CurrentModeKey()` делает EC-чтение и вызывается из-под `_state`.** Это
  наблюдение шире правки выше и **не** ею заведено: `CurrentModeKey()` (`LaptopService.Profiles.cs`)
  вызывает `device.PowerProfiles?.Current()`, а его собственная документация
  (`LaptopService.Profiles.cs` `CurrentModeKey`) называет это EC-round-trip. Аргумент `TryGetValue(CurrentModeKey(),
  …)` вычисляется **внутри** `lock`, поэтому `CurrentGpuOc`, `CurrentCo`,
  `CurrentFan`, `SetGpuOc` и соседи держат `_state` поверх обращения к железу —
  причём в самом частом пути, а не в экзотическом. Перечень D17 в
  дизайн-документе (`ApplyCustom`, `ApplyStartupState`, `SetGpuOc`) этой широты
  не передаёт. Не моя правка и не на эту ночь: сокращение области захвата здесь
  и есть предмет отложенных Волн 5–6.

- **Четыре находки тестов Curve Optimizer — оставлены как есть.** Все четыре
  **недостижимы из поставляемого UI**, поэтому записаны, а не починены: правка
  недостижимого пути непроверяема, а правило здесь — «фичи важнее».
  `SetCo` пишет значение **без клампа** и возвращает `false`, когда порта нет,
  тогда как `SetCoDomains` отказывает **до** записи — там кламп стоит внутри
  `if (co != null)`, то есть сторожит не тот путь, ради которого написан;
  `SetCoDomains([])` на CPU без доменов проходит мимо проверки `0 != 0`,
  вставляет пресет и тем **навсегда разоружает** намеренную защиту
  `ApplyModeCo` «пустое хранилище → не трогать SMU» (`LaptopService.Tuning.cs`);
  `ApplyModeCpuPower` отдаёт `null` для **настроенного** режима, когда порта нет,
  в отличие от `ApplyModeGpuOc`/`ApplyModeCo`, которые возвращают сохранённый
  пресет; `SetCo` возвращает `false` для «нет порта», не выставив `LastError`.

- **`LastError` — план был неверен, правка ОТМЕНЕНА; решение за владельцем.**
  Отдельный разбор (2026-09-14) опроверг и список, и лекарство.
  **Список был не тот.** В плане стояло «четыре», перечислялось семь, а
  кросс-поточно читается вообще другое. Проверено мной по дереву:
  `AcerEcHidController.LastError` не читает **никто** (все ссылки на класс —
  объявления, конструктор и partial-заголовки; ни одного `_ec.LastError`) — это
  мёртвое поле, а не гонка; пять полей `DelegatePorts` пишутся и читаются на
  **одном** потоке (`HwSerial`-продолжение, у каждой строки свой экземпляр
  порта); у `LampArrayBridge` запись воркера и чтение не пересекаются, потому что
  воркер живёт только между успешным `Enable` и своим выходом, а `Enable` при
  живом воркере выходит сразу (`if (Enabled) return true`).
  **Единственное поле, читаемое кросс-поточно, — `LaptopService.LastError`**
  (`AppController` — в `ApplyProfile`, `SetTurbo`, `SetGpuOc`, `SetCpuPower`, `SetCo`; `OptionsAssembler.cs` `RunSet`), и `_state`
  тут не помогает: **ни один читатель его не берёт**, а блокировка упорядочивает
  потоки только когда её берут обе стороны. Запись идёт и с UI (`LaptopService.Profiles.cs` `ApplyProfile`, `SetTurbo`), и с
  фонового прохода (`LaptopService.Fans.cs` `ApplyFan`), и с пул-задач (`LaptopService.Tuning.cs` `SetCo`, `SetCoDomains` — в том числе
  из `ApplyModeCo`, который `LaptopService.cs` `ApplyStartupState` намеренно пускает мимо `_state`).
  **`volatile` — неверное лекарство, а не недостаточное.** К свойству его
  применить нельзя вовсе (нужно переписывать в backing-поле), а на x64 он не
  меняет ничего наблюдаемого: запись и чтение одного адреса из одного потока не
  переупорядочиваются, так что читатель и так видит минимум собственную запись.
  Все шесть найденных гонок — вида «читатель подхватил ошибку **чужого** вызова»;
  `volatile` делает это **детерминированнее**, а не реже, потому что гарантирует
  видимость самой свежей записи, в том числе чужой.
  **Правильная правка — убрать побочный канал, а не расширять его видимость:**
  вернуть ошибку из вызова (`SetCpuPower(...)` → `(bool ok, string? error)`),
  тогда общего поля не остаётся. Объём: ~8 сигнатур, ~10 мест вызова плюс
  плумбинг делегатов в `UiActions`/`OptionsAssembler`.
  **Почему не сделано этой ночью.** Симптом гонки косметический (неверный текст
  ошибки при окне в несколько инструкций), а цена ошибки в самой правке —
  «ошибка перестала показываться», то есть молчаливая регрессия ровно там, куда
  моя проверка не достаёт: тесты покрывают `FanCurveEngine`, конверсию WMI и
  кодирование SMU, но **не путь сообщений об ошибке в UI**, а железа у меня нет.
  По принципу «инвариант — фичи» такая правка помечается, а не делается вслепую.
  **Рекомендация владельцу:** делать, отдельным коммитом, с проверкой глазами,
  что все шесть сообщений об отказе по-прежнему показываются.
- **НЕ в этой волне:** снятие блокировки UI-потока на EC-`Gate` в `BuildUi`
  (`AppController.cs:134-173`) — вынесено в отдельную Волну 6. Причина: меняет
  поведение при старте (`:63`) и при **каждой смене языка** (`:198`) — это живой
  UI-флоу, который нельзя проверить без человека за экраном. Сам дефект
  зафиксирован: 6–10 сериализованных WMI-транзакций, обычно 10–50 мс, но
  **неограниченно** при зависшем EC — то есть ровно тот столл, ради выживания
  при котором `BackgroundPass` и создавался. Чинить по правилу приоритета и
  таймауту на существующих местах вызова, а не переписыванием модели
  конкурентности (см. обоснование отложенной Волны 5).

### Волна 5 — Hardware actor — ОТЛОЖЕНА (решение от 2026-09-14)

Дизайн **готов и не выбрасывается**: `docs/hardware-actor-design.md` (679 строк) —
инвентаризация 137 мест синхронизации в 22 файлах, инвентаризация потоков,
10 рисков и инкрементальный порядок из 8 шагов, каждый из которых собирается и
откатывается отдельно.

Решение — **не делать сейчас**. Обоснование получено независимым анализом:

- Подтверждённые дефекты актора не требуют: это незаблокированные чтения и
  свойства без `volatile`. Их правки перенесены в Волну 2 и дают ~90 % ценности
  за дюжину строк. Актор даёт **читаемость, а не корректность**, и его список
  рисков длиннее и тяжелее списка дефектов, которые он убирает.
- `WmiSession.Gate` — это **уже почти актор**, и лучшее по качеству конкурентное
  место в дереве: одна статическая реентерабельная блокировка, одна EC-транзакция
  за раз, с выписанным рассуждением об интерливингах. Для EC-пути актор —
  движение вбок.
- Проблема не в сериализации, а в **приоритете**: `BuildUi` блокирует UI-поток на
  EC-`Gate`, и это лечится правилом приоритета и таймаутом на существующих местах
  вызова, а не переписыванием модели конкурентности.

**Ограничения, которые обязаны пережить любые будущие правки** — иначе актор
сделают неправильно:

- Два HID-`Gate` (`EneHidController`, `AcerEcHidController`) — это **сглаживание
  темпа и коалесинг, а не сериализация**. Втягивание их в один актор поставит
  10-мс-размеренные записи за 5-секундным ожиданием SMU-мейлбокса. **53
  примитива обязаны остаться снаружи.**
- **2 примитива межпроцессные** и актором не заменяются в принципе:
  `Global\Access_PCI` (`RyzenCurveOptimizer.Windows.cs:137`, держится на всей
  транзакции `:410-448`) и мьютекс единственного экземпляра (`Program.cs:11`).
  Плюс 4 межприложенческие точки координации вне области: драйвер PawnIO, узел
  устройства LampArray (другие процессы пишут туда кадры), SMU-мейлбокс на
  кристалле, доставка `SystemEvents`/`RegisterPowerSettingNotification`.

**Пересматривать только по замерам**, не по вкусу: шаг 0 дизайна —
инструментировать ожидания на `Gate`, чтобы решение опиралось на числа.

**Шаг 0 сделан — `4ba84cf`.** `Diagnostics/GateStats.cs` (без суффикса платформы;
на Linux счётчики остаются нулевыми, `WmiSession` там нет) считает захваты,
суммарное и максимальное ожидание, удержание и «стойла» (удержание > 50 мс) в
двух корзинах — пул и не-пул (`IsThreadPoolThread`). Инструментированы оба
`lock (Gate)` в `Vendors/Generic/WmiSession.Windows.cs`; вложенный захват
(`InvokeMethod` → `QueryFirst`, реентерабельный) считается один раз — флаг
`[ThreadStatic]`, образец принадлежит внешней области, иначе одна EC-транзакция
дала бы два числа. `AppController` снимает дельту не-пуловой корзины вокруг
`ApplyStartupState` и `BuildUi`: это «до» для Волны 6, и это время,
**заблокированное на EC**, а не стенное. Строка дописывается в
`%AppData%\AcerHelper\gate-stats.log` раз в минуту (на таймере самого опроса) и
в `ExitApp` — периодическая запись нужна потому, что убитый процесс до `ExitApp`
не доживёт, а интересна именно живая сессия. Счётчики **всегда включены**, не под
`#if DEBUG`: замеры обязаны идти с той сборки, которой пользуется владелец.

**Критерий решения зафиксирован ДО замеров** — чтобы «пересмотреть по замерам»
не превратилось в «пересмотреть по вкусу, приложив замеры». Волна 5 делается,
если подтвердится хотя бы одно:

| # | наблюдение | почему это довод за актора |
|---|---|---|
| 1 | ожидание `Gate` на UI-потоке регулярно > 100 мс | 10-50 мс терпимо (D16), сотни — нет |
| 2 | заметная доля транзакций ушла в стойло EC (> 50 мс удержания) | тогда очередь всё равно одна, и отсрочка чтений не спасает |
| 3 | проход опроса выдаёт много транзакций подряд, UI-чтение вклинивается редко | линия приоритета — настоящая потребность |

Если ни одно не подтвердится — Волна 6 закрывает вопрос, актор не делается, и
это тоже записывается как решение с обоснованием, а не остаётся висеть.

**Риски, которые не закрываются тестами в принципе** — важно для честных
ожиданий от Волны 2: мок-транспорт не проверяет потерянный ре-апплай (Curve
Optimizer / GPU OC / CPU power), гонку владения LampArray и PCI-мьютекс.
Волны 2→5 оставляют эти решения проверяемыми только на живом железе — то есть
там же, где они сейчас. Тесты повышают надёжность, но не превращают переписку
модели конкурентности в безопасную.

### Волна 6 — Отсрочка чтений вместо приоритета *(шаг 1 сделан; шаги 2-4 в работе)*

Формулировка «правило приоритета и таймаут» при разборе **не подтвердилась**, и
это стоит зафиксировать отдельно, потому что волна была названа по ней. По
`WmiSession.Windows.cs:19-27` замок берётся **на транзакцию** и отпускается
между ними, поэтому UI-чтение встаёт в очередь максимум за одной транзакцией, а
не за проходом опроса. Схема приоритетов купила бы ровно эту одну транзакцию,
которую мьютекс уже даёт бесплатно, — и в том самом замке, который эта же волна
запрещает перестраивать. Абзац про «два приоритета» в
`docs/hardware-actor-design.md` §4.4 — требование к **будущему актору** (одна
FIFO-очередь команд), а не к сегодняшнему дереву, где опрос уже идёт с пула.

Честное прочтение задачи: не сериализовать UI за опросом, а сделать так, чтобы
UI от опроса **не зависел**. Значит — снять с UI-потока те чтения, которые он
делает при сборке UI, на уже существующую машинерию: у строки уже есть `Sync()`
(«перечитать железо вне UI-потока и поправить контрол»), и он уже вешается на
открытие ящика. `Prime` — это тот же `Sync`, вызванный на старте; для строк, у
которых `Read` уже задан, отдельный делегат не нужен (`Prime ?? Read`). Нового
потока, нового замка и новой точки `Dispatcher.UIThread.Post` не заводится.

Плейсхолдер на время отсрочки берётся равным **сегодняшнему ответу на неудачное
чтение** (`false` / `0` / `null`), а не выдумывается: тогда отсрочка не создаёт
нового вида лжи, а на машинах с мёртвым портом строка выглядит ровно как
сегодня. Отдельный случай — яркость подсветки: плейсхолдер **читаемой** зоны
обязан быть `0`, а не `state.Brightness`, иначе сторож ложного нуля
(`LightingViewModel.cs:279`) проглотит первый честный нуль от железа и слайдер
соврёт до конца сессии.

`ApplyStartupState` **не переезжает**: внутри нет ни одной `Gate`-транзакции
(powrprof, gdi32 `SetDeviceGammaRamp`, NvAPI), а два действительно медленных
члена уже уведены с UI-потока внутри самого метода. Переезд не убрал бы ни
одного EC-ожидания, но сломал бы порядок «apply до чтений», который защищает
строку clamshell.

Шаги (каждый отдельным коммитом, с пометкой `[M]` — «проверяется только
человеком за экраном»): 1) строки опций — `Prime`, плейсхолдеры, вызов после
`BuildUi`; 2) подсветка; 3) CPU power — через `Tick`/`BackgroundPass`, только
чтение, не `ApplyModeCpuPower`; 4) соседние чтения профиля в конструкторе
(в задании их не было) — последним и опционально.

**Шаг 1 сделан — `b51c38d` (строки опций).** `Prime` лёг на `OptionToggle`
(`Options.cs:18`) и на `OptionChoice` (`:27`); `Prime()` есть у обеих строк и у
`OptionsViewModel` (`OptionsViewModel.cs:130`), зовётся из `AppController` сразу
после `BuildUi` — в конструкторе и в `RebuildForLanguage`, рядом с
`_lightingCoord.Attach`. `Initial`/`InitialIndex` в `OptionsAssembler` стали
плейсхолдерами по таблице выше; явный `Prime: lcd.Get` заведён только LCD
overdrive (`:31`), и только потому, что у него нет `Read`.

Три ворот пройдены (`tests/AcerHelper.Tests/OptionsPrimeTests.cs`): сборка строк
не трогает ни одного порта (`GetCount == 0` по восьми фейкам, плюс
`FakeAutostart.IsEnabledCalls == 0`); значение доезжает — `Prime()` → серийный
воркер строки → пост → контрол; клик между сборкой и приходом чтения не теряется.
**Утверждение «диспетчер сливается из голого xUnit-процесса» проверено
исполнением, а не чтением** — `Dispatcher.UIThread.Post` +
`RunJobs(null)` работают без платформы, так что точка инъекции `post` не
понадобилась (она была названа запасным вариантом; тест-проба удалён). Ассерты
`GetCount` в `OptionsAssemblerTests` действительно поехали 1 → 0 — это и есть
предмет изменения, а не побочный ущерб.

Новые фейки — `tests/AcerHelper.Tests/Fakes/FakeShellPorts.cs`. `FakeClamshell`

## Известные особенности (решение ожидается)

Найдено тестами (Волна 2 и последующие). Часть находок **латентные** — на
текущих путях вызова недостижимы, поэтому в проде не проявляются; часть
достижимы, но выглядят как осознанные решения, а не как ошибка (это у каждой
отмечено). Тесты зафиксировали текущее поведение под именами, которые **не
выдают его за правильное**. Решение за владельцем: менять поведение прод-кода
или принять как есть. Набор тестов зелёный намеренно — чтобы он продолжал
ловить настоящие регрессии.

### 1. `Encode` схлопывает любой неотрицательный вход в 0

`Vendors/Generic/RyzenCurveOptimizer.Windows.cs:388`:

```csharp
=> (counts >= 0 ? 0u : 0x100000u - (uint)(-counts)) & 0xFFFFFu;
```

Ветка «неотрицательное» — литерал `0u`, поэтому `Encode(5)` возвращает `0`, а не
`5`. **Обе трактовки защитимы, и код их не различает:**

- *Намеренная защита от овервольта.* Приложение умеет только андервольт, всё
  клампится в `[MinCounts, 0]`, значит положительный запрос безопасно
  схлопывается в «без смещения».
**Проверено дополнительно, и это меняет вероятный ответ.** Файл сам
документирует политику в `:145-146`: «Negative only: a positive offset RAISES
voltage, which buys nothing here and is a thermal and stability risk, so it is
not offered». Обе шкалы (`MinCounts = -40`, `GpuMinCounts = -50`) выставляют
только отрицательные значения. Отсюда:

- `Encode` со своим `0u` **согласуется** с документированной политикой:
  положительный запрос, который не должен приходить, схлопывается в «без
  смещения». Это безопасное поведение.
- `GpuMargin` — ведёт себя **небезопасно**: пропускает положительное значение
  как есть, а значит, дойди оно до мейлбокса, подняло бы напряжение.

Вероятный вывод: не «чинить» `Encode` под `GpuMargin`, а наоборот — **снабдить
`GpuMargin` той же защитой**, что в `Encode` уже есть. Моя прежняя формулировка
(«приведение `Encode` к `GpuMargin` уведёт положительное в мейлбокс») верна, но
указывала не на того виновника.

Недостижимо и то, и другое: `Set` (`:256`), `SetDomains` (`:319,:323`),
`Range` (`:174`), `CoViewModel.cs:115`, `LaptopService.Tuning.cs` `SetCo` — все клампят
отрицательным диапазоном.

**Что решить.** Снабдить ли `GpuMargin` защитой `Encode` — выглядит правильно и
на достижимых путях не меняет ничего, — или оставить как есть, раз недостижимо.

### 2. `EvalCurve` берёт `duties[^1]` вместо дежурства последнего якоря

`Features/FanCurveEngine.cs:45`. Все остальные обращения по якорям в том же
методе индексируются **якорным** индексом (`duties[0]` в `:43`/`:44`,
`duties[i-1]`/`duties[i]` в цикле), а ветка «на последнем якоре и выше» берёт
последний элемент массива. Ограничитель в `:42` отбраковывает только
`Length < 5`, поэтому кривая длиной 6 берёт плоскую вершину из элемента, не
относящегося ни к одному якорю: `[10,20,30,40,50,999]` при температуре ≥ 90 даёт
`100`, а не `50`.

Для корректной кривой длины 5 незаметно — индексы совпадают. Достижимо только из
рукописного `settings.json`: UI всегда пишет 5 значений
(`FansViewModel.Duties`).

**Что решить.** Починить индекс — но тогда меняется поведение вентиляторов при
испорченных данных, — либо ужесточить ограничитель и падать на дефолтную кривую.

### 3. Дедбенд `Step` проверяет только `_cpu` (наблюдение, тестами не закреплено)

`Features/FanCurveEngine.cs:33` — ограничитель проверяет лишь `_cpu >= 0`,
поэтому состояние `_cpu >= 0 && _gpu == -1` отключило бы дедбенд GPU целиком.
Недостижимо: `Commit` пишет оба вентилятора, `Reset` очищает оба. Закреплять
тестом не стали — недостижимый путь, а утверждение про него было бы
спекулятивным.

### 4. `RunSet`'s `catch` недостижим для строк-флагов и строк-списков

`OptionsAssembler` `RunSet` ловит исключение из сеттера (`catch { ok = false; }`),
но до него исключение почти никогда не доходит: строки-флаги и строки-списки
идут через `LaptopService.SetFlag`/`SetChoice` → `Run`, а `Run` уже ловит
(`LaptopService.cs` `Run`). Единственный настоящий вход в этот `catch` —
`PowerSourceProfiles`: там `ApplyProfile` зовёт порт напрямую
(`LaptopService.Profiles.cs` `ApplyProfile`), без `try`. Оба пути закреплены
тестами, так что слоёность теперь видна, а не подразумевается.

Отказа нет и менять нечего — это наблюдение о двух уровнях обработки одного и
того же. **Что решить:** оставить как есть или убрать недостижимый `catch` как
мёртвый код (второе сделает падение порта в `PowerSourceProfiles` необработанным
внутри `RunSet` — суди по тому, полагается ли кто-то на внешний обработчик).

### 5. Имя в сообщении об ошибке — не подпись строки (достижимо, видит пользователь)

Строка, которую пользователь видит как `Keyboard backlight timeout:`, падает с
сообщением `Backlight timeout`; `Charge limit (~80%)` — с `Battery limit`.
Английские имена контролов в `RunSet` не совпадают с подписями строк, и
локализация применяется к обоим (`Loc.T(what)`), так что расхождение
сохраняется и в русском: «Тайм-аут подсветки клавиатуры:» против «Тайм-аут
подсветки», «Ограничение заряда (~80%)» против «Ограничение заряда» (обе пары
есть в `Localization/Strings.Ru.cs`). Пользователь получает сообщение про
контрол, которого интерфейс ему не показывал — но получает, то есть это не
молчаливый отказ.

**Что решить:** брать имя из подписи строки (то есть перестроить `RunSet` так,
чтобы он получал уже локализованный label) или принять как есть.

**Ещё один экземпляр D17, не перечисленный в дизайн-документе:**
`LaptopService.Tuning.cs` `ApplyModeCpuPower` вызывает `cp.Set(id)` **внутри** `_state` и выбрасывает
результат. Не меняю: канала для ошибки у метода нет (возвращает `string?`), а
смена сигнатуры задевает вызывающих. Куда более широкий случай того же класса —
`CurrentModeKey()`, см. выше.

**`LastError` из очереди выведен** — его судьба решается владельцем.

**Проверка EOL — результат отрицательный, оставлено как есть.** Девять файлов в
рабочем дереве имеют чистый LF там, где `core.autocrlf=true` ожидал бы CRLF.
Смешанных переводов строк нет ни в одном файле, а на коммит это не влияет вовсе:
`* text=auto` нормализует в LF, и дифф показывает только строки комментариев.
Установить, были ли эти файлы LF **до** правки, невозможно — блоб в HEAD всегда
LF по нормализации, поэтому равенство `HEAD_blob_CR = 0` не доказывает ничего.
Первая моя формулировка («LF был и раньше») опиралась именно на эту негодную
проверку и была снята.
